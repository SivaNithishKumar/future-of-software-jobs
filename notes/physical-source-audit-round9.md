# MINERVA and GEOID-Flood: public source and manifest audit, round 9

Draft curation for the developer-futures research; checked 19 October 2026, 19:05 UTC. This is source inspection, not benchmark replication. No third-party code ran; no repository was cloned, package installed, or model/raster downloaded. Only public source, documentation and text metadata were read. Earlier reports and catalogues remain frozen.

## Result and scope of proof

MINERVA is an unusually explicit finite-task baseline: the inspected implementation converts a recognized instruction string to a learned integer task ID, rejects an unknown string, and evaluates binary simulator success over a declared 2,000 episodes. Its default asynchronous evaluator freezes completed environments, which supplies concrete counterevidence to blanket hidden-retry or initial-state-skipping accusations. The aggregate result remains a reported result, rather than independently rerun evidence. A small masking boundary defect exists in generic evaluation code, but this inspection does not show that it changes the headline score.

GEOID has inspectable selection, pairing and scoring rules, a real held-out evaluation configuration, and stronger metadata provenance than a paper-only proposal. Nevertheless, its sample manifest places the same activation in train and test; an AoI-separated split must not be called activation-separated. The default loader can substitute another sample after certain read failures, and model/modality comparisons can silently use different eligible subsets. Neither issue establishes that published results are wrong. They define specific denominator checks a useful engineering contribution should implement.

## MINERVA: instruction, task and trajectory identity

The public environment supplies `task.language`; evaluation prefers that description and calls the policy processor. That processor first accepts an existing integer ID, otherwise looks up the exact string or a normalized variant. Normalization lowercases, replaces underscores, removes terminal punctuation and collapses whitespace. Unrecognized text raises `KeyError`. The policy then embeds `task_index`; there is no semantic language encoder in this path. Dataset task names and indices are serialized into checkpoint configuration. This establishes fixed-label conditioning, not the stronger claim that every arbitrary instruction change is ignored. A previously unseen paraphrase may be rejected before action generation. [Environment lines 178–180](https://github.com/k1000dai/MINERVA/blob/64c3cc8be364eb62df4f9fdc4bdccb1be9d1118e/src/lerobot/envs/libero.py#L178), [processor lines 35–89](https://github.com/k1000dai/MINERVA/blob/64c3cc8be364eb62df4f9fdc4bdccb1be9d1118e/src/lerobot/policies/tinyflow/processor_tinyflow.py#L35), [model lines 55–68,135–151,506–524](https://github.com/k1000dai/MINERVA/blob/64c3cc8be364eb62df4f9fdc4bdccb1be9d1118e/src/lerobot/policies/tinyflow/modeling_tinyflow.py#L135).

The public task-ID probe rewrites only the mapping in `policy_preprocessor.json`: rotate to the next task within each suite or map all tasks to that suite's task-zero embedding. It leaves model weights unchanged. This is a real, controlled conditioning ablation already supplied by the authors. Repeating it is not an original language-generalization contribution. A useful extension separates normalization-equivalent strings, unknown paraphrases, contradictory known-task requests, and task-ID remapping, recording rejection and execution separately. [Probe lines 23–59](https://github.com/k1000dai/MINERVA/blob/64c3cc8be364eb62df4f9fdc4bdccb1be9d1118e/exp_small_libero/make_taskid_probe_ckpts.py#L23).

The headline training script pins the dataset revision, declares an L1 objective, a `t3C_2.75M` distillation teacher, task upweighting, 100,000 steps and inference ensembling. It does not declare a held-out demonstration list. Dataset defaults allow all episodes and disable the optional offline `eval_split`. Simulator rollouts are a different evaluation surface from demonstration holdout; neither a task-ID map nor a pinned dataset proves independent trajectories, novel tasks or a train/test near-duplicate audit. This pass did not obtain episode hashes, LIBERO asset revision or `.pruned_init` hashes, so those remain launch gates. [Training lines 8–24](https://github.com/k1000dai/MINERVA/blob/64c3cc8be364eb62df4f9fdc4bdccb1be9d1118e/exp_small_libero/train_t05_l1.sh#L8), [dataset defaults lines 26–51](https://github.com/k1000dai/MINERVA/blob/64c3cc8be364eb62df4f9fdc4bdccb1be9d1118e/src/lerobot/configs/default.py#L26).

Do not confuse the LIBERO-plus filename adapter with language removal. Its regex strips perturbation suffixes when locating compatible initial-state files; the environment separately retains `task.language`. That adapter needs asset/version auditing, but is not evidence that a language encoder was secretly bypassed. [Initial-state adapter lines 60–87](https://github.com/k1000dai/MINERVA/blob/64c3cc8be364eb62df4f9fdc4bdccb1be9d1118e/src/lerobot/envs/libero.py#L60).

## MINERVA: success, reset and denominator

1. The headline script specifies four suites, five parallel environments, 50 episodes per task, one concurrently evaluated task, one action step and ensembling coefficient 0.01. The saved TSV agrees with README rates 96.8/99.6/97.4/89.2, averaging 95.75. At 500 episodes per suite, this is arithmetically consistent with 484+498+487+446 = 1,915 successes from 2,000. This is a consistency calculation, not recovered episode logs. The broad `eval_all.sh` instead specifies 16 BID samples/two action steps; it is not the correct headline L1 reproduction command. [Headline script lines 28–47](https://github.com/k1000dai/MINERVA/blob/64c3cc8be364eb62df4f9fdc4bdccb1be9d1118e/exp_small_libero/train_t05_l1.sh#L28), [headline result](https://github.com/k1000dai/MINERVA/blob/64c3cc8be364eb62df4f9fdc4bdccb1be9d1118e/exp_small_libero/results_t05_l1.tsv), [other inference protocol](https://github.com/k1000dai/MINERVA/blob/64c3cc8be364eb62df4f9fdc4bdccb1be9d1118e/exp_small_libero/eval_all.sh#L41).
2. Each worker starts at an initial-state index equal to its worker index and increments by the parallel environment count at genuine reset, modulo available states. With five workers/ten batches, the intended schedule covers indices 0–49. A default seed of 1000 controls other randomness; it should not be described as independently sampling 50 new task distributions. [Reset lines 339–352](https://github.com/k1000dai/MINERVA/blob/64c3cc8be364eb62df4f9fdc4bdccb1be9d1118e/src/lerobot/envs/libero.py#L339), [worker factories lines 419–438](https://github.com/k1000dai/MINERVA/blob/64c3cc8be364eb62df4f9fdc4bdccb1be9d1118e/src/lerobot/envs/libero.py#L419).
3. Success is the simulator's `check_success()`. It ends the episode alongside simulator termination; the evaluator additionally caps the suite horizon at 280/280/300/520 steps for these suites. Without a success flag by that boundary, an episode contributes false, rather than disappearing. Reward sums/maxima are logged but there is no audited partial-credit, intervention or successful-retry metric. Task exceptions propagate through the runner; it does not catch and omit failed tasks. [Environment success lines 366–390](https://github.com/k1000dai/MINERVA/blob/64c3cc8be364eb62df4f9fdc4bdccb1be9d1118e/src/lerobot/envs/libero.py#L366), [rollout lines 263–378](https://github.com/k1000dai/MINERVA/blob/64c3cc8be364eb62df4f9fdc4bdccb1be9d1118e/src/lerobot/scripts/lerobot_eval.py#L263), [runner/aggregate lines 1033–1097](https://github.com/k1000dai/MINERVA/blob/64c3cc8be364eb62df4f9fdc4bdccb1be9d1118e/src/lerobot/scripts/lerobot_eval.py#L1033).
4. Default evaluation is asynchronous. Its terminal-freeze wrapper absorbs automatic resets and replays a completed transition with zero reward until a genuine new-rollout reset. This protects initial-state scheduling and avoids substantial wasted simulation. The synchronous branch lacks that wrapper, so changing async/batch configuration requires a schedule check rather than assuming equivalence. [Default lines 94–101](https://github.com/k1000dai/MINERVA/blob/64c3cc8be364eb62df4f9fdc4bdccb1be9d1118e/src/lerobot/configs/default.py#L94), [freeze/wrapper lines 180–289](https://github.com/k1000dai/MINERVA/blob/64c3cc8be364eb62df4f9fdc4bdccb1be9d1118e/src/lerobot/envs/utils.py#L180), [sync branch lines 517–527](https://github.com/k1000dai/MINERVA/blob/64c3cc8be364eb62df4f9fdc4bdccb1be9d1118e/src/lerobot/envs/libero.py#L517).
5. A scoped defect: the generic first-done mask is `step <= first_done_index + 1`; it retains one extra transition. For zero-based terminal index 2, it retains 0,1,2,3. The async freeze returns zero reward and the same already-known success flag, which materially limits score consequences. This arithmetic is not evidence of an inflated 95.75 result. An independent boundary oracle should test both vector modes before modifying code. [Mask lines 551–565](https://github.com/k1000dai/MINERVA/blob/64c3cc8be364eb62df4f9fdc4bdccb1be9d1118e/src/lerobot/scripts/lerobot_eval.py#L551).

The README itself distinguishes the single training seed, simulator-only results, visual/geometric robustness drops and a mismatched pi0.5 reference. Those limitations survive this audit. There is no source-backed claim of physical robot reliability, novel language grounding, paid labor saved or full camera-to-actuator latency. [Limitations lines 210–222](https://github.com/k1000dai/MINERVA/blob/64c3cc8be364eb62df4f9fdc4bdccb1be9d1118e/README.md#L210).

## GEOID: actual manifest and split contract

The checked-HEAD sample CSV contains test rows for `EMSR712-3-9` and train rows for `EMSR712-10-3`, both with activation `EMSR712` and event date `2023-12-24T08:00:00`. Test examples use 256-pixel offsets; training examples include 128-pixel offsets. Thus activation-disjointness does not hold for the released sample. It remains possible that the AoIs are spatially separated; no geometry bytes were inspected. Do not turn this counterexample into a claim of overlapping pixels or quantify the full release's activation leakage from it. [CSV header/test rows 1–34 and train rows around 3242–3304](https://huggingface.co/datasets/links-ads/geoid-flood/raw/main/sample/geoid-flood/data_tiles_s256_st128_sample.csv).

The same sample records S1 pre-image `2023-09-08T17:09:31` and post-image `2024-01-03T05:33:41` for a December 24 event: approximately 106.62 days before and 9.90 days after the recorded event timestamp. Those are metadata differences, not independently established flood-onset errors, label times, product delivery latency or model latency. They motivate acquisition/delineation/availability checks before proposing near-real-time flood detection. The loader uses filename acquisition suffixes for optional model timestamps, falling back to **2024-06-15** for malformed/missing suffixes; it does not enforce date eligibility or activation separation. [CSV test rows](https://huggingface.co/datasets/links-ads/geoid-flood/raw/main/sample/geoid-flood/data_tiles_s256_st128_sample.csv), [timestamp parser lines 45–62](https://github.com/links-ads/geoid-flood/blob/3a1647ed11aea0c81d5f59a8022e9cb8548bddab/src/geoid_flood/datasets/geoid.py#L45).

The loader trusts the CSV split; `make_tiles.py` copies event date/split from the tile catalog. Neither computes independent activation or temporal splits. It does deliberately make val/test non-overlapping within each raster by default, while permitting an explicit evaluation-stride override. This is counterevidence to a generic overlapping-patches accusation. The catalog filter `is_valid AND invalid_pixel_frac <= .95` is explicit. The dataloader then further filters cloud/positive/valid fractions; benchmark configs use at least 1% valid pixels. These are selected and partially labeled pixels, not complete arrival coverage. [Tile selection/copy lines 110–142](https://github.com/links-ads/geoid-flood/blob/3a1647ed11aea0c81d5f59a8022e9cb8548bddab/scripts/make_tiles.py#L110), [stride lines 171–178](https://github.com/links-ads/geoid-flood/blob/3a1647ed11aea0c81d5f59a8022e9cb8548bddab/scripts/make_tiles.py#L171), [loader filters lines 160–188](https://github.com/links-ads/geoid-flood/blob/3a1647ed11aea0c81d5f59a8022e9cb8548bddab/src/geoid_flood/datasets/geoid.py#L160).

The published checksum list declares sample CSV SHA-256 `87dc69765c1081225735fc79ba22c88b2d01ee2596530076183b390b1839439a`; full CSV `8b6e4eb8e1b95cd8f0030458a0332f5562d6886bf5fc2da497d5ba66d8897998`; held-out CSV `0413da55f4892989935ac189fda231c4f6d08d301df36ce2dbfbb942fccfdd39`. They were read, not recalculated. Full CSV is displayed as 411 MB and was not fetched; the parquet catalog was not parsed. Full activation-intersection, geometry and held-out date counts remain unknown. [Checksum manifest](https://huggingface.co/datasets/links-ads/geoid-flood/blob/main/SHA256SUMS), [full metadata listing](https://huggingface.co/datasets/links-ads/geoid-flood/tree/main/geoid-flood).

## GEOID: modality, reference and score denominators

Paired data requires both temporal groups and every requested time-varying/static modality; incomplete groups are dropped. Unpaired multimodal data also requires a complete requested set. Two models with different modalities can therefore be evaluated over different samples unless the experiment explicitly intersects eligible sample IDs. The pre/post mapping uses a single three-class reference: permanent water is water in both binary targets; flooded water is background before and water after. This is a useful supervised target construction, not two separately observed contemporaneous labels. [Grouping lines 208–318](https://github.com/links-ads/geoid-flood/blob/3a1647ed11aea0c81d5f59a8022e9cb8548bddab/src/geoid_flood/datasets/geoid.py#L208), [label mapping lines 394–406](https://github.com/links-ads/geoid-flood/blob/3a1647ed11aea0c81d5f59a8022e9cb8548bddab/src/geoid_flood/datasets/geoid.py#L394).

The paired scorer makes separate pre/post forward passes, reconstructs three classes by combining predicted water masks, excludes ignored pixels and updates global confusion-based macro IoU/F1 plus per-class IoU. It is not an activation-macro metric, uncertainty calibration, onset detector, recovery metric or all-arrival service availability. It supports `--max-batches` for smoke testing but writes the same metric tags; a partial run must be flagged externally. No unique-requested/returned coverage counter is emitted alongside those scores. [Scorer lines 171–182,283–335](https://github.com/links-ads/geoid-flood/blob/3a1647ed11aea0c81d5f59a8022e9cb8548bddab/scripts/eval_flood_paired.py#L283).

Default `skip_bad_samples=True`, `max_skip_retries=16` catches raster/read/missing-file failures and returns the next loadable index, wrapping around. This is logged, not entirely silent, but is not reflected in a requested-versus-returned metric denominator. A pass over requests [0,1,2] can return [1,1,2] when 0 is unreadable. That is a fabricated mechanism fixture, not evidence that released rasters are corrupt. Test dataloaders retain the final incomplete batch, so the issue is replacement, not blanket `drop_last` loss. The held-out config explicitly enables the replacement path. [Defaults lines 72–95 and fallback lines 409–454](https://github.com/links-ads/geoid-flood/blob/3a1647ed11aea0c81d5f59a8022e9cb8548bddab/src/geoid_flood/datasets/geoid.py#L409), [dataloader lines 232–243](https://github.com/links-ads/geoid-flood/blob/3a1647ed11aea0c81d5f59a8022e9cb8548bddab/src/geoid_flood/datamodules/geoid.py#L232).

Reference masks are not secretly fed into the audited input path: supported image modalities are S1 GRD/RTC, S2 and DEM; labels are returned separately. FloodSegmentationTask strips bookkeeping keys before forwarding. Annual permanent-water reference construction can still influence target quality or temporal suitability, but this code does not establish annual-reference input leakage. A label-generation provenance implementation was not found in the complete public tree; a comment names an external acquisition tool path absent from that tree. Ground-truth creation, manual review exclusions and same-year feature eligibility need independent evidence. [Input dispatch lines 328–378](https://github.com/links-ads/geoid-flood/blob/3a1647ed11aea0c81d5f59a8022e9cb8548bddab/src/geoid_flood/datasets/geoid.py#L328), [task input allowlist lines 28–45](https://github.com/links-ads/geoid-flood/blob/3a1647ed11aea0c81d5f59a8022e9cb8548bddab/src/geoid_flood/tasks/flood_segmentation.py#L28).

Artifact acquisition also needs explicit version control. The pinned downloader verifies available shard hashes, checks disk requirements and uses atomic extraction, but its `hf_hub_download` calls omit a Hub revision. A pinned code checkout alone does not pin downloaded data. Proposed execution must supply the separately declared data revision and verify metadata and shard checksums, without using a resource-preflight override. [Downloader lines 63–77,160–177,212–224](https://github.com/links-ads/geoid-flood/blob/3a1647ed11aea0c81d5f59a8022e9cb8548bddab/scripts/get_data.py#L160).

## Attainable contributions and launch gates

These are alternatives, each budgeted at approximately 40 working hours in 30 days and 120 total hours in 90 days. Neither is a promise of employment or production readiness. No download/install/run is authorized by this report itself; existing research constraints remain in force.

**MINERVA path.** In 30 days, spend the first eight hours resolving source/weights/data/asset rights and exact configs; stop or narrow to a source-only audit if one required artifact remains inaccessible. Build an independently authored task/episode ledger and terminal-state oracle, then, only with an approved runtime, reproduce one suite over its 50 initial states per task. Record requested/completed/exception/timeout/rejection counts, task and init-state hashes, first success step, exact inference config and host/runtime. Compare original mask versus terminal-inclusive mask and async versus sync schedule before interpreting any score. Acceptance: all planned IDs accounted for exactly once, no unrecorded retry/substitution, and an independently checked success/timeout boundary fixture. The 90-day extension adds at least three training seeds if resource preflight permits, held-out visual/geometric perturbation families, a small classical visual+proprioception or compact CNN baseline, paired episode evaluation and failure confidence intervals. Unknown language rejection is a separate metric. If timing cannot include simulator/render/transport, label timing as policy-only. If instruction semantics remain unavailable, present a finite-task robustness tool, not a general VLA.

**GEOID path.** In 30 days, first verify rights for each chosen layer, metadata checksum and available disk/RAM; use text manifests before raster acquisition. The documented sample is about 3.09 GB, so it is not a tiny fixture, and its train/test result cannot demonstrate unseen-activation generalization. Build activation/AoI/date/modality intersection reports and an independent requested/returned/unique-ID ledger; explicitly separate label-derived selection from deployment eligibility. Gate progression on zero activation intersection for the intended generalization split, all image/label/availability timestamps represented or explicitly unknown, zero unrecorded substitute samples and a fixture distinguishing ignored pixels from correct background. After authorized data access, compare a SAR change/threshold baseline and a compact segmentation baseline with the frozen model on identical sample/pixel support. In 90 days, evaluate whole held-out activations and a future time block, report per-activation intervals, onset/availability lag, valid-area coverage, missing-modality failure and compute/storage cost per accepted map. Use a later official delineation as an independent retrospective oracle; it is not a real-time operational oracle. Kill a model-gain claim if eligible supports differ or acquisition/label timing cannot be reconciled; retain an engineering contribution if the ledger exposes that limitation honestly.

What these projects can prove: deterministic evaluation contracts, finite-task robustness under declared perturbations, selected-domain flood mapping accuracy and practical provenance/coverage tooling. What they cannot prove: physical recovery, safe autonomous control, real-time disaster response, labor savings or commercial demand. The relevant paid engineering work is data/evaluation integrity, runtime and pipeline integration, and failure accountability; research-policy or novel geophysical claims require stronger experimental supervision and domain grounding.

## Validation and unresolved evidence

`physical-source-audit-round9-fixtures.json` contains only independently written arithmetic/fabricated mechanisms: reported-rate consistency, zero-based terminal-mask boundary, hypothetical sample substitution, intended async init-state enumeration, and two observed timestamp differences. All completed locally using Python's standard library. No benchmark inference, simulator, raster IO, training or model execution occurred.

Unresolved: MINERVA historical execution hash, full resolved checkpoint configs, per-rollout outcomes, exact LIBERO init/BDDL assets and demonstration independence; GEOID immutable byte verification, full activation/geometric/time intersection, reference-generation pipeline, actual corrupt-read frequency, per-model eligible-subset counts and whether any published score used debug truncation. These are marked unknown rather than inferred defects. The companion proposals JSON adds scoped claims and launch gates to existing record IDs; it does not edit frozen curation or assert final acceptance.
