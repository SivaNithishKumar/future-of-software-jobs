# State estimation: clock, gauge freedom and failed-support audit, round 13

Owner: robotics_physical. Checked 19 October 2026 UTC / 20 October IST. Draft evidence and projects. No main-tree or frozen-report edits.

## Precise gap and developer implication

Existing robotics, field robotics, compute and interface notes already cover SLAM broadly, SE(3), timestamps and degraded-localization metrics. This pass addresses a narrower unresolved claim: **can an apparently accurate trajectory still have the wrong clock, scale, frame or tracking denominator?** It audits the 2026 Hilti protocol, mature OpenVINS source and current evo source, rather than another SLAM history or model roundup.

Yes: alignment and timestamp association can intentionally remove information; unmatched/failed output can disappear from a local error metric. That is not automatically a defect or evidence of benchmark misconduct. These are different questions that require different evaluation contracts. Preserve explicit safeguards where they exist.

Inference through 2031: an accessible software entry is rigorous replay, calibration/provenance, estimator integration and performance measurement, followed by deeper estimator/control work if the mathematics and field access fit. It is not evidence of skill scarcity, employment growth or an underserved startup market. Existing estimators and evaluation tools already solve substantial parts of this problem. A new “SLAM dashboard” or wrapper needs a concrete advantage.

## What the source establishes

### 1. A benchmark score can have sensible safeguards

The pinned [Hilti evaluation guide](https://github.com/Hilti-Research/hilti-trimble-slam-challenge-2026/blob/ca58b646cbafa799e518b0a354982b7fbfa1e94a/docs/challenge-evaluation.md#L18) requires at least **99% matched-ground-truth coverage**, otherwise a run scores zero. It excludes the first five seconds because the reference starts later; this exclusion is documented rather than silently attributed to successful initialization. Scale correction is expressly forbidden. SLAM and map-referenced localization are distinct tasks; the paper specifies rigidly aligned 3-D SLAM versus unaligned 2-D floor-plan localization. Localization ignores height. The guide excludes five early-release ground-truth runs and one additional no-floor-plan sequence for localization: 25 SLAM runs versus 24 localization runs.

Keep those denominators. A low-coverage matched-only ATE critique cannot be transferred to this benchmark without checking the server’s implementation. The **server’s full scoring source and exact timestamp-association configuration were not obtained**; guide/paper agreement does not establish independently reproduced server behaviour. The general repo helper inspected here publishes/loads trajectories and is not that server.

The [current ground-truth guide](https://github.com/Hilti-Research/hilti-trimble-slam-challenge-2026/blob/ca58b646cbafa799e518b0a354982b7fbfa1e94a/docs/ground-truth.md#L6) names the pose convention: camera 0 expressed in the map frame. It provides an initial reference pose near timestamp 10005 seconds. [Sensor docs](https://github.com/Hilti-Research/hilti-trimble-slam-challenge-2026/blob/ca58b646cbafa799e518b0a354982b7fbfa1e94a/docs/sensors.md#L38) explain a common 10,000-second shift, avoiding negative IMU timestamps. The actual tiny CSV header and rows were read; it is an initial-pose fixture, **not a continuous trajectory, covariance file or a successful SLAM result**.

The [OpenVINS demonstration guide](https://github.com/Hilti-Research/hilti-trimble-slam-challenge-2026/blob/ca58b646cbafa799e518b0a354982b7fbfa1e94a/docs/openvins.md#L6) expressly says its displayed trajectory is aligned to the initial ground-truth pose and is **not explicitly localizing against the floor plan**. The install commands select the Hilti fork. [Camera documentation](https://github.com/Hilti-Research/hilti-trimble-slam-challenge-2026/blob/ca58b646cbafa799e518b0a354982b7fbfa1e94a/docs/sensors.md#L64) explains its EUCM support and fitted pinhole-equidistant parameters. Thus “OpenVINS supports this dataset” needs the correct fork, camera model and configuration; a visually convincing map overlay does not establish map matching.

The reference labels and all trajectories were released after the challenge, according to the pinned README. A later developer may legitimately use them, but must declare any tuning and construct a new holdout before claiming unseen-session performance. A single evolving building also does not establish a new-site holdout.

### 2. Gauge freedom must match the intended task

The upstream [OpenVINS alignment implementation](https://github.com/rpng/open_vins/blob/69488123ed9362dd44b6f28e7f4680abbff1442b/ov_eval/src/alignment/AlignTrajectory.cpp#L26) supports no alignment, position+yaw, rigid SE(3), single-pose variants and scale-adjusting Sim(3). These modes remove different freedoms. Gravity-aligned metric VIO and monocular vision without an observable scale are not interchangeable evaluation settings.

[evo APE](https://github.com/MichaelGrupp/evo/blob/3ca861e03a412626c4faa0b71c6140b1f44295d6/evo/main_ape.py#L34) separately supports rigid alignment, scale correction, origin alignment and projection. Its default function parameters do not align or correct scale; the library is not secretly correcting every trajectory. [Trajectory alignment](https://github.com/MichaelGrupp/evo/blob/3ca861e03a412626c4faa0b71c6140b1f44295d6/evo/core/trajectory.py#L237) explicitly implements a chosen prefix length by slicing the position arrays, or all poses with n=-1. Whole-trace alignment is a valid retrospective shape metric; it does not prove the frame transform was available online. Origin/prefix registration and an unaligned map-frame result answer different questions.

A scoped source discrepancy deserves a later regression fixture: OpenVINS’ [alignment header](https://github.com/rpng/open_vins/blob/69488123ed9362dd44b6f28e7f4680abbff1442b/ov_eval/src/alignment/AlignTrajectory.h#L57) documents n_aligned as the number of alignment poses. In the inspected .cpp, branches handle n=1 specially, but the other positive values do not bound the loops before Umeyama. The ordinary ResultTrajectory caller uses the default all-pose mode, so this does **not** invalidate its default reports. It is a potential contract mismatch for callers expecting an n>1 prefix; no executable reproduction or effect on published results is claimed. evo’s inspected slicing provides contrary evidence that the same concern does not apply to its n parameter.

Frame conventions also matter. OpenVINS uses JPL-oriented state types and notes world-to-IMU versus IMU-in-world conventions; its calibration state names the transform into the camera. TUM file storage order alone does not specify quaternion algebra, active/passive transform direction or sensor origin. Camera-pose ground truth cannot be compared directly to IMU-origin positions without the lever arm and orientation transformation. An apparently small translation fit can conceal that error on restricted motion.

### 3. Association is not sensor-clock calibration

[evo’s association](https://github.com/MichaelGrupp/evo/blob/3ca861e03a412626c4faa0b71c6140b1f44295d6/evo/core/sync.py#L42) matches timestamps within a tolerance and optional **constant offset**. It copies/reduces trajectories to matched support; the API also offers interpolation at timestamps of the sparser trajectory. The [current CLI parser](https://github.com/MichaelGrupp/evo/blob/3ca861e03a412626c4faa0b71c6140b1f44295d6/evo/cli/ape_parser.py#L232) exposes those choices and a default 0.01-second association tolerance. This is not an affine clock-skew estimator. Interpolation does not create independent measurements or establish that a missing estimate existed.

Nearest matching searches per timestamp and does not enforce unique use of the longer stream’s indices in the inspected function. Dense clusters and gaps therefore need explicit duplicate/unique-support accounting in an extension. No actual Hilti scoring exploit or real dataset inflation was demonstrated.

OpenVINS’ [local ResultTrajectory helper](https://github.com/rpng/open_vins/blob/69488123ed9362dd44b6f28e7f4680abbff1442b/ov_eval/src/calc/ResultTrajectory.cpp#L26) associates at zero offset with a 0.02-second tolerance and computes errors on the resulting intersection. Its [association utility](https://github.com/rpng/open_vins/blob/69488123ed9362dd44b6f28e7f4680abbff1442b/ov_eval/src/alignment/AlignUtils.cpp#L114) explicitly advances the reference pointer to enforce injectivity, unlike the nearest-evo helper. Neither local helper alone establishes the attempted-run or wall-clock availability denominator. These are different protocols, not proof one package is universally wrong.

The [Hilti September synchronization update](https://github.com/Hilti-Research/hilti-trimble-slam-challenge-2026/blob/ca58b646cbafa799e518b0a354982b7fbfa1e94a/docs/ground-truth.md#L16) goes further: it uses angular-rate norms from two IMUs, correlation initialization, then offset plus **linear clock-scale** refinement, interpolation and joint gyro-bias optimization. Its LiDAR/IMU hardware uses PPS; the independently running camera system is aligned in software. Preserve that actual clock-scale treatment rather than describing the reference as hardware-synchronized end to end.

Upstream [OpenVINS State.h](https://github.com/rpng/open_vins/blob/69488123ed9362dd44b6f28e7f4680abbff1442b/ov_msckf/src/state/State.h#L140) names one scalar camera-to-IMU time-offset state, with t_imu=t_cam+t_offset. That is not an explicit affine skew state. Updating a scalar online might accommodate some changing offset; its performance under skew is not established by merely reading the state definition. Constant angular-rate data also cannot identify offset from its constant norm. Calibration needs informative motion and identifiable models; turning every calibration switch on is not evidence of observability.

### 4. Error, confidence and compute need independent support

[OpenVINS NEES source](https://github.com/rpng/open_vins/blob/69488123ed9362dd44b6f28e7f4680abbff1442b/ov_eval/src/calc/ResultTrajectory.cpp#L244) requires recorded covariance and skips NaN results with a warning. The dataset helper aggregates some time-indexed RMSE/NEES only when all supplied runs contribute at that timestamp ([lines 248–274](https://github.com/rpng/open_vins/blob/69488123ed9362dd44b6f28e7f4680abbff1442b/ov_eval/src/error_dataset.cpp#L248)). A consistency plot therefore needs its support counts and invalid-covariance count, not only its mean.

NEES uses an error and an appropriate covariance; its expected degrees-of-freedom interpretation assumes a correctly specified reference/error model. It is not required to equal three at every individual time. Correlated samples from one trace are not independent Monte Carlo runs. Ground-truth uncertainty, alignment/gauge fitting and covariance frame must be handled before a field confidence guarantee is asserted. A low ATE does not establish honest uncertainty.

The [timing documentation](https://github.com/rpng/open_vins/blob/69488123ed9362dd44b6f28e7f4680abbff1442b/docs/eval-timing.dox#L15) distinguishes estimator component duration from process CPU/memory and warns against cross-hardware CPU-percentage comparisons. Internal estimator timing omits some capture, decoding, transport, queue, scheduling and publication work. Compare named CPU/threads/compiler/backend, sensor rates, input size, processing delay, dropped measurements, memory and deadline misses. Offline global optimization and online causal estimates need separate tables. No benchmark runtime was reproduced here.

## Independently authored fixtures: what they prove

The companion JSON includes actual tiny analytic pose/gyro/specific-force samples, with declared frames, quaternion storage, clock mapping and gravity. It is not an empty schema. It also contains closed-form counterexamples, checked with independently written standard-library arithmetic:

- A unit square estimated at twice its metric scale has zero error after a known scale correction; with rigid alignment alone its position RMSE is sqrt(0.5). This is not an evo execution.
- On constant 2 m/s motion, a 10 ms time error produces 2 cm position error; a global translation can remove it. Zero aligned ATE does not identify the clock.
- A 50-ppm clock-scale mismatch accumulates 9 ms over 180 seconds. A constant fit at the midpoint still leaves a maximum 4.5 ms end residual under this clock model.
- Returning only 20 perfect poses of 100 attempted ones yields zero matched-only error and 20% support. The declared Hilti 99% rule rejects this example.
- A synthetic 0.1 m position error with isotropic 0.01 m standard deviation gives NEES 100. One residual is not a statistical consistency experiment.

The tiny motion fixture uses a circular path with **varying** angular speed from a closed-form angle. Specific force is derived analytically in the rotating IMU frame, separately from position generation. Its yaw-only excitation does not calibrate all six-degree-of-freedom extrinsics. The richer 90-day proposal must add independent 3-D motion; this fixture demonstrates units/time/geometry plumbing only.

## Proposed 30/90-day path, without new hardware

### First 8 hours and day 30: at most 40 hours

Build a small trajectory/clock contract checker before an estimator. Use own analytic traces and the existing tiny fixture, with explicit t_reference, t_sensor, frame direction, q storage/algebra, units, pose validity and attempted sample IDs. Add a second independently implemented transform/time calculation and known translations/rotations; shared generator/evaluator code is not an independent oracle. Include quaternion-sign equivalence and a changing orientation with a nonzero camera–IMU lever arm.

Launch gates: inspect one actual pose/IMU fixture and reference association; verify source/rights, host dependencies and output fields; freeze alignment freedom, timestamp tolerance and attempted support. Any new package installation remains a separate explicit approval. No internet upload or benchmark submission is part of this experiment.

Compare four declared modes on the same trace: unaligned map-frame error, origin/prefix registration, all-trace rigid registration and diagnostic Sim(3). Keep Sim(3) out of the metric-VIO acceptance result. Compare known-clock, constant-offset and affine-clock association, plus a strict one-to-one baseline. An offline fit using future reference poses is labelled retrospective, not causal calibration.

Acceptance: all closed-form fixtures agree within 1e-8 for double-precision geometric calculations; malformed/nonmonotonic/duplicate timestamps, missing frames and invalid quaternions are counted and refused where the contract requires. Do not hide lost support by shortening the denominator. On noiseless, informative synthetic signals, recover the injected offset/skew so heldout timing residual is <=1 ms over a declared 60-second test. On constant-rate/insufficient motion, report ambiguity or refusal rather than a falsely precise calibration. These are educational targets, not industrial specifications.

Limit the first corpus to <=10,000 poses/IMU samples, <=25 MB saved output, <=1 GB process memory and <=60 seconds per evaluator trial on the measured host. These chosen limits need measurement; no runtime claim is made now. A successful outcome proves evaluation and synchronization semantics on analytic data. It does not prove visual tracking, actual IMU noise, rolling-shutter calibration, relocalization or safe navigation.

Kill a result if a gauge fit hides the injected error yet is labelled a physical correction; if the evaluator fits clock/calibration on final truth and calls it online; if independent fixture calculations disagree; or if coverage and invalid covariance are omitted. If mature tools plus a small adapter meet the whole task, retain them and do not build a new evaluation platform.

### By day 90: at most 120 hours total, conditional native baseline

Use the pinned upstream OpenVINS **simulated feature/IMU path**, conditional on approved dependency installation and an actual native input/output fixture. The [ROS-free guide](https://github.com/rpng/open_vins/blob/69488123ed9362dd44b6f28e7f4680abbff1442b/docs/gs-installing-free.dox#L4) permits that interface but explicitly calls its support limited. It needs C++/CMake and Eigen, OpenCV, Ceres/Boost; the complete toolchain lock was not tested. Current evo metadata requires **Python >=3.11**, despite README text saying >=3.10: use the pinned package metadata and a measured environment preflight.

The inspected [run_simulation entry point](https://github.com/rpng/open_vins/blob/69488123ed9362dd44b6f28e7f4680abbff1442b/ov_msckf/src/run_simulation.cpp#L115) initializes from ground truth and feeds **projected feature measurements**, not camera images. It forces repeatability-related threading choices. ROS-free builds also need an explicit bounded recorder/adapter because normal visualization/output calls are conditional on ROS. Thus the easiest no-camera run tests tracking/calibration **after privileged initialization**; it does not reproduce dynamic initialization or image-feature tracking. Preserve this limit in every result.

Start with 30 seconds, 30-Hz feature updates, 200-Hz IMU and a small fixed landmark set. Cap a trial at 10 minutes, 2 GB memory, 100 MB output; full planned sweep <=2 CPU-hours before reconsideration. Freeze seeds/noise/landmarks across paired comparisons. Expand to at most ten independent seeds after the first successful actual run. This is a chosen portfolio budget, not a published OpenVINS minimum.

Compare fixed correct calibration, fixed injected offset and online scalar offset under rich versus degenerate motion. A skew-injected adapter is a separately declared input perturbation; native offset estimation is not relabelled an affine model. Use known analytic geometry and independently derived IMU/feature projection checks to limit shared-simulator oracle bugs. Hold an entire motion family, noise realization and offset/skew regime out; random individual timestamps are not an adequate split.

Measure initialization privilege, attempted/returned/unique-matched poses, tracking gaps, raw and gauge-declared ATE, time/distance RPE at fixed intervals, offset/skew residual, invalid covariance and causal output age. Compare covariance in a declared anchored error frame across independent seeds; report finite-sample uncertainty and do not infer calibrated field confidence from ten traces. Count all trials, aborted runs and deadline misses.

A useful final deliverable is a small source-backed regression or measurement adapter with a negative result path. Native-library agreement on the analytic fixtures must precede claiming a source defect, including the n_aligned mismatch. No source issue, PR or contact is authorized here. Kill the extension if the complete environment/recorder cannot be pinned inside the budget or the only improvement needs future truth. Later camera/field proof separately requires actual timestamp/exposure/rolling-shutter calibration, mount rigidity, sensor faults and an independent physical reference with known coverage/uncertainty. Synthetic feature IDs cannot substitute for those tests.
