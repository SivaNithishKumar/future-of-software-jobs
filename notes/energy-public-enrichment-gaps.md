## What was curated and checked

Read the existing taxonomy, institution directory, catalog requirements, corrections, independent actionability review and all five authored energy/public reports. The JSON records hashes of those input snapshots. Earlier notes and the main tree were not edited. Source evidence is carried from those notes with file/line pointers; no web retrieval, software/data installation, benchmark execution, private access, outreach or application occurred during round 6.

Structural validation checks unique IDs, all existing technical-node links, patch targets, linked catalog records and source IDs. It also rechecks input hashes. This proves reference consistency for the inspected snapshots; it does not establish the truth, completeness or current availability of every carried claim.

The generator checks and a separate JSON parse/record-contract check **passed**: 144 new catalog records, eight existing-identity patches, 129 source records, seven unmerged subnode proposals and nine unexecuted projects. All 288 IDs are unique, references resolve against the inspected taxonomy/directory, and all ten input hashes remained unchanged. One source has an explicit durable-provenance gap, detailed under CUBE below.

Each of nine project records includes a **30–50 focused-hour first month and 90–150 total-hour three-month planning assumption**, a 5–10-hour setup stop budget, an assumed 4–8-hour reviewer allowance and explicit unknown actual user availability. These are estimates, not measured runtimes or a personal commitment. Choose one main project. The JSON distinguishes learning, tested implementation, operational workflow, hiring eligibility and recurring paid demand. None of the latter four is established merely by drafting a project.

## Corrections integrated into the new records

- **Energy replay:** retain event/target, publication/revision, retrieval, endpoint, completeness/pagination and transformation version. A later revision must not alter the reconstructed earlier information set. Compare against SQL over the same source data.
- **Battery dispatch:** define tariff/settlement, fees, reserve, efficiency, terminal energy and degradation before solving. Already-published forward prices can be legitimate; unpublished realized prices cannot be silently used. PyPSA's no-export/constant-import-cost toy excludes forecast error and is not a full arbitrage backtest. Current docs state HiGHS is included by default; a commercial solver is not an unavoidable launch dependency.
- **FlexDC:** the initial proof is batch completion/deadline simulation. Supplied P100 profiles and sojourn thresholds do not validate interactive TTFT/TPOT, prefill/decode, KV memory, modern hardware power or a real utility response.
- **Rights:** code, weights, source documents, datasets, transformed data and similarly named implementations have separate terms. Unknown rights are a launch gate, not a negative finding that the whole field is inaccessible.
- **Value:** native Siemens/NVIDIA/water/legal platforms and Redbox's documented discontinuation make competition concrete. Residual engineering tasks, a job, a successful workflow and a defensible business are separate claims.

## Rights, version and methods gaps

1. **CAMELS-IND:** exact dataset licence did not render. Version 2.2's 242 sufficient-observation gauges differs from the paper's 228; observed and model-filled discharge coexist. Confirm selected files' terms and target flags before reuse. Predicted flow cannot become independent truth.
2. **CAMELS-GB/EA:** paper states OGL, but individual metadata, flags, coverage and attribution still need a launch manifest. Observation/reanalysis records do not establish archived operational weather issue times. Until that is proven, use the word **hindcast**, not operational forecast lead time.
3. **BattLeDIM/WNTR/EPANET:** benchmark data rights were supported by a government catalog; exact selected file/evaluator/component licences need confirmation before distribution. Public 2019 test labels require an untouched extra regime/network. A synthetic leak oracle cannot validate utility discovery/repair effectiveness. No repair record is not automatically a negative label.
4. **AquaCrop:** FAO Python and AquaCrop-OSPy are different implementations. The former's inspected licence restricts commercial reproduction; the latter's package metadata declares MIT. No cross-implementation permission or numerical equivalence is assumed. Agronomic/field benefit remains unvalidated.
5. **FAIR-MAST:** active historical archive, MIT software and CC-BY-SA data/site except resource exceptions. The older MAST request portal has different noncommercial/share-alike wording and incomplete validation. Do not apply one archive's terms to every resource. No endpoint was exercised. Historical publication/calibration fields may be unavailable and must stay unknown.
6. **FDS/PROCESS/OpenMC:** FDS has no deployments and provisional schema/API; synthetic examples are not real-data permission. PROCESS needs a released case and supported-environment comparison for sensitive convergence. OpenMC cross-section/ENDF processing and some NJOY test dependencies are separate from code rights. No build/data/runtime compatibility or numerical result was tested.
7. **LegalBench-RAG:** MIT code does not erase four underlying datasets' policies. Corpus regeneration is LLM-assisted and not byte-equivalent. Its precision/recall task does not prove legal application.
8. **OmniDocBench:** Apache-2.0 repository code; separate unambiguous dataset licence not located in inspected card. Current 1,651-page version differs from older 1,355-page reports. 11. **2025 commercial legal-tool study:** exact evaluation is March–May 2024, not a current 2026 vendor comparison. 13. **ThemeFinder:** README still calls it incubation and unsuitable for critical uses. Its setup defaults can upload to an organizational S3 bucket. No command was run; any future approved local adaptation must disable external writes and use synthetic inputs. Public source code is not private consultation-data access.
