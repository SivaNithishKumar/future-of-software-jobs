## Finding and uncertainty

**Inference:** a developer can enter this area through reliable decision software considerably sooner than through inventing a new optimization algorithm. The useful combination is software engineering + mathematical modeling + a specific operational workflow + independent validation. This is an existing commercial activity. Whether it grows employment by 2031, and whether it suits the reader's actual mathematical depth, remain unmeasured. A solver API tutorial alone is weak evidence of readiness.

The counterargument matters: modeling, code generation and heuristic design are themselves being automated. The defensible preparation is the ability to specify what a valid decision means, find a strong baseline, measure consequences under uncertainty, and get a system used. Do not describe OR as an automation-proof refuge.

## The technical tree to preserve in the eventual mind map

These are stable knowledge branches. Particular future commercial opportunities are hypotheses attached underneath them.

- **Decision problem ownership**
  - Identify the decision, its owner, and when it must be made.
    - Strategic: facility/network design, capacity investment, make/buy choices.
    - Tactical: inventory targets, production quantities, crew/vehicle allocation.
    - Operational: dispatch, sequencing, shift assignment, disruption recovery.
  - Specify the feasible actions.
    - Physical capacity, task precedence, qualifications, calendars, inventory conservation.
    - Hard constraints versus explicitly priced soft constraints.
    - Contradictory requirements → an explained infeasibility result, not a fabricated plan.
  - Specify value.
    - Cost/service/tardiness/throughput tradeoffs → units and stakeholder-approved priorities.
    - Model objective → independently recomputed outcome → observed operational value.
- **Optimization methods**
  - Network structure: shortest paths → assignment/matching → min-cost flow → network design.
  - Continuous decisions: linear programming → duality/sensitivity → convex quadratic/conic models.
  - Discrete decisions: mixed-integer formulations → relaxations/bounds → branch-and-bound/cuts → decomposition/column generation.
  - Scheduling/logic: constraint propagation → intervals/no-overlap/cumulative resources → CP-SAT → optional tasks and alternative machines.
  - Large instances: constructive heuristics → local/large-neighborhood search → hybrid methods → anytime solution quality.
  - Specialized solver engineering: presolve, numerics, sparse linear algebra, parallel search, proof/checker infrastructure.
- **Uncertain and sequential decisions**
  - Forecast input distributions, not just a single expected value.
  - Stochastic programming → scenario generation → recourse → non-anticipativity.
  - Robust optimization → explicit uncertainty sets → conservatism/feasibility tradeoff.
  - Rolling-horizon control → reveal information at its real arrival time → freeze committed work → replan safely.
  - Simulation → calibrated dynamics → repeated stochastic trials → policy comparisons → external validation.
- **ML and agents inside the workflow**
  - Predict demand/duration/travel time → ordinary downstream optimizer.
  - Decision-focused learning → train against decision regret, not solely predictive loss.
  - Learn branching, warm starts, neighborhoods or dispatch priorities → retain a feasibility checker.
  - LLM model assembly/what-if explanation → semantic tests and restricted execution → solver → independent decision validation.
  - Algorithm discovery → candidate generation → trusted evaluator → held-out distributions → complete search-cost accounting.
- **Production decision systems**
  - ERP/WMS/TMS/calendar ingestion → unit/schema/time reconciliation → reproducible snapshot.
  - Model/solver service → time/memory budgets → feasible fallback → human change/override.
  - Plan comparison/explanation → change stability → approval/export → outcome feedback.
  - Monitoring → infeasibility/data drift → re-optimization trigger → rollback/audit history.

Google's official job-shop example covers ordered operations and machine exclusivity; those are a starting specification, not all factory requirements. CP-SAT is itself a hybrid: integral constraint programming and SAT with linear relaxations and diverse search workers, so “classical solver versus AI” is often a poor binary. [Job-shop specification](https://developers.google.com/optimization/scheduling/job_shop), [Perron, Didier and Gay, CP 2023](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.CP.2023.3).

## Prediction, optimization, simulation and causality answer different questions

**Prediction:** “How long will this job take?” **Optimization:** “Which machine should do it, and when, given capacity and deadlines?” **Simulation:** “What happens to a chosen policy under a specified model of breakdowns and arrivals?” **Causal evaluation:** “What did adopting this policy actually change?” An agent can coordinate these components; fluent language and successful execution do not establish any of the four answers.

Elmachtoub and Grigas's *Smart Predict, then Optimize*, v5 (2020), formalizes prediction-induced decision loss and a tractable surrogate. Its base setup has a known, fixed feasible region and uncertain linear costs. It supports learning for downstream decisions; it does not prove that hidden constraints, uncertain feasibility or endogenous demand disappear. Its numerical examples are shortest-path and portfolio tasks, not an unrestricted real-world deployment result. [Full primary paper, §§2–4 and experiments](https://arxiv.org/html/1710.08005v5).

Bertsimas and Sim's *The Price of Robustness* (2004), printed pp.35–38, shows how to trade nominal performance for protection against bounded parameter uncertainty while retaining tractable linear/discrete formulations. The stated uncertainty model and assumptions behind probability bounds matter. An arbitrary “robust” buffer is not a universal service guarantee, and an uncertainty set missing a regime change offers no protection from that missing regime. [Primary paper](https://www.mit.edu/~dbertsim/papers/melvyn/The-Price-Of-Robustness-OR52.pdf).

**Proposed evaluation discipline:** use common random seeds/exogenous event streams when comparing policies in a simulator; keep evaluation seeds out of model selection; report both average and tail outcomes, with simulation uncertainty. Validate dynamics against independently observed events before interpreting operational value. Simulation can expose a policy's failure under its assumptions; it cannot establish the assumptions or identify an actual causal saving by itself. A historical replay that allows a new plan but holds all affected downstream behavior fixed can be misleading.

An industry-authored Eastman Chemical case describes feeding optimization outputs into a separate simulation, checking practical risks/rules, then iterating with users before implementation. This is evidence that implementation and model interpretation are longstanding engineering problems, not a new market discovered by agent startups. It is a case report, not a controlled estimate of general ROI. [Cope and Lakshmanan, 2012](https://pubsonline.informs.org/do/10.1287/orms.2012.05.10/full/).

For actual value, a future authorized pilot would need the current process and all integration/review costs as its comparator. Before/after savings can reflect demand, staffing or seasonality. A controlled rollout or another defensible identification design may be needed; this research has no operator, participant access or live trial authorization.

## What automation evidence actually supports

**FunSearch (Nature, 2023/2024)** couples LLM program proposals to an evaluator. Its online-bin-packing experiment improves on first-fit/best-fit baselines using specified generated/OR-Library distributions; its offline lower bound is a reference, not necessarily achievable by an online policy. The separate cap-set discoveries are real mathematical contributions, not evidence of a general logistics product. The transferable lesson is that executable evaluation and a useful search scaffold can turn generation into improvements. Extrapolation requires new constraints, distributions, and full search-cost amortization. [Primary paper, online bin packing and supplement](https://www.nature.com/articles/s41586-023-06924-6).

**PyVRP+ (AAMAS 2026; arXiv v1, 9 April)** evolves HGS components with GPT-4.1. Table 2 reports up to 2.70% objective improvement, but GVRP runtime rises 0.87→1.89 seconds. The paper reports approximately 3–4 H100 hours and $15–20 API design cost per component, separate from execution. Five search runs select the best heuristic; distributions, exact baseline revision and held-out selection need reproduction. Its “Reactive Evolution” is a proxy, not a full implementation-level replication of every named competitor. This supports a targeted experiment, not general human replacement. [Primary methods, §§5–6 and Appendix D](https://arxiv.org/html/2604.07872v1).

**A current-baseline trap:** PyVRP's official 0.13 release on 15 January 2026 replaced HGS with iterated local search, reporting improved limited-runtime/large-instance behavior. Therefore the April paper's HGS comparison does not establish superiority over the current algorithm. This does not invalidate a component-level result on HGS; it changes what one can claim about today's best practical alternative. Pin both code revisions and rerun the current baseline. [Official release history](https://github.com/PyVRP/PyVRP/releases), [PyVRP's original solver paper](https://arxiv.org/abs/2403.13795).

**OSCAR (preprint, 1 October 2026)** is unusually relevant to the oracle problem: it certifies an independently evaluated simulator on labeled plans before iterative model generation. It studies five target instances and solution correctness; general formulation correctness is future work. Its cost comparisons charge model calls, and repeated runs condition on one constructed simulator per problem; frontier agents do not receive the simulator/feedback. Thus 95–100% reported accuracy and 3.1/5.8× token-cost ratios do not show general industrial reliability or equivalent-information superiority. Certification means passing construction checks, not formal proof. [Primary paper, §§2,5 and Appendix 10](https://arxiv.org/html/2610.00912v1).

Microsoft says OptiGuide has been used in production for cloud planners' what-if questions. That is a company-reported deployment, with no independent outcome estimate here. It supports integration of language with existing optimization, not abandoning solvers. [Research project](https://www.microsoft.com/en-us/research/project/optiguide-genai-for-supply-chain-optimization/).

**Matched comparison required:** same feasible region/objective, data available at decision time, hardware/core-seconds/memory, timeout and warm starts. Check every returned plan independently. Report time to first feasible plan, quality-versus-time, failures and lower bounds, not just one average. Include training, candidate search, API spend, repair and human interpretation; show the volume at which an upfront search pays back. Large sample count is not free computation. A heuristic's feasible output is not a proof of optimality; an optimizer's optimal output may still optimize the wrong specification.

## A concrete 30/90-day proof: scheduling that survives its own checker

**Proposed project, not executed:** a reproducible job-shop scheduling evaluator and small offline planning service. Start with fixed-machine JSP; alternative machines, setup times and dynamic arrivals are later extensions, not all first-month requirements. The first month tests engineering/modeling fit before committing to a research degree or company pivot.

**Tools and rights:** proposed solver pin `ortools==9.15.6755` (Apache 2.0), ordinary Python standard-library checker/CSV/JSON tooling; use an already installed compatible Python where possible, and require approval for any needed installation. Use original seeded synthetic instances and hand-authored cases, with authorship/license declared. The TU/e MIT benchmark's generator and Google examples can supply a reproducible public comparison. Preserve notices and original instance citations; don't wholesale relicense third-party historical datasets from a top-level repository label. Freeze the generator, input hashes, original unit/index conventions, solver version/options and hardware in a manifest. No commit hash or runtime result has been frozen yet.

**30 days, planning allowance 35–55 hours:**

1. Write a one-page mathematical/specification contract: integer duration units, every operation exactly once on its assigned machine, job-order precedence, nonpreemption, no machine overlap; minimize makespan. Record deliberately excluded constraints. Create two tiny examples with manually or exhaustively established optimum and intentionally invalid schedules.
2. Write a solver-independent checker which reads only the input and exported schedule, not solver variables or status. It recomputes durations, operation counts, capacity conflicts, precedence, and objective. Mutation tests must reject deleted/duplicated tasks, overlaps, reversed precedence, wrong machines, negative times and false objective values. Separate parsing tests prevent a shared off-by-one indexing bug.
3. Compare FIFO and shortest-processing-time/most-work-remaining dispatch rules against CP-SAT under fixed budgets. Greedy-only comparisons are insufficient: the solver is the serious baseline for any later learned method. Report `OPTIMAL`, `FEASIBLE`, `INFEASIBLE`, `UNKNOWN` and actual bounds separately. Prove toy optimum independently; for larger cases use the valid bound/gap, not a guessed optimum.
4. Produce a results table, raw checked schedules, anytime-quality plot and three explained failure cases. Expose one local import/solve/compare/export path only after the evaluator works. A flashy dashboard adds little without the evidence bundle.

**Workload budget:** proposed initial 24 public/generated cases stratified by size and bottleneck, four methods, three seeds where applicable, ≤60 seconds each; at most 4.8 CPU-hours for that grid if each run consumes one core. Cap total first-month solving at eight core-hours, RAM at 8 GB and logs at a declared limit. Record actual core-seconds; a portfolio solver using eight workers is not a one-core 60-second competitor. This is a budgeting proposal, not a measured completion-time guarantee. Increase difficulty only when the initial dataset is trivial or fails to distinguish meaningful behavior.

**Days 31–90, another 60–100 hours if the first month is useful:** choose one extension, preferably rolling arrivals and machine downtime. A synthetic event generator reveals each arrival/breakdown at its event time. Every policy receives the same revealed information and identical event stream; a perfect-future offline solution is separately labeled as a bound/reference, not a deployable competitor. Started operations remain fixed; define whether near-term commitments can move and price schedule churn. Keep a held-out event distribution/seed set; separate machine-load shift and duration-error stress tests.

Compare (a) strong dispatch rule, (b) periodic rolling-horizon CP-SAT, (c) one narrowly motivated improvement, such as a warm-start/neighborhood policy. A learned model or LLM heuristic is optional; it earns inclusion only after matching feasibility and accounting for search/training cost. Evaluate makespan/tardiness only where the objective calls for them, plus time-to-feasible, checked failure rate, tail delay, schedule changes and inference/solve resources. Use paired per-instance outcomes and uncertainty; avoid claiming independent observations from many correlated operations in one instance.

**Independent validation boundary:** at 90 days, challenge the checker with hand-derived counterexamples and a second formulation or exhaustive enumerator on small cases. Passing a finite test set does not prove the general model correct. A simulator using the same broken assumptions as the solver is not independent validation. Actual operational performance, operator usability and willingness to pay remain unmeasured until a separate authorized domain pilot.

**Kill or redirect criteria:** stop any “improvement” claim if a hard constraint fails, an objective is miscomputed, future information leaks, or a tuned method only wins its training family. If mature CP-SAT already meets quality/latency needs, concentrate on modeling, data quality, explanations and integration rather than inventing a weaker solver. If the improvement vanishes after matching compute/current versions, report the negative result. If no genuine user decision, credible input data or economically meaningful metric can be identified, keep this as a technical portfolio exercise and do not call it a business opportunity.

## From prototype to deeper expertise

**First practical depth:** linear algebra/probability + LP duality/bounds + one discrete formulation + independent checking. Then learn network flows, MIP/CP tradeoffs, numerical tolerances and experimental design while owning one workflow end to end. Strong software developers can contribute service design, data contracts, reproducibility and diagnostic interfaces, but must learn enough mathematics to notice a valid solution to the wrong problem.

**Next depth:** scenario/robust models, decomposition, simulation validation and domain-specific constraints; reproduce a published method against a serious updated baseline. Demonstrate why an approach fails, not just where it wins. This can prepare an optimization engineer/applied-science route; actual job requirements and the user's current baseline decide whether formal study is worthwhile.

**Research/technical leadership:** novel algorithms, proofs, solver internals or domain-level validated decisions require sustained specialization, often graduate training and long industry collaboration. Leadership means owning the model's limits, deployment economics and decision consequences, plus communicating tradeoffs to operators. A three-month artifact can reveal fit and build evidence; it cannot confer that depth automatically.
