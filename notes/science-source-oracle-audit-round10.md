# Scientific software oracles: source audit at two existing versions

Checked **20 October 2026**. This pass read the existing science metadata repairs, science/physical/energy semantic review, SE-01 independent methods review and actionability R4 before tracing public source. It adds no market or hiring claim. Earlier catalogues, reports and tree remain unchanged.

The source supports the earlier distinction between software consistency and scientific truth, with two useful refinements. **Matbench's paper-referenced version is not a ready-made reproduction of the corrected paper:** there are identifiable snapshot differences and two static consistency defects. **Opentrons already implements meaningful state/volume checks:** a project should reuse them, then test the remaining declaration, composition and external-acknowledgement boundaries. Calling the simulator a complete physical oracle is too strong; calling it merely a command printer is also too weak.

## Matbench: where the scientific contract enters the score

### M1. The corrected population and code defaults must be joined explicitly

The article specifies unrelaxed inputs and relaxed PBE targets, an MP-2022.10.28 training ceiling and a 215,488-member unique-prototype population with 32,942 positive labels. Its corrected model list has 13 entries, including EquiformerV2+DeNS and Orb-MPtrj-only-v2; it identifies MACE's December-2023 medium model. Stability is relative to the fixed MP hull, not a synthesis or dynamical-stability outcome. These are distinct dimensions of the benchmark contract. [Article Methods and Models](https://www.nature.com/articles/s42256-025-01055-1)

At the referenced source pin, [`Model` defaults](https://github.com/janosh/matbench-discovery/blob/38a6e1704f2dac244ccd3ae70670e33b887f6b7e/matbench_discovery/preds.py#L23-L89) contain 15 models, including GNoME, MatterSim and two Orb entries, without EquiformerV2+DeNS. The MACE prediction path points to `2023-12-11-mace-wbm-IS2RE-FIRE.csv.gz`, while the checked run script now selects a `mace_mp_0b` checkpoint and the join script selects July-2024 outputs. Those are observable identity differences, not a numerical finding about which models improve the score. [Run configuration](https://github.com/janosh/matbench-discovery/blob/38a6e1704f2dac244ccd3ae70670e33b887f6b7e/models/mace/test_mace.py#L39-L84), [join input](https://github.com/janosh/matbench-discovery/blob/38a6e1704f2dac244ccd3ae70670e33b887f6b7e/models/mace/join_mace_preds.py#L24-L30)

The earlier warning about exact corrected-artifact alignment is therefore stronger and more actionable: select the corrected table row, model/checkpoint, prediction file, evaluator, population and dependencies as a single manifest. The September correction concerns extra published models; **it should not be confused with the separate MP energy-correction mechanisms below**. This audit neither identifies all numerical effects of the journal correction nor establishes an exact Zenodo-archive-to-Git/file match.

### M2. Reference energies and chemical corrections are real code paths

The inspected path is:

1. Convert total energy and composition to formation energy by subtracting stoichiometric elemental reference energies, then divide by atom count. References are read from a named MP elemental-entry artifact and rounded to four decimals. [energy.py L68–124](https://github.com/janosh/matbench-discovery/blob/38a6e1704f2dac244ccd3ae70670e33b887f6b7e/matbench_discovery/energy.py#L68-L124)
2. Process WBM entries with legacy corrections, then MP2020 corrections using `strict_anions="no_check"`; store per-atom corrections and calculate signed hull distance against a saved MP phase diagram with negative distances allowed. [compile script L517–581](https://github.com/janosh/matbench-discovery/blob/38a6e1704f2dac244ccd3ae70670e33b887f6b7e/data/wbm/compile_wbm_test_set.py#L517-L581)
3. For MACE, copy ML energy **and ML-relaxed structure** into entries before structure-dependent compatibility processing; require all entries to process; then calculate corrected formation energy. This avoids silently applying a correction derived from the DFT-relaxed structure to the ML-relaxed output. [join_mace_preds.py L58–85](https://github.com/janosh/matbench-discovery/blob/38a6e1704f2dac244ccd3ae70670e33b887f6b7e/models/mace/join_mace_preds.py#L58-L85)
4. Convert predicted formation energy to predicted signed hull distance by adding the formation-energy prediction error to the stored true hull distance. The DFT term algebraically supplies the reference-hull baseline; it is not evidence that the model received the DFT-relaxed structure. [preds.py L211–229](https://github.com/janosh/matbench-discovery/blob/38a6e1704f2dac244ccd3ae70670e33b887f6b7e/matbench_discovery/preds.py#L211-L229)

Thus the independent reference is more than a CSV column name. It includes the energy convention, chemical correction, elemental phases, fixed competing-phase set and dependency behaviour. The compile script itself comments on changed correction counts after a pymatgen change; the phase-diagram script documents a rebuilt pickle following algorithm/object changes. Root package requirements are lower bounds, while the MACE metadata contains older package versions; the Git pin alone is not an environment lock. [Compatibility-change comment](https://github.com/janosh/matbench-discovery/blob/38a6e1704f2dac244ccd3ae70670e33b887f6b7e/data/wbm/compile_wbm_test_set.py#L541-L560), [phase-diagram reconstruction](https://github.com/janosh/matbench-discovery/blob/38a6e1704f2dac244ccd3ae70670e33b887f6b7e/data/mp/build_phase_diagram.py#L43-L73), [package requirements](https://github.com/janosh/matbench-discovery/blob/38a6e1704f2dac244ccd3ae70670e33b887f6b7e/pyproject.toml#L26-L46), [model requirements](https://github.com/janosh/matbench-discovery/blob/38a6e1704f2dac244ccd3ae70670e33b887f6b7e/models/mace/mace.yml#L37-L42)

A self-authored AB2 example checks units: total energy −10 eV, elemental total −8 eV gives −2/3 eV/atom; adding a +0.3 eV total correction shifts formation energy by +0.1 eV/atom. This is arithmetic, not a real material, a DFT validation or a measured chemical effect. A mismatch of correction or per-atom/total conventions can change a threshold label even when an adapter executes correctly.

**Static rebuild defect, narrowly stated:** immediately after asserting that the legacy-processed list has 76,390 entries, the script sums one Boolean per entry and asserts that the sum is 99,000. Both assertions cannot hold in that sequential path. [L528–534](https://github.com/janosh/matbench-discovery/blob/38a6e1704f2dac244ccd3ae70670e33b887f6b7e/data/wbm/compile_wbm_test_set.py#L528-L534) This establishes a source inconsistency at this pin, not that released labels or the paper's ranking are false. It makes an unmodified raw-data rebuild an unresolved gate; editing away assertions without an authoritative count would not resolve it.

### M3. Population filters, prediction filters and missingness are different operations

The population construction removes outliers from the original WBM uncorrected formation-energy column using a strict open interval −5 to +5 eV/atom: 257,487 becomes 256,963. It then marks matches against MP prototypes and duplicate WBM prototypes, sorting on the original WBM hull-distance column (`each_wbm`) to retain a member; the asserted unique subset is 215,488. This is not a new sort on the subsequently derived `each_true` column. Prototype labels are computed from relaxed structures. This defines a retrospective benchmark population; it is not a prospective rule that can identify every future duplicate without the relevant outcome information. [Population filter](https://github.com/janosh/matbench-discovery/blob/38a6e1704f2dac244ccd3ae70670e33b887f6b7e/data/wbm/compile_wbm_test_set.py#L447-L507), [prototype selection](https://github.com/janosh/matbench-discovery/blob/38a6e1704f2dac244ccd3ae70670e33b887f6b7e/data/wbm/compile_wbm_test_set.py#L626-L678)

A **separate prediction cleaner** defaults to flagging absolute predicted-minus-DFT formation-energy errors above 5 eV/atom as missing. It therefore reads the reference label, regardless of the docstring's prospective rationale. It does not remove the material row. Whether this changes any corrected-paper result cannot be inferred without the exact predictions. [Loader signature/documentation and cleaner](https://github.com/janosh/matbench-discovery/blob/38a6e1704f2dac244ccd3ae70670e33b887f6b7e/matbench_discovery/preds.py#L96-L184)

With `fillna=True`, missing predictions become **unstable** for classification: a missing true-positive material becomes a false negative, while a missing true-negative material becomes a true negative. Regression calculations drop missing pairs. Precision, recall, F1, DAF and MAE therefore do not share a simple common coverage denominator. The loader rounds the joined dataframe to three decimals before scoring; equality with the zero threshold counts as stable. These behaviours must be reproduced or deliberately changed and relabelled. [Classification](https://github.com/janosh/matbench-discovery/blob/38a6e1704f2dac244ccd3ae70670e33b887f6b7e/matbench_discovery/metrics.py#L17-L65), [regression/drop logic](https://github.com/janosh/matbench-discovery/blob/38a6e1704f2dac244ccd3ae70670e33b887f6b7e/matbench_discovery/metrics.py#L98-L139), [rounding](https://github.com/janosh/matbench-discovery/blob/38a6e1704f2dac244ccd3ae70670e33b887f6b7e/matbench_discovery/preds.py#L188-L189)

**Static Accuracy defect:** after calculating full-population classification counts, `stable_metrics` drops missing pairs and uses the reduced length for `Accuracy`. In the exposed four-row arithmetic fixture, true values are `[−0.1,+0.1,+0.1,−0.1]` and predictions `[−0.1,+0.1,missing,missing]`. Counts are TP=1, FN=1, FP=0, TN=2. Intended full-population accuracy is 3/4; the inspected expression yields 3/2. Precision=1, recall=1/2 and F1=2/3 remain separately defined. No package code was run. Existing tests compare Accuracy against sklearn on complete random data; their missing-data case checks other metrics without this Accuracy invariant. [Affected expression](https://github.com/janosh/matbench-discovery/blob/38a6e1704f2dac244ccd3ae70670e33b887f6b7e/matbench_discovery/metrics.py#L125-L139), [test coverage](https://github.com/janosh/matbench-discovery/blob/38a6e1704f2dac244ccd3ae70670e33b887f6b7e/tests/test_metrics.py#L54-L85)

The top-10,000 code selects the smallest predicted distances **within the unique-prototype subset**, then divides precision by the prevalence of that entire subset when calculating DAF. A second implementation that instead uses prevalence among the selected candidates answers a different question. Top-k exclusions/coverage, tie handling and the eligible population need explicit recording. [preds.py L207–244](https://github.com/janosh/matbench-discovery/blob/38a6e1704f2dac244ccd3ae70670e33b887f6b7e/matbench_discovery/preds.py#L207-L244)

### M4. A finite relaxed energy does not establish convergence or physical stability

The inspected MACE example uses initial atoms, FIRE, a Frechet cell filter, `fmax=0.05 eV/Å`, a 500-step cap and float64. It records the final energy after `optimizer.run`; this path does not persist/check a convergence result or final-force acceptance before storing that energy. Exceptions omit the material. Default debug mode processes only 128 structures; this is explicitly a smoke test, not a full benchmark run. [Configuration and sample limit](https://github.com/janosh/matbench-discovery/blob/38a6e1704f2dac244ccd3ae70670e33b887f6b7e/models/mace/test_mace.py#L39-L116), [loop](https://github.com/janosh/matbench-discovery/blob/38a6e1704f2dac244ccd3ae70670e33b887f6b7e/models/mace/test_mace.py#L132-L169)

This does not prove the published predictions failed to converge; their provenance is not yet matched to this script. It does require separating converged, step-limited, exception/missing and chemically invalid outputs in a fresh evaluation. A potential can be numerically self-consistent yet agree poorly with an independent DFT reference, and an energy-screening success need not have stable phonons, a synthesis pathway or useful device performance. The benchmark remains useful for its stated screening task.

## Opentrons: what the simulator already checks, and what it cannot observe

### L1. Choose the implementation and do not rebuild existing validation

At this snapshot, API levels below 2.14 follow the legacy context; newer levels use Protocol Engine. The proposed 2.27 trace uses the latter. Simulation config enables virtual pipettes/modules/gripper, simulated deck configuration and ignored pauses; virtual aspirate/dispense are explicitly no-op hardware operations. [Context selection](https://github.com/Opentrons/opentrons/blob/62b223719f61c779adbbf43d21580c3e3de0a0d2/api/src/opentrons/simulate.py#L311-L338), [config](https://github.com/Opentrons/opentrons/blob/62b223719f61c779adbbf43d21580c3e3de0a0d2/api/src/opentrons/simulate.py#L1039-L1051), [virtual implementation](https://github.com/Opentrons/opentrons/blob/62b223719f61c779adbbf43d21580c3e3de0a0d2/api/src/opentrons/protocol_engine/execution/pipetting.py#L395-L434)

This still performs useful checks. The pipetting layer requires a tip, limits aspirate to remaining working volume and rejects excessive dispense relative to tracked aspirated volume. Tiny excesses within a 1e−9 µL rounding tolerance can be clamped; that tolerance is numerical, not an accuracy specification for a robot. [Volume checks](https://github.com/Opentrons/opentrons/blob/62b223719f61c779adbbf43d21580c3e3de0a0d2/api/src/opentrons/protocol_engine/execution/pipetting.py#L521-L598), [constant](https://github.com/Opentrons/opentrons/blob/62b223719f61c779adbbf43d21580c3e3de0a0d2/shared-data/python/opentrons_shared_data/pipette/constants.py#L17-L29)

The independent project baseline should therefore compare its invariant checks with the SDK's real checks, distinguish requested from adjusted volume and retain warnings. Merely writing another tip-capacity test suite would not demonstrate a new framework limitation.

### L2. Loading declared liquid is neither dispensing liquid nor a capacity proof

The modern `Labware.load_liquid` method checks well membership and numeric type, then forwards metadata. The core constructs `LoadLiquidParams`. The command validates the liquid ID, well existence and allowed labware role; `EMPTY` must be zero. The inspected path does not compare a positive declared volume with the well's capacity. [Public API](https://github.com/Opentrons/opentrons/blob/62b223719f61c779adbbf43d21580c3e3de0a0d2/api/src/opentrons/protocol_api/labware.py#L1434-L1484), [core](https://github.com/Opentrons/opentrons/blob/62b223719f61c779adbbf43d21580c3e3de0a0d2/api/src/opentrons/protocol_api/core/engine/labware.py#L251-L258), [command](https://github.com/Opentrons/opentrons/blob/62b223719f61c779adbbf43d21580c3e3de0a0d2/api/src/opentrons/protocol_engine/commands/load_liquid.py#L23-L78), [role/well validation](https://github.com/Opentrons/opentrons/blob/62b223719f61c779adbbf43d21580c3e3de0a0d2/api/src/opentrons/protocol_engine/state/labware.py#L836-L855)

For the selected definition, H1's nominal `totalLiquidVolume` is 360 µL. A declaration of 400 µL is thus an exact candidate counterexample for an independent capacity check. **This audit statically traces its missing bound check; it does not report simulator acceptance as observed.** A future authorised runtime test must establish the exact full path and retained state before changing that label. [Definition H1](https://github.com/Opentrons/opentrons/blob/62b223719f61c779adbbf43d21580c3e3de0a0d2/shared-data/labware/definitions/2/corning_96_wellplate_360ul_flat/2.json#L71-L81)

The well store assigns/replaces the loaded volume and resets the operation counter. It also updates tracked volumes after operations. Hence the earlier description “labeling” must not be shortened to “the engine has no liquid tracking.” Equally, a custom ledger must not treat two metadata declarations as two physical additions: declaring 100 µL and then 80 µL produces a replacement tracked declaration of 80 µL in this store, not proof that 180 µL was physically mixed. An assay-level component/concentration ledger needs an independently specified physical-event contract. [Loaded and operated state](https://github.com/Opentrons/opentrons/blob/62b223719f61c779adbbf43d21580c3e3de0a0d2/api/src/opentrons/protocol_engine/state/wells.py#L63-L123)

The public API documents that uninitialised wells are untracked, while geometry raises an unknown-height error when a relevant tracked volume is unavailable. Height calculation can adjust out-of-bounds volumes for geometry; it is not a general mass-balance assertion. The pipette validator above checks pipette availability, not measured reagent in a source well. No claim is made here that every source-depletion scenario will pass the complete SDK path. [Tracking contract](https://github.com/Opentrons/opentrons/blob/62b223719f61c779adbbf43d21580c3e3de0a0d2/api/src/opentrons/protocol_api/labware.py#L1439-L1449), [unknown volume](https://github.com/Opentrons/opentrons/blob/62b223719f61c779adbbf43d21580c3e3de0a0d2/api/src/opentrons/protocol_engine/state/geometry.py#L2055-L2086), [height adjustment](https://github.com/Opentrons/opentrons/blob/62b223719f61c779adbbf43d21580c3e3de0a0d2/api/src/opentrons/protocol_engine/state/geometry.py#L2203-L2245)

### L3. Preserve existing uncertainty, then identify the external boundary

On a defined aspirate error, the command clears affected well-volume knowledge; on success, it adjusts the volume using returned operation volume and nozzle coverage. The store deletes cleared knowledge instead of silently retaining a known amount. This is useful existing recovery semantics to reuse. [Aspirate state update](https://github.com/Opentrons/opentrons/blob/62b223719f61c779adbbf43d21580c3e3de0a0d2/api/src/opentrons/protocol_engine/commands/aspirate.py#L188-L221), [CLEAR handling](https://github.com/Opentrons/opentrons/blob/62b223719f61c779adbbf43d21580c3e3de0a0d2/api/src/opentrons/protocol_engine/state/wells.py#L109-L155)

That does not settle an external orchestrator's lost acknowledgement after a potentially completed physical action. Its requested, accepted, executing, result-received and unknown states need authoritative command identity and reconciliation evidence. A fake backend can test that the controller never silently promotes unknown to success or blindly repeats a transfer; it cannot show that a real pump completed, transferred the correct amount, avoided contamination or preserved assay validity. Those stronger outcomes need authorised physical measurements, calibration and domain review. No such trial occurred here.

## Narrowed project acceptance gates

For `science-enrichment-round5.project.materials`:

1. **Identity gate:** freeze the corrected comparison's exact model/prediction/summary/phase-diagram IDs, checksums, dependencies, correction settings and test population. The named Git version alone fails this gate. A reduced source/metric audit is a valid fallback, labelled as such.
2. **Independent metric gate:** predeclare paired regression coverage and full classification population; implement a second metric path with no missingness, mixed missingness, threshold equality, ties and degenerate classes. Require bounded Accuracy, count conservation, explicit undefined results and correct top-k/DAF baseline. Record historical formula reproduction separately from a corrected metric; do not silently change one and claim paper replication.
3. **Information gate:** keep unrelaxed inputs separate from reference-relaxed labels. Report raw and label-cleaned predictions with excluded counts/reasons, or explicitly limit to the historical cleaner. Do not market a reference-error filter as an outcome-blind prospective filter.
4. **Relaxation gate:** retain checkpoint/optimizer/filter/dtype, final force/step/convergence status, failures and original IDs. Do not call a finite final energy a converged relaxation. A new clean split does not erase unknown pretraining exposure.
5. **Truth gate:** consistency tests and a matched published DFT evaluation support numerical/evaluator engineering. Physical generalisation needs an independent reference/property task; synthesis and device claims remain out of scope. No 1e−4 reproduction tolerance is justified until snapshot/rounding alignment is complete.

For `science-enrichment-round5.project.labrunner`:

1. **Runtime gate:** before an authorised implementation, choose a supported release/API, robot type, labware URI/version and simulation mode; reproduce one vendor reference path. The inspected development pin is evidence, not an install recommendation.
2. **Oracle gate:** specify units, initial snapshots/relabels, physical transfers, capacities, source availability, tip contents and unknown state independently. Reuse engine checks. Test the 400-in-360 declaration as a future runtime counterexample; until then call it statically inferred.
3. **Control gate:** use actual adjusted operation results/warnings, multi-nozzle volume semantics and existing CLEAR behaviour. Do not equate command request, metadata assignment and measured physical transfer.
4. **Failure gate:** preserve action IDs and a separately specified authoritative outcome observer. Test failure before execution, during execution, after completion before acknowledgement, duplicate response and reconciliation. Hand-authored seeded runs establish only those scenarios, not a population failure rate.
5. **Scientific gate:** an accurate software ledger still needs measured transfer/calibration, composition/assay validation and appropriate domain authorisation for any physical claim. Keep a useful CPU-only software project without implying wet-lab proof.

These gates strengthen the accessible engineering project while narrowing its claims. The most valuable first contribution might be a version-specific reproduction note or regression test for an existing framework rather than a new model or lab orchestrator. That is a conditional contribution hypothesis, not evidence of employer demand or original-research acceptance.

## What would change these findings

An exact corrected prediction/environment archive could resolve M1. A runtime test at this pin could confirm or disprove the source-path counterexamples and establish their operational reach; data analysis would still be needed to measure impact on a reported table. An authoritative count/environment history could repair the rebuild inconsistency without implying the released labels were invalid. A capacity validator in an untraced layer or a different selected release could narrow L2; it would not convert virtual no-op success into a physical observation. A real authoritative reconciliation interface could make the controller's external-acknowledgement model simpler.

This was selected source inspection, not a formal verification of either repository or a check of the latest branch. Public-source retrieval had one transport failure and several initially incorrect paths; successful directory/file reads supplied the cited paths. No failed retrieval is treated as a scientific finding. The correction's direct page remains inaccessible, and exact corrected data/archive correspondence remains unresolved. The report exposes these gaps rather than declaring final project acceptance.
