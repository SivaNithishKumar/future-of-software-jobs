# Accessibility workflow option: keyboard, focus, errors and recoverable task state

Prepared 20 October 2026; main evidence cutoff 19 October 2026. Existing `interfaces-accessibility-round6.md`, creative and security coverage were read first. This option deepens the conventional web/application branch; it does not repeat voice/BCI/XR studies or replace their human-evaluation gaps. Proposed attachment: `darkside2031.interfaces.multimodal.accessibility.design`. Research and contract design only: no UI, browser/AT execution, installation, private screen, user/patient data, accounts, recruitment or outreach.

The useful question is whether a person can reach, understand, complete and recover a task across its actual states. A correctly named button, static scan or attractive screen does not establish that its error, asynchronous update or modal works. Native HTML and mature testing already do much of the work. The candidate expertise is implementing and maintaining the missing transitions with evidence, not selling a generic accessibility score.

## 1. Standards, patterns and native behavior have different authority

The current **WCAG 2.2 Recommendation is dated 12 December 2024**. Its conformance requirements include full pages and complete processes; selected passing components or happy-path screens are insufficient for a whole-process claim. Keyboard operation, focus order/visibility, field errors, programmatic names/states and status messages are relevant requirements for the proposed flow. This is a selected engineering scope, not a complete conformance assessment. [Normative Recommendation](https://www.w3.org/TR/2024/REC-WCAG22-20241212/)

**WCAG 3.0 remains a Working Draft dated 10 September 2026.** Do not turn its evolving model into a current Recommendation or universal legal duty. [Exact draft](https://www.w3.org/TR/2026/WD-wcag-3.0-20260910/)

The **ARIA Authoring Practices Guide (APG)** supplies design/implementation guidance. Giving a `div` the role of button does not supply native button keyboard behavior. [APG principles](https://www.w3.org/WAI/ARIA/apg/practices/read-me-first/) Its modal pattern describes initial focus, contained page tab navigation, Escape and a logical return target, with context-dependent focus choices. Keeping page focus inside a modal while providing an exit is different from an inescapable keyboard trap. [Modal pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) The example explicitly warns that it is illustrative, not production-ready, and needs testing with relevant browser/AT combinations. [Example limits](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/examples/dialog/)

Use semantic HTML controls first: labels, native buttons/selects/checkboxes, required constraints, sensible document order and a native modal only where the task needs it. The HTML Living Standard already defines modal dialog focusing, document blocking and return-focus behavior. Custom ARIA/focus code must justify its extra behavior against that baseline. The standard is living; its current text is not proof of identical behavior in every installed browser. [Native dialog contract](https://html.spec.whatwg.org/multipage/interactive-elements.html#the-dialog-element)

Rights: APG repository documents use the **W3C Software and Document License**; Recommendation/draft document-use rules apply separately. No example was copied or executed here. [APG rights](https://raw.githubusercontent.com/w3c/aria-practices/main/LICENSE.md) This future fixture can be authored from scratch, without inheriting an assumption that every web example or asset has identical terms.

## 2. Mature automation is both baseline and limit

The inspected catalogs expose **axe-core 4.14.0**, commit `e797173`, and **Playwright 1.64.1**, commit `cfe490d`. Release pages show 5 October and 14 October timestamps respectively; the extracted header timestamps omit their year. Record exact package/browser/runtime versions before a later run, rather than infer compatibility from a website. [axe catalog](https://github.com/dequelabs/axe-core/releases), [Playwright catalog](https://github.com/microsoft/playwright/releases)

axe 4.14 adds or changes rules and fixes false positives, so issue totals can change after an upgrade without the application changing. Its preceding 4.13 release adds ElementInternals support, demonstrating that automated coverage expands. These are maintainer-reported changes, not our reproduced performance results. Native tools therefore oppose the assumption that every currently manual check is permanently human work. axe also records **incomplete** outcomes when a determination needs review; these are not passes. [Tagged README](https://raw.githubusercontent.com/dequelabs/axe-core/v4.14.0/README.md)

Playwright's accessibility guide integrates axe and warns that automated scans cannot detect every WCAG violation. Its sample tag set is not a universal claim to all WCAG 2.2 coverage, and exclusions remove coverage from entire selected subtrees. Scans should run after the relevant form, error or dialog state is reached. [Testing guide](https://playwright.dev/docs/accessibility-testing)

Its aria snapshots constrain roles, names, attributes and structure; a template need not serialize a complete accessibility tree. They are useful state assertions but do not establish that a user reached that state by keyboard, heard an announcement or understood the task. [Snapshot contract](https://playwright.dev/docs/aria-snapshots) A test that clicks a role locator can bypass the very keyboard path being evaluated. That is a test-design distinction, not a claim that role locators are defective.

AI automation is already a native alternative: Playwright documents planner, generator and healer test agents that explore applications, produce plans/tests and repair failing tests. [Agent tooling](https://playwright.dev/docs/test-agents) No agent was run here, and no causal time saving or accessibility accuracy follows from that feature list. The project must keep its expected state/focus oracle outside automatically generated or healed test code; updating an expected snapshot is not evidence that a regression was fixed.

## 3. Subbranches that need actual depth

| Branch | Concrete implementation/evaluation question | Independent evidence |
|---|---|---|
| Keyboard task path | Can the task start, edit, submit, correct, cancel and retry using expected keys, without pointer assistance? | Predeclared action sequence and completed data state; event delivery to an element is not the same as keyboard reachability. |
| Focus lifecycle | Does a dialog receive appropriate focus and return logically? What if its invoker disappears? Does an asynchronous result steal focus? | Expected target or small allowed set for each transition, captured invoker/context and observed focus sequence. Browser chrome is distinct from outside-page controls. |
| Error recovery | Are invalid fields identified, errors associated, corrections retained and retry reachable? | Exact invalid field/error relationship and task values; visible red text alone cannot supply the relationship. |
| Semantics and state | Are names, labels, selected/expanded/invalid state and conditional controls truthful? | Role/name/state assertions alongside actual input/activation behavior; adding ARIA is not an action implementation. |
| Updates and reading | Is an important status exposed without forcing focus? Does document order remain meaningful under reflow or inserted content? | Semantic intent plus later browser/AT observations; DOM presence alone does not certify an announcement was heard. |
| Evaluation coverage | Which states, browsers, OS/AT combinations, exclusions, versions and user goals were checked? | Full attempted-case/status matrix, not a single count or a generated all-green screenshot. |

This selected keyboard/error branch still excludes many needs: contrast, captions, language, cognitive load, authentication, motion, touch and document accessibility require their own evaluation. Automated tree checks, author keyboard tests, specialist AT tests and disabled-user task outcomes are different evidence layers. None can be silently substituted for another.

## 4. One no-new-hardware synthetic flow and test contract

**Flow: edit a local synthetic project task.** Fields are required task title, native priority select, native “Blocked” checkbox and a conditional reason field. Submission creates only a fake local save. An injected failure supports retry; cancelling dirty edits opens a native discard-confirmation dialog with “Keep editing” and “Discard.” No real booking, address, account, network save, message or personal record.

Use **eight states**: clean, dirty, invalid, saving, failed, saved, discard prompt and discarded, with conditional-field variants. The companion `accessibility-workflow-option-round15-contract.json` specifies 20 transitions, focus/semantic/data oracles, negative controls and not-run boundaries. This is a proposed design, not an authored UI. Its small state graph was checked using owned standard-library arithmetic: all 8 states are reachable, all transition targets resolve and the 24-case category totals agree. That proves internal contract bookkeeping only.

The independent oracle is a separately authored table of expected field values, fake save count, visible controls, role/name/state relationships, keyboard paths and focus destinations. It cannot call the UI implementation's own focus/validation helper. A second person's review is still absent. Freeze **24 development cases**: 4 valid keyboard paths, 4 errors/conditional fields, 4 modal/return-focus cases, 4 asynchronous/retry cases, 4 semantic/read-order cases and 4 coverage/tool negative controls; hold out 8 combinations.

Baseline A uses native controls and browser constraint validation; Baseline B adds only the application semantics needed for asynchronous failure/retry and discard behavior, using native dialog support. If a different error-summary pattern is evaluated, declare its expected focus profile separately before testing: native first-invalid-field focus and a deliberately focused summary are different designs, not automatically a winner and loser. Custom widgets or AI-driven interaction are unnecessary for this question.

Important oracle examples:

- Revealing Blocked reason preserves the current checkbox's focus and exposes a correctly labelled field; it does not move focus merely because DOM changed.
- Invalid submit identifies the invalid field and gives a keyboard-reachable correction path. If a summary is part of that profile, its links and focus are tested too.
- The discard dialog receives appropriate initial focus; background page controls cannot be activated; Escape/Keep editing restores the captured form/context and a logical target. Removed invokers have an explicit fallback.
- Repeated submit while pending cannot create duplicate fake saves. A stale response cannot overwrite newer edits or steal focus. A failure retains input and exposes a reachable retry; status-only success does not force unnecessary focus movement.

**30 days, 25–40 focused hours, drawn from the existing interface-project allocation:** spend 5–8h on the independent contract, fixture rights and exact version/config manifest; 10–15h on a later authorized minimal native implementation; 5–8h on keyboard/semantic/axe comparisons at each state; 5–9h on all cases, negative controls and repair time. This task authorizes research/design only: implementation, browser execution and any missing runtime/AT installation remain later gates. No final research UI is being authored now.

Predeclare acceptance relative to this fixture: exact fake task values/save counts; all declared valid keyboard paths complete; focus/return/error invariants hold; no silent unknown or excluded state is counted as pass. Print case counts and failures, not a WCAG compliance percentage. Fixed intentionally chosen cases are not random samples and cannot estimate population usability or rare failure rates.

**Days 31–90, an additional 50–80h only if the first window is useful:** add the 8 withheld combinations, changed viewport/reflow and reduced-motion/forced-colour variants where relevant, a removed dialog invoker, delayed failure and changed labels/localization. Record an actual browser/OS/AT version matrix when approved existing software and skills are available. A headless browser is not a screen reader, and a desktop result does not establish mobile/switch-control behavior.

Later specialist and disabled-user review needs its own authorization, accessible materials, informed participation and appropriate scope. It should measure correct task completion, error discovery/repair, retained context, unnecessary effort and preferences across relevant users. No recruitment, recordings or claims about disabled participants occur here. ARIA-AT offers a public pattern-support/contribution route, but its dynamic reports were not readable in this pass; no support score was reconstructed. [Project repository](https://github.com/w3c-cg/aria-at), [report surface](https://aria-at.w3.org/reports)

Metrics: state/transition coverage; exact completed task state; keyboard dead ends and wrong activations; focus target violations; lost inputs/duplicate effects; unassociated errors; automation findings versus incomplete/not-run cases; false positives/negatives relative to the declared oracle; and active/total authoring, diagnosis and repair time. Actual announcement quality, cognitive usability and user effort remain unknown until reviewed using the relevant methods.

**Stop criteria:** native controls/components plus mature tests satisfy the task with lower effort; custom focus/ARIA creates more failures; generated/healed tests change the oracle to excuse regressions; a scanner score is the only demonstrated benefit; or no reviewer can interpret the intended interaction correctly. A reduced regression fixture or corrected component documentation is a useful result without claiming a new accessibility product or job category.

## 6. 2031 interpretation and remaining evidence

Inference: this is a transferable product-engineering depth path: stateful frontend correctness, semantic HTML, keyboard/focus diagnosis, automated regression and collaboration with AT/user specialists. Native platforms and AI may reduce implementation and test-authoring effort, and expand coverage. The useful contribution is fewer failed tasks and cheaper sustained remediation at a fixed accepted outcome; this source set establishes no net employment increase, shortage or salary premium.

Leadership evidence can progress from a minimized component regression → an adopted design-system/test contract → a measured release process across teams → coordination with disabled users and specialists. An original contribution must survive native-tool comparison and relevant human review. Scanner issue counts, certification badges and a locally passing task are not that broader authority.

Open gaps: actual UI/browser/axe execution; immutable wrapper/browser/runtime pins; independent contract review; AT-specific announcements and mobile/touch support; disabled-user task outcomes; current candidate eligibility; and an authorized buyer/deployment with all-in cost/acceptance evidence. No scan, UI test or human study was run, and no WCAG conformance, legal compliance, universal usability, production readiness or new job creation was established.
