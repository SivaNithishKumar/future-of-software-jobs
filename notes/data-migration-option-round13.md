# Data migration option: snapshot-to-stream and target-state correctness

Prepared 20 October 2026; main evidence cutoff 19 October 2026. Read the relevant database/state sections of `software.md` and `systems-round2.md`, and the source-evaluation audit notes before this pass. Earlier work covers generic recovery, queries and retry labs; this option narrows to copy/log handoff, cross-table state, schema/type/delete meaning and recovery acceptance. Proposed attachment: `darkside2031.software.data`. No private work repositories or production systems were inspected.

The attainable specialty is owning a verifiable migration contract: what target state must match which committed source boundary, which transformations are permitted, and how a failed run can resume without silent loss or duplicate effects. Mature tools already automate capture, initial copying, replay, conversion and some validation. Ordinary integration demand does not demonstrate scarcity, a new product moat or guaranteed income.

## 1. Three mature artifact families and their actual contracts

### PostgreSQL native logical replication: first baseline for compatible PostgreSQL systems

The inspected documentation is explicitly **PostgreSQL 18**; it still lists 19 as development and announces 19 RC1 on 15 October 2026. This pass does not choose an unverified 18.x patch or claim 19 is generally available. Native table synchronization copies existing rows, catches up from a replication slot and hands control back to the main apply worker. That is an existing copy/log coordination protocol, with table-level synchronization and visibility details, rather than an instruction to write a new CDC engine. Initial copying does not honor the publication's DML `publish` filter in the same way as subsequent replication. [Architecture](https://www.postgresql.org/docs/18/logical-replication-architecture.html)

DDL/schema changes and sequence state are not automatically replicated. Additive target schema changes can often precede the source change; incompatible incoming rows cause replication errors until the target is ready. Switchover also needs sequence handling. TRUNCATE has subscription/foreign-key caveats, and large objects are outside this path. [Restrictions](https://www.postgresql.org/docs/18/logical-replication-restrictions.html) A crash-safe logical slot can resend recent changes after restart because its position is persisted at checkpoints. Clients must avoid duplicate-message side effects. The slot does not know the receiver's application state. [Logical decoding concepts](https://www.postgresql.org/docs/18/logicaldecoding-explanation.html)

Rights: the PostgreSQL License permits use/modification/distribution with its notice conditions; it does not promise correctness or support. [Official licence](https://www.postgresql.org/about/licence/) Do not generalize these native guarantees to arbitrary heterogeneous databases, a custom Kafka consumer or application-trigger behavior.

### Debezium: use current native snapshot reconciliation and explicit delivery scope

The release overview identifies **3.7.0.Final, 29 September 2026**, as latest stable. Its tested PostgreSQL list is 14–18, with `pgoutput`/`decoderbufs`; connector Java requirements and Server/Operator requirements differ. Code is Apache-2.0, documentation CC-BY-3.0. Pin connector, database, driver, serializer, runtime and offset storage separately; a documentation-series URL is not a binary checksum. [3.7 release matrix](https://debezium.io/releases/3.7/)

The 3.7 PostgreSQL connector already reconciles incremental snapshot/log collisions: changed keys supersede buffered copied rows. Concurrent schema changes during that snapshot are unsupported. Relevant settings include `provide.transaction.metadata` (default false), `tombstones.on.delete` (true) and `skipped.operations` (default `t`, meaning TRUNCATE is skipped). A delete and a Kafka tombstone have distinct purposes. Keyless TRUNCATE events can be reordered relative to row events across multiple partitions. Temporal conversion modes can lose precision. These are configurations and representational contracts, not evidence that every default matches a new consumer. [Version-specific connector documentation](https://debezium.io/documentation/reference/3.7/connectors/postgresql.html)

Strong opposing evidence to “deduplication must be custom”: Debezium supports participation in Kafka Connect source exactly-once delivery. Its documented requirements include distributed mode, Connect 3.3+, worker `exactly.once.source.support=enabled`, connector `exactly.once.support=required`, and `transaction.boundary=poll`. The page also describes implementation correctness concerns; their presence is not a freshly reproduced bug in the selected version. This source delivery feature does not certify an external target update, its checkpoint or a downstream side effect. [Exactly-once scope and configuration](https://debezium.io/documentation/reference/3.7/configuration/eos.html)

### AWS DMS: managed capture, validation and conversion oppose a generic custom service

The current release document lists **3.6.1, released 15 May 2025**, while still naming **3.5.4 as default** and describing a future default transition. It extends the latter's support into 2027. “Newest listed” and “what a new instance uses” therefore differ; no account/region instance was queried. Data Resync is listed for Oracle/SQL Server sources to PostgreSQL, not universally for every source pair. [Release/support table](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_ReleaseNotes.html)

PostgreSQL-target full load is table-by-table: target tables can temporarily disagree while copying and applying cached changes. [Target behavior](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Target.PostgreSQL.html) Source limitations include primary-key requirements, ignored or unsupported key-definition changes and filter/delete interactions. Do not generalize support across an unlisted source topology. [PostgreSQL source limitations](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Source.PostgreSQL.html) `BatchApplyEnabled` defaults false; switching it changes apply behavior. The tempting `BatchApplyPreserveTransaction` control applies **only to Oracle targets**, so it is not a blanket PostgreSQL-target solution. [Task settings](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Tasks.CustomizingTasks.TaskSettings.TargetMetadata.html)

Native row validation already compares source/target content and reports pending, suspended, failed and validated states, adding source/target/network work. CDC validation retries and delays comparison; reversing source/target in a validation-only task can miss errors because changed-row discovery follows the configured source log. A temporarily matching row is not proof of all future transitions. [Validation contract](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Validating.html) This managed service is not an Apache-licensed self-hosted connector; using it requires an authorized account, connectivity, permissions and a cost boundary. None was used here.

## 2. Meaningful technical subbranches

| Branch | Required invariant and practical test | Why an easy green signal can mislead |
|---|---|---|
| Snapshot → stream | Every copied row is associated with a defined source cut/window; subsequent committed changes replace it without gaps or resurrection. | “Copy finished” says neither what source point it represents nor whether delayed copies overwrote newer values. |
| Transaction and order | State exposed at a declared ready barrier corresponds to an allowed committed prefix; cross-table dependencies are handled. | Per-key/topic order does not automatically publish a multi-table transaction atomically. Eventual targets may legitimately show transient states; specify that contract. |
| Identity and replay | Source instance/epoch, table, key and operation identity are preserved across restart. | A row key is not a unique event. A single source LSN is not a universal deduplication key for every connector/envelope or multi-row transaction. |
| Types and time | Integers, decimals, null/absent/unavailable values, local timestamps, instants and precision survive the declared mapping. | A successful cast can silently change a large integer or timestamp. Equal display strings do not establish equivalent typed values. |
| Deletes and schema | Delete, tombstone, TRUNCATE, primary-key change, rename, default and backfill each have an explicit policy. | Counting rows misses wrong values. Treating missing fields as NULL can erase existing content; adding a target default need not recreate source history. |
| Checkpoint and recovery | Applied data/effect and durable progress have a coordinated commit/replay policy; a missing log range fails closed or invokes declared repair. | Checkpoint-before-effect can lose work; checkpoint-after-effect can replay it. “Resume” is not a proof that a vanished log range was recovered. |
| Cutover and rollback | Readers, writers, permissions, sequences, lag and reconciliation satisfy a stated cutover gate; backup/forward-repair policy is rehearsed. | An application rollback cannot restore information discarded by a data transformation. An unchanged schema version does not prove equivalent data. |

These requirements are proposed specifications, not a claim that all migrations need one global serial order or that every intermediate mismatch is a defect. A cache/search index can accept eventual convergence; a workflow reading a cross-table invariant may need a readiness barrier. Define that distinction before measuring errors.

GitLab's own migration guide is a useful existing application-level baseline: it distinguishes reversible migration definitions from production recovery, describing roll-forward for its production environments and backup restoration for self-managed upgrades. Data-losing transformations can be inherently irreversible. That is an organizational policy/example, not a universal instruction to run rollback against a live database. [Migration guide](https://docs.gitlab.com/development/migration_style_guide/)

A current research extension is **Andreas Andreakis, Generalized DBLog**, arXiv v4 revised **5 October 2026**. Its abstract states assumptions under which copied rows and logged changes reconstruct source state, and reports Isabelle/HOL, Lean4 and bounded TLA+ artifacts. It is a preprint/theory claim, not an audited guarantee for an installed connector or end-to-end application. The paper is CC-BY-4.0; its linked artifact DOI failed to resolve in this reader, so code licence and executable proof were not verified. [Exact paper version](https://arxiv.org/abs/2609.08160v4) No research-lab affiliation or employment route is inferred from its author listing.

## 3. AI and native automation: test the opposing explanation

AWS DMS Schema Conversion already combines rules-based conversion with optional generative AI for unsupported constructs; its setting `EnableGenAiConversion` defaults false. This reduces manual conversion work in supported paths, rather than making schema translation permanently human work. [Settings](https://docs.aws.amazon.com/dms/latest/userguide/schema-conversion-settings.html) The current service page separates **schema conversion from data migration** and lists regional/path limits. It lists London for generative conversion, while Mumbai/Hyderabad offer the migration-project feature without generative conversion; cross-region use has separate implications. [Service and regional matrix](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_SchemaConversion.html) No account entitlement, real conversion rate, all-in time saving or error rate was measured here.

Inference: AI can draft SQL, conversion maps, compatibility checks and recovery explanations; native validation can catch much ordinary mismatch. The career experiment should ask whether a developer improves accepted recovery/repair outcomes beyond those tools. More generated code may increase the value of a well-specified migration test while reducing time spent writing it. That does not establish a fixed amount of irreducible review labor.

## 4. Tiny synthetic project with an independent state oracle

**One project: a two-table copy/log handoff and migration acceptance fixture.** Use owned synthetic `carts` and `cart_items`, four initial rows and six declared committed transactions. Exact amounts use integer minor units; timestamps and large integer IDs are test fields. No real users, transactions, commercial dataset or private schema. The companion arithmetic file is owned illustration data, not a captured Debezium/DMS stream. Future publication requires an explicit author-selected fixture licence; none is assigned on their behalf here.

Freeze **24 development scenarios** in advance: 4 valid handoffs/replays, 4 snapshot/stream overlap faults, 4 transaction/order/progress faults, 4 type/time/NULL faults, 4 delete/key/TRUNCATE faults and 4 schema/recovery-contract faults. Separately hold out 8 changed schedules/schema variants. The event format is an authored abstract model: do not pretend its synthetic event IDs or source-order numbers are universal Debezium identifiers.

The independent oracle is a handwritten table of expected source states at each committed cut, transformation version and permitted target visibility barrier. It must not call the candidate replay/merge function. Invariants include exact key/value/type equality; `cart.total = sum(item.amount)` at declared ready barriers; every live item has a cart; a deleted key is absent; each accepted authored operation has one declared effect; and unknown schema/gap cannot report ready. Hashes/counts can accelerate comparison but the tiny fixture should retain exact differing fields. A second reviewer and real connector translation remain later gaps; an authored oracle is not independently human-validated truth.

**First 30 days, 25–40 focused hours within existing project hours:**

1. Spend 5–8h writing the source-state oracle, visibility/repair contract and version/config/rights manifest before a consumer. Specify allowed loss and rejection behavior. Record whether the end goal is final convergence, transaction-consistent reads or a separate side effect.
2. Spend 10–15h on a small authored simulator/adapter using only an already available runtime. Compare naive arrival-order overwrite with an explicit snapshot cut/window reconciliation and transaction-ready barrier. Replay duplicate deliveries and restart positions; retain the negative baseline failures.
3. Spend 5–8h designing native comparisons: PostgreSQL native logical replication for a compatible peer; Debezium's supported initial/incremental snapshot with default delivery and separately configured Connect exactly-once; DMS native validation for an authorized later service test. Profiles are **not run** until approved runtimes/services exist. Do not reward a custom simulator for outperforming a deliberately broken connector configuration.
4. Spend 5–9h auditing all 24 verdicts and repair effort. Require exact final equality at the declared source cut, zero silent stale-row resurrection, no duplicate declared effect, preservation or explicit rejection of precision/type changes, and correct non-ready status for unknown ranges. Report active/total authoring, diagnosis and repair minutes, unsupported cases and configuration complexity.

**Days 31–90, an additional 50–80h only after the first result:** use the 8 withheld variants and a changed schema/type contract. Change row order, transaction size, source epoch, nullable field, precision and target readiness needs. Native profiles may solve everything; accept that outcome. A later separately approved disposable database/connector environment is required to claim real snapshot overlap, crash-before/after-offset persistence, source restart, retained-WAL exhaustion or schema-lock behavior. A simulated crash flag cannot establish disk durability, WAL retention, Kafka transactions, actual resnapshot correctness or source load.

In that later gate, keep native constraints, durability and error policies explicit; test both data and checkpoint/effect outcomes. Compare cold bootstrap, repair/rebootstrap and ordinary streaming at matched accepted states. Measure recovery duration, unavailable interval, retained log/storage, source load, target lag and operator effort. No throughput/RPO/RTO or cost benchmark can be claimed from this design.

**Stop criteria:** native replication/configured connectors plus ordinary checks satisfy the declared contract with comparable effort; the oracle cannot distinguish permissible transient states from defects; success requires inaccessible production details; or the proposed new layer mostly duplicates native snapshot reconciliation/validation. Keep a minimal regression fixture or migration-contract contribution instead of inventing a platform. A product/customer claim needs an authorized workflow, baseline cost and demonstrated acceptance; no outreach is authorized by this project.

### What was actually run now

Five small Python-standard-library arithmetic illustrations were executed and saved in `data-migration-option-round13-arithmetic.json`: stale snapshot overwrite, stale-row resurrection after delete, a transaction-visible prefix with equal row counts but a broken value invariant, two deliveries yielding one extra naive counter effect, and binary64 loss for integer `9007199254740993`. All five authored assertions passed. File SHA256: `7c2af9fff47c625a640d040c03fee75a53bf7128d04cf006aee63a23fe4ae202`.

These show why the proposed oracle checks matter. They do **not** reproduce a PostgreSQL, Debezium or DMS defect, implement the real native watermark algorithm, validate crash recovery, or establish performance/economics. No upstream code or database ran.

## 6. 2031 implication and remaining gaps

Inference: this is a practical adjacent depth path for a backend/AI engineer because accepted AI-agent outputs, analytical data, search indexes and ordinary product operations all depend on current correct state. The defendable skill is testing and owning the migration outcome across versions and recovery, with mature native tools. AI/native platforms can keep absorbing implementation work; the specialty's opportunity should be reassessed using accepted results and actual roles.

Leadership evidence can progress from a reduced fixture and precise invariant → an adopted migration/recovery test → ownership of cutover criteria and incident repair → cross-team standards and maintainer review. Original contribution requires showing an actual unhandled native-tool case or cheaper accepted workflow, not renaming an existing watermark/validation pattern. Community authority and a public repository are not evidence of paid demand.

Open gaps: immutable runtime/package pins and real approved replay; independently reviewed source-state oracle; actual cost/source load and recovery behavior; behavior for the chosen consumer's schema/transaction visibility; DMS account/region/engine entitlement; formal artifact code/rights inspection; current candidate eligibility; and an authorized customer's accepted outcome/cost baseline. No scarcity, moat, guaranteed salary, production readiness or five-year job-count estimate follows from the evidence.
