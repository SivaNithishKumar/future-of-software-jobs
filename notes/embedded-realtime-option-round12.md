# Embedded firmware and real-time engineering as a distinct option

Checked **20 October 2026**. This extends the existing compute-hardware, telecom-edge, robotics and systems notes after reading their relevant sections and source index. It covers MCU firmware: interrupts, concurrent state, sensor acquisition, resource/deadline contracts and recoverable authenticated updates. It does not repeat ROS policy, EDA or inference benchmarking. The [structured attachment](embedded-realtime-option-round12.json) holds three artifact records, exact source pins, a bounded role/group directory, proposed taxonomy nodes and an unexecuted project.

The accessible first step is **C firmware semantics plus an independent trace/recovery test**, with one mature runtime. A developer can demonstrate useful debugging and integration depth without buying a board. Target interrupt latency, calibration, flash behaviour and root-of-trust claims require additional physical evidence. This distinction preserves a practical entry experiment while avoiding an imagined shortcut to board bring-up or senior embedded employment.

## Three primary artifacts and what they establish

### 1. Zephyr: interrupt context, resource bounds and scheduler semantics

The audit resolves **Zephyr v4.4.0** to commit `684c9e8f32e4373a21098559f748f06915f950c9`. The [release index](https://docs.zephyrproject.org/latest/releases/index.html) lists 4.4.0 as stable and 4.5 as planned; a planned October release is not treated as released. Recheck maintenance/security status before any later implementation. The exact audited code is a reproducibility reference, not an instruction to install an unreviewed package set.

An ISR needs a bounded amount of work and must respect the API's context rules. Zephyr's queue implementation asserts non-waiting use in ISR context; it uses a spinlock and copies queue items. Large copied messages increase the critical section, so “move work to a thread” can still leave a substantial interrupt cost if the queue payload is large. Passing pointers reduces copying but adds ownership/lifetime and DMA/cache-coherency obligations; it does not make the problem disappear. Assertions also depend on build configuration and cannot substitute for satisfying the API contract. [Queue implementation L150–224](https://github.com/zephyrproject-rtos/zephyr/blob/684c9e8f32e4373a21098559f748f06915f950c9/kernel/msg_q.c#L150-L224), [copying/latency guidance L185–195](https://github.com/zephyrproject-rtos/zephyr/blob/684c9e8f32e4373a21098559f748f06915f950c9/doc/kernel/services/data_passing/message_queues.rst#L185-L195)

Two nonobvious constraints matter. Zephyr's **zero-latency IRQ** mechanism has architecture-specific restrictions and generally cannot interact with kernel APIs. Its name is not a whole-application deadline guarantee. Separately, `CONFIG_SCHED_DEADLINE` uses deadlines to order threads with **equal static priority**; enabling it does not turn all threads into one global EDF queue. A proposed scheduling improvement must compare the actual policy configured. [IRQ constraints and deferred work L167–226](https://github.com/zephyrproject-rtos/zephyr/blob/684c9e8f32e4373a21098559f748f06915f950c9/doc/kernel/services/interrupts.rst#L167-L226), [scheduler L40–51](https://github.com/zephyrproject-rtos/zephyr/blob/684c9e8f32e4373a21098559f748f06915f950c9/doc/kernel/services/scheduling/index.rst#L40-L51)

The strong starting baseline is the existing `k_msgq` implementation and `kernel.message_queue` test configuration, not a new queue written for the portfolio. The pinned test config enables ztest and IRQ offload; actual target support and executed/skipped tests still need checking. [Test configuration](https://github.com/zephyrproject-rtos/zephyr/blob/684c9e8f32e4373a21098559f748f06915f950c9/tests/kernel/msgq/msgq_api/testcase.yaml), [project configuration](https://github.com/zephyrproject-rtos/zephyr/blob/684c9e8f32e4373a21098559f748f06915f950c9/tests/kernel/msgq/msgq_api/prj.conf)

`native_sim` produces a **Linux host executable**, not an emulated Cortex-M CPU. Its normal kernel time comes from hardware models; synchronising ticks to host time can lag under load. ILP32 and LP64 targets also expose different pointer/long sizes. A host speed result or `--rt` mode does not establish MCU WCET, cache/DMA effects or interrupt latency. For this user's macOS workflow, an already approved compatible Linux/runtime path is a launch gate, not an assumed available dependency. [Host/architecture](https://github.com/zephyrproject-rtos/zephyr/blob/684c9e8f32e4373a21098559f748f06915f950c9/boards/native/native_sim/doc/index.rst#L3-L16), [ABI](https://github.com/zephyrproject-rtos/zephyr/blob/684c9e8f32e4373a21098559f748f06915f950c9/boards/native/native_sim/doc/index.rst#L148-L163), [clock behaviour](https://github.com/zephyrproject-rtos/zephyr/blob/684c9e8f32e4373a21098559f748f06915f950c9/boards/native/native_sim/doc/index.rst#L220-L266)

### 2. A sensor path: timestamp precision, acquisition accuracy and quantity semantics

The pinned ICM4268x stream path obtains cycles from the **configured sensor clock** when handling a FIFO event, converts them to nanoseconds and puts that timestamp into the returned batch metadata. It also carries range, axis alignment, ODR and clock frequency. The decoder derives sample deltas from configured periods, frame counts and `rtc_freq`. This is a specific auditable timestamp construction, not proof that each sample carries a physically latched acquisition instant with nanosecond accuracy. [Clock-source contract](https://github.com/zephyrproject-rtos/zephyr/blob/684c9e8f32e4373a21098559f748f06915f950c9/include/zephyr/drivers/sensor_clock.h#L16-L39), [event timestamp L186–215](https://github.com/zephyrproject-rtos/zephyr/blob/684c9e8f32e4373a21098559f748f06915f950c9/drivers/sensor/tdk/icm4268x/icm4268x_rtio_stream.c#L186-L215), [batch metadata L136–153](https://github.com/zephyrproject-rtos/zephyr/blob/684c9e8f32e4373a21098559f748f06915f950c9/drivers/sensor/tdk/icm4268x/icm4268x_rtio_stream.c#L136-L153), [delta calculation L336–355](https://github.com/zephyrproject-rtos/zephyr/blob/684c9e8f32e4373a21098559f748f06915f950c9/drivers/sensor/tdk/icm4268x/icm4268x_decoder.c#L336-L355)

The output format combines a 64-bit base with 32-bit nanosecond deltas. A delta spans at most about **4.295 seconds**; this is not a limit on total uptime. The decoder explicitly detects excessive deltas and skips affected frames in the inspected branches. Any trace consumer must distinguish decoded, dropped and missing observations rather than inventing evenly spaced timestamps for everything. This is a useful test surface already acknowledged in the code, not a newly discovered physical defect. [Types L19–56](https://github.com/zephyrproject-rtos/zephyr/blob/684c9e8f32e4373a21098559f748f06915f950c9/include/zephyr/drivers/sensor_data_types.h#L19-L56), [overflow handling L404–428](https://github.com/zephyrproject-rtos/zephyr/blob/684c9e8f32e4373a21098559f748f06915f950c9/drivers/sensor/tdk/icm4268x/icm4268x_decoder.c#L404-L428)

Range conversion, fixed-point shift and axis mapping also belong to the data contract. A successful decoder does not establish real sensor bias, temperature compensation or calibration accuracy. A board-free experiment can validate a known synthetic scale/offset transformation and calibration-version transition; measured physical accuracy needs a reference and suitable equipment. Record source clock, boot epoch, capture/estimated time, arrival time, configuration and uncertainty separately. [Conversion L58–131](https://github.com/zephyrproject-rtos/zephyr/blob/684c9e8f32e4373a21098559f748f06915f950c9/drivers/sensor/tdk/icm4268x/icm4268x_decoder.c#L58-L131), [axis mapping L466–475](https://github.com/zephyrproject-rtos/zephyr/blob/684c9e8f32e4373a21098559f748f06915f950c9/drivers/sensor/tdk/icm4268x/icm4268x_decoder.c#L466-L475)

### 3. MCUboot: recovery and authenticity have configuration-dependent meanings

Use the MCUboot revision in that Zephyr release's manifest: **`ee39e2d694bd827ffd1bebbce2f571a9154e6ec2`** in the `zephyrproject-rtos/mcuboot` fork. This avoids silently joining arbitrary current SDK and bootloader releases. [west.yml L337–341](https://github.com/zephyrproject-rtos/zephyr/blob/684c9e8f32e4373a21098559f748f06915f950c9/west.yml#L337-L341)

A test update becomes permanent only after the application confirms it; the fallback mechanisms differ across swap, direct-XIP and overwrite modes. Image signatures, transport authentication, health checks and rollback protection solve different problems. Hardware rollback protection requires an optional security counter interface backed by trusted nonvolatile storage. Equal security counters can intentionally permit an older semantic version, so “reject every lower version” is not a faithful universal oracle. The product's fallback and security-epoch policy must be consistent. [Test/revert design L459–477](https://github.com/zephyrproject-rtos/mcuboot/blob/ee39e2d694bd827ffd1bebbce2f571a9154e6ec2/docs/design.md#L459-L477), [rollback protection L1400–1432](https://github.com/zephyrproject-rtos/mcuboot/blob/ee39e2d694bd827ffd1bebbce2f571a9154e6ec2/docs/design.md#L1400-L1432)

The mature baseline is MCUboot's Rust simulator around the upgrade code. Existing tests cover bad signatures, oversized images, revert, permanent updates, interruptions and status-write failures. Reuse them before proposing a new OTA engine. A particularly useful acceptance lesson is that a passing test name is insufficient: `basic_revert` contains a TODO about passing without an actual swap, and selected modes or the `MCUBOOT_SKIP_SLOW_TESTS` environment variable can bypass work. These are visible prior-art boundaries, not proof that MCUboot recovery is broken. Require image-selection and fault-injection witnesses. [Existing suite L26–87](https://github.com/zephyrproject-rtos/mcuboot/blob/ee39e2d694bd827ffd1bebbce2f571a9154e6ec2/sim/tests/core.rs#L26-L87), [revert/interrupt paths L713–755](https://github.com/zephyrproject-rtos/mcuboot/blob/ee39e2d694bd827ffd1bebbce2f571a9154e6ec2/sim/src/image.rs#L713-L755), [skip control L2513–2521](https://github.com/zephyrproject-rtos/mcuboot/blob/ee39e2d694bd827ffd1bebbce2f571a9154e6ec2/sim/src/image.rs#L2513-L2521)

The inspected Zephyr and MCUboot core licences are Apache-2.0. External modules, crypto libraries and Rust crates need their own manifest/terms. The simulator's ordinary build can fetch dependencies; nothing was built, installed or run here. Flash-operation resets in a model do not establish behaviour during real torn writes, brownouts, flash wear or tamper attempts.

## A no-new-board 30/90-day experiment

This is **one project**, with an assumed first 30–50 focused hours and a further 60–100 hours during the next 60 days. Availability and baseline setup are unknown. If approved Linux/compiler/Rust access is absent, the useful deliverable is the trace specification, independent oracle design and blocked-baseline report. No installation request is needed for this research-only deliverable.

**First 30 days: sensor state and timing contract.** Define an acquisition→ISR/deferred worker→consumer pipeline with a bounded queue. Keep source clock/boot epoch, sequence, range/ODR, calibration version, quality flags and arrival/decision times. Specify overwrite/drop policy and make every loss visible. Compare against `k_msgq` and the pinned decoder contract. Reserve fresh traces and expected outcomes prepared by someone independent of the learner/implementation; self-authored fixtures remain exposed design diagnostics.

Use an independent event ledger and a simple schedule model. Include counter wrap, reset, reordered/burst arrivals, stale data, corrupt frames, range changes and a calibration transition. A self-authored arithmetic example illustrates why utilisation is insufficient: tasks with C/T = 0.2/1 and 0.8/5 use 36% of the model CPU, yet a 1.2 ms non-preemptible block plus the first task's 0.2 ms execution already exceeds a 1 ms deadline. Those execution/blocking values are assumptions, not MCU measurements. Separately, `0xfffffff0→0x20` is 48 ticks only under a same-epoch, bounded-gap wrap model; a reset must not be silently unwrapped.

**Days 31–90: update recovery tied to application health.** After any later authorised setup, reproduce upstream tests with exact features and target support recorded. A proposed starting bootsim profile is `sig-ecdsa` plus `swap-offset`, subject to compatibility checks. Its existence in Cargo features does not establish that a local build or every mode combination works. Keep crypto checks active, slow-test skipping unset and exercised flash-operation counts positive. [Feature definitions](https://github.com/zephyrproject-rtos/mcuboot/blob/ee39e2d694bd827ffd1bebbce2f571a9154e6ec2/sim/Cargo.toml#L7-L37)

Witness a clean A→B test boot→A revert and A→B→B confirmation, then inject resets at the selected flash-operation boundaries. Retain independent image identities/digests, boot selections and state transitions. A green result without the intended B boot or injected failure is not coverage. Extend only one gap: for example, a confirmation policy that refuses an image whose synthetic acquisition/compatibility/freshness check fails. Do not reimplement cryptography or treat a mocked trusted counter as tamper-resistant storage.

The acceptance contract is:

- Independently labelled valid/invalid traces plus fresh combinations; all critical invalid cases are rejected or explicitly unknown. Arrivals equal processed plus dropped plus pending, without silent loss or duplicate decisions.
- Model deadlines hold only within the declared feasible model envelope; overload and long blocking produce the expected miss/drop/degraded-state evidence. Host timing is reported separately.
- Memory accounting includes queue objects, padding, stacks and update slots where actually built. Eight 48-byte wire records imply only 384 raw payload bytes; they do not establish whole-system RAM or target `sizeof`.
- Selected OTA cases have real stage/exercise witnesses in the software model, reject bad image validity and preserve the declared recovery/confirmation policy. Coverage is conditional on flash geometry and failure model; fixture counts are not field reliability rates.
- One independently reproducible limitation, regression attempt or justified negative result. If upstream already covers it, narrow the contribution or stop the novelty claim.

Hard timing needs a supported MCU/configuration, an actual compiler/map and appropriate timestamp/GPIO measurement with instrumentation effects accounted for. Calibration needs a physical reference; flash/power recovery needs actual device/power behaviour; security epochs need a genuine root-of-trust/key lifecycle. No such evidence was obtained. Hardware-in-loop work becomes a later access-dependent branch, not an implied result of desktop simulation.

## Skills, employers and contribution routes

**C is the initial depth requirement:** fixed-width arithmetic and undefined behaviour, ownership/lifetime, alignment/endianness, memory-mapped I/O, interrupt-safe synchronization, stacks/heaps and linker maps. `volatile` is not a substitute for a concurrency contract. Add C++ object/allocation/exception policy when the selected stack uses C++; Rust is relevant to this simulator and some firmware stacks, but learning all three languages is not the entry requirement. Rust ownership helps with particular memory/concurrency errors; FFI, DMA and deadlines still need explicit reasoning. Formal scheduling/proof work is a deeper optional research route.

## What automation changes, and what remains unknown

Nordic documents [AI-assisted configuration/migration/troubleshooting capabilities](https://www.nordicsemi.com/Products/Technologies/AI-assisted-development) and [optional agent tools](https://docs.nordicsemi.com/r/bundle/nrf-connect-vscode/page/index.html/ai-agent-tools-included?contentId=TueA8I2BvtPAHxEqe7ENAA) that can access SDK context and local build/flash/device operations. These are vendor capability descriptions, not an independent time-saving or headcount study. Existing RTOS drivers, code generation and automated tests already remove considerable bespoke setup work. Boilerplate generation alone is therefore a weak preparation signal.

The useful hypothesis is that deeper ownership remains valuable where a team needs correct clock/quantity interpretation, a reproducible failing execution, a timing/resource argument or a recoverable release. It would weaken if the selected existing tool already supplies the needed verification, if no accessible team values the artifact, or if the engineer lacks required domain/bench access. AI can improve verification as well as implementation; none of these sources establishes permanent human scarcity, growing firmware headcount or automation immunity.

For year-one evidence, seek a narrow reproducible fix/test and a clear statement of its limits. Later ownership could include a driver/data contract, release regression suite or update subsystem that others actually use. Leadership would require sustained decisions across hardware/firmware/product boundaries and mentoring, with independent adoption evidence. These are development criteria, not a five-year promotion guarantee. FreeRTOS is an employer-specific alternative; micro-ROS adds no necessary proof to this bounded experiment.
