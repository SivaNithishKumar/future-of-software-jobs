## What an accepted proof establishes

Keep four boundaries separate:

| Boundary | Useful question | Typical portfolio overclaim |
|---|---|---|
| Informal requirement → formal statement | Did the predicates preserve admissible inputs, required outputs, unchanged state, error cases and intended meaning? | The proof is accepted, so the requirement must have been understood |
| Statement → checked proof | Were the exact obligation, imports, axioms and checker configuration fixed? Were placeholders or unchecked assumptions allowed? | A green editor/build means an assumption-free, independently rechecked theorem |
| Program/model → executing implementation | Do the verified semantics match compiled code, data representations, integer/memory semantics and external functions? | A mathematical model automatically verifies a deployed service |
| Environment → actual use | Do clocks, concurrency, permissions, failure modes and operating conditions satisfy assumptions? | A finite protocol model or RTL property establishes every real-world safety/liveness claim |

These are different engineering tasks. A Lean theorem can be fully valid while proving a weak or unintended mathematical proposition. Program verification additionally needs a relationship to executable behavior. RTL work adds architecture, reset/clock and abstraction knowledge; protocol assurance adds failure/fairness/liveness assumptions. A small software proof is transferable reasoning evidence, not qualification for all four domains. The existing systems/protocol notes supply the latter boundaries; this pass audits the first two.

## Three primary anchors

### FV-1 — Verus-SpecGym tests the specification, not just proof compilation

[Agarwal et al., arXiv:2605.26457v1](https://arxiv.org/html/2605.26457v1), submitted **26 May 2026**; preprint, paper **CC BY 4.0**. CMU/Amazon affiliations are publication context, not a current-employment directory. [DOI lineage](https://doi.org/10.48550/arXiv.2605.26457).

The 581 Codeforces-derived tasks test valid/invalid inputs and correct/incorrect outputs. Agents receive three completeness examples; hidden tests include adversarial hacks. Reported strongest pass@1 is 77.8%, with a $2.50/75-minute/400-call cap and 4-CPU/8-GB task environments; these are selected contest tasks and historical model/configuration results, not October-wide capability or workforce estimates. Its faithfulness signal is explicitly approximate. The runtime fallback uses `exec_spec_unverified`, omitting a proof that executable checks preserve specification meaning; this is acknowledged testing infrastructure, not a proved semantic-equivalence oracle. Unsupported/floating-point tasks are filtered. Passing all retained tests cannot establish equality with every informal requirement. See §§2–4 and Appendices D/F. **Implication:** specification writing already has substantial AI automation; independently grounded adversarial cases and evaluator-semantics audits remain useful work.

### FV-2 — Self-Spec keeps the model's own statement through downstream verification

[Qian et al., arXiv:2609.39568v1](https://arxiv.org/html/2609.39568v1), submitted **30 September 2026**; preprint, paper **CC BY 4.0**. Peking University/SJTU/other byline affiliations are source context. [DOI lineage](https://doi.org/10.48550/arXiv.2609.39568) is marked pending registration by arXiv.

VeriCodeBench has 400 tasks, 100 each in C, Java, Rust and Python. It separates code validity from coverage of curated requirement obligations and requires both on the same task for joint success. Direct generation averages 71.0% validity but 44.1% joint success across the reported model–language settings; these are aggregate benchmark results, not population estimates. Coverage checks reverse implication direction for preconditions to penalize overly restrictive input domains. Stronger contracts can make proofs harder, so maximizing proof success alone can select easier, weaker statements. The fixed obligation set/normalization/SMT machinery remains an oracle to audit; deterministic scoring does not prove the curated targets captured the whole requirement. No independent replication or peer review was verified. **Implication:** compare frozen independent statements and self-generated statements end to end, rather than multiplying separately measured stage success rates. See §§3.2/4 and Appendix A.

### FV-3 — Lean's current validation instructions explicitly retain the meaning boundary

The [official validation guide](https://lean-lang.org/doc/reference/latest/ValidatingProofs/) separates ordinary build/editor checking, transitive axiom inspection, `lean4checker`, and a sandboxed `comparator` challenge with external checking. Even its strongest route still trusts the independently written challenge statement and interpretation of definitions. Therefore an axiom-clean result can have the wrong meaning.

For a fixed snapshot, [`Manual/ValidatingProofs.lean` at `400f1682…`](https://github.com/leanprover/reference-manual/blob/400f1682df64bc00e485215bfa4398d24c0f220c/Manual/ValidatingProofs.lean) was inspected. Its native-evaluation notes distinguish pre-4.29 `Lean.trustCompiler` from per-computation native axioms after 4.29 and removal of the former machinery in 4.35. A future acceptance script that merely searches for the old axiom name would be incomplete. Check the transitive axiom footprint and exact version; do not use “no `sorry` text” as the whole audit. This is documented tool behavior, not a checker run performed here.

## A classical-software experiment with a separate oracle

**Proposed main path: verified interval normalization.** Use only self-authored integer-interval data and an existing mature native-language reference, under one declared bounded integer representation. A separate setter defines the requirement before generation: sorted disjoint output, exact union coverage, empty/singleton behavior, adjacency convention, invalid-range handling and unchanged input. The setter resolves those product choices rather than letting the model choose the easiest contract. Byte-buffer, object mutation, full concurrency and real-time claims are excluded unless later separately specified.

Required foundations are propositional/predicate logic, quantifiers and implication direction; sets/sequences; induction/loop invariants; host-language integer overflow and mutation; independent test construction; debugging and experimental accounting. Learn targeted gaps rather than restarting an entire CS degree. Verus adds Rust ownership/views and solver proof diagnostics. The optional Lean route adds dependent types, definitions, theorem signatures, induction and library search; it is a different depth from RTL design or operating a protocol model checker.

**First 30–50 focused hours (a 30-day probe only if time permits).** Spend roughly 6–10 on a fresh logic/code diagnosis and exact contract; 10–16 on simple reference/independent tests and intentionally weakened contracts; 8–16 on a tiny verified implementation slice; 6–8 on explaining failures and preserving the manifest. This is a planning range, not a completion guarantee. If approved tool access is absent, finish the contract, source audit and authored fixtures first and label proof execution pending.

Before any model generation, seal distinct valid-input, invalid-input, correct-output and wrong-output cases. Include output with correct shape but wrong coverage, dropped duplicates/ranges, a boundary overflow, accidental input mutation and a precondition excluding a valid edge case. A nonempty precondition witness catches one class of vacuity; it does not prove the full domain is preserved. Include a deliberately weakened specification that can be proved while violating an independent case. The learner must explain why proof success did not imply requirement success.

**Next 90–150 hours (a 90-day extension only if worthwhile).** Compare three arms on fresh matched task variants: ordinary reference/tests; AI-generated statement plus AI implementation/proof; independently frozen statement plus AI implementation/proof. Use the same checker/version, allowed editing scope, resource limits and independently hidden requirement tests. The statement must remain frozen during implementation repair; any proposed specification change is separately reviewed and reported. Record learning/order effects; this small purposive comparison is not a developer-productivity RCT. No new model training is necessary.

Report joint requirement-and-proof acceptance per all planned tasks, invalid/wrong outputs accepted, valid/correct outputs rejected, unknown/timeouts, transitive assumptions, changed-interface cases, actual human review/repair hours and complete model/compiler/evaluator costs. Keep code validity and requirement fidelity separately visible. Preserve failures and reviewer disagreement. Then introduce one requirement change and measure what breaks in the proof, reference and implementation; maintenance is a useful extension beyond a one-shot green result.

**Optional mathematical contrast, not another simultaneous curriculum:** fix a small meaningful theorem and its definitions independently, then let AI supply only its proof. Separately author a trivial altered definition that makes the theorem easy and demonstrate conceptually why a checker could accept it. Audit exact statement identity and transitive axioms under the current Lean guidance. Do not present a deliberately weak toy as a discovered Lean bug or as original mathematical research.

**Advance/redirect gates.** Advance only if at least one independent counterexample or changed-requirement failure is correctly diagnosed, the exact tool/rights path is feasible, and the learner can explain the proof unaided. Redirect if no independent oracle exists, the proof changes the goal, hidden cases were exposed/tuned on, setup exceeds the approved budget, or ordinary tests/reference meet the same scoped contract with lower maintenance/review cost. A negative result can demonstrate depth. A useful upstream contribution would be a minimized supported-language counterexample, translation mismatch or diagnostic/test fix with maintainers' context—not another unreviewed batch of generated proofs.

## What this could mean for work by 2031

**Observed:** current research already automates substantial specification and proof/code work; official contribution standards demand understanding, and an actual hardware role demands domain experience. **Inference:** the most useful small entry artifact is a faithful, maintainable contract plus a diagnostic counterexample and a proof under explicit assumptions. Proof-token volume alone is a weaker signal.

**Hypothesis, not a scarcity claim:** wider AI-generated software could increase verification adoption and shift work toward choosing valuable properties, connecting model/implementation/environment, maintaining libraries/toolchains and reviewing requirement changes. The counterhypothesis is that native AI tools automate much of this within existing teams and reduce standalone proof-writing work. Neither two papers nor selected vacancies measures net jobs, wages, unfilled demand or a guaranteed human advantage. Falsifiers include improved autoformalization on new independently authored requirements, lower whole-workflow review/maintenance costs, and employers obtaining the same outcomes with unchanged or smaller teams.

Leadership evidence would be a verified component or diagnostic workflow others actually maintain/use, fewer review escapes at measured cost, clear assumption ownership and successful requirement changes across versions. An original result could be a reproducible fidelity/evaluator failure on a meaningful task with a credible rival explanation ruled out. Neither a proof certificate nor a 90-day schedule alone establishes expertise, research novelty or leadership.
