The readable [logical security model](https://opentitan.org/book/doc/security/logical_security_model/) is the technical anchor. It gives native security functions a meaningful contract and leaves later software responsible for further properties. A conceptual counterexample illustrates the boundary: an authorized signed owner image may still implement inappropriate isolation or accept an unintended application request. That would not refute boot authentication, nor does this note demonstrate an OpenTitan flaw. No candidate firmware, attack, credential or real target was used.

The distinction creates useful software questions—requirements, privilege boundaries, release identity and policy/test evidence—but does not prove they remain manual or require another custom layer. Native verification and hardware automation are positives. Appropriate configured native controls may fully meet a real use case; that should stop extra custom work. The model’s normative requirements are not an executed formal proof or a certification, and a moving model is not automatically the contract implemented in a particular shipped release.
