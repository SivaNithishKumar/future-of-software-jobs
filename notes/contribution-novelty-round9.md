## Finding

The most credible near-term contribution routes are **a requested regression test or a carefully controlled benchmark correction**. Randomized assessments, hidden answers, experiment provenance and reproducible reports already exist. A generic new wrapper in those categories would mostly repeat prior art.

There are concrete public requests: PyMatching's negative-weight/correlation tests and PyVRP's quick benchmark/performance work. These are evidence of specific maintainer interest, not reserved assignments, guaranteed acceptance, research novelty or paid employment. Neither this bounded search nor an open issue proves that the current code still lacks a test or that no competing PR exists.

## C1 — Can a cheap routing regression test catch a real change without changing the problem?

**Catalogue link:** `education-quantum-or-round7.project.scheduling`, OR branch and PyVRP/current-baseline records. This is a routing-specific contribution alternative to the initial scheduling learning project, not a requirement to do both.

**Prior art checked.** PyVRP already documents benchmark instances, CPU-normalized runtime conventions and different rounding rules for CVRP versus time-window instances. Its current developer documentation is labeled **1.0.0a0**, not the same artifact as a selected stable package. The official VRPLIB parser explains a consequential trap: an X-instance's Euclidean specification can produce unrounded distances while the literature comparison uses rounded integers. Its solution parser reads routes/costs; parsing is not independent feasibility certification. [Benchmark conventions](https://pyvrp.org/dev/benchmarking.html), [VRPLIB format/rounding notes](https://github.com/PyVRP/VRPLIB).

The issue board supplies a narrower target than “invent a better VRP solver.” Maintainer-authored **#1040** asks about short GitHub Actions benchmarks, while **#992** tracks improving ILS on small instances. An algorithm's newer release does not automatically dominate every size/variant. The earlier HGS→ILS change therefore motivates a matched comparison; it does not settle the winner. [Quick benchmark issue](https://github.com/PyVRP/PyVRP/issues/1040), [small-instance performance issue](https://github.com/PyVRP/PyVRP/issues/992). The original solver paper's arXiv v2 is dated 21 March 2024 and describes HGS; it is foundational prior art, not a specification of the 2026 ILS implementation. [Original primary paper/version](https://arxiv.org/abs/2403.13795v2).

**Residual question.** Can a tiny benchmark detect an actionable regression on supported constraints with acceptable false alarms on the intended runner? Is the apparent change actually from rounding, instance indexing, objective terms, different termination rules, version defaults or host noise? A successful answer could be valuable even if it shows that a proposed algorithm gain disappears.

**Minimal convincing test, proposed.** Start with owned tiny CVRP/VRPTW fixtures whose capacity, depot, time-window, distance and service-time calculations are independently written down. Check both deliberately invalid routes and alternative valid routes; recompute the objective rather than trust a reported `Cost`. Pin two selected solver revisions, instance hashes, rounding, build flags, seed and one-core budget. Add small/medium cases with one relevant operational constraint and preserve the same feasible region in every arm.

Before claiming a speed regression, perform an A/A repeat comparison with no code change, then a controlled known slowdown or a previously documented regression. Report quality versus time, first feasible result, failures and variability. If runner noise masks the proposed signal, use a more stable dedicated measurement or limit the CI check to correctness/algorithmic work—not a misleading wall-clock gate. Official full benchmark runtimes are much larger than this proposed CI slice; do not label the slice a full published-benchmark reproduction.

**Rights/resources.** PyVRP/VRPLIB code is MIT; third-party instances retain their own provenance/terms. Owned fixtures avoid assuming rights over an entire benchmark collection. Conditional first-month allowance: 35–55 focused hours, up to four CPU core-hours / 8 GB for the initial experiment; a 12-instance × two-version × three-seed × 60-second grid is 72 core-minutes at one core per run, leaving room for A/A checks. A C++ toolchain/dependencies require a separately approved setup. No CI infrastructure or cloud minutes were used.

**Correct channel and acceptance.** PyVRP's official contribution guide asks for a GitHub issue discussion **before** substantial work; tests, documentation, benchmark evidence and AI-use disclosure apply. The new-variant guide also expects existing-instance regression evidence. The public issue is a place to check existing work later, not authorization to post now. [Contribution policy](https://pyvrp.org/dev/contributing.html), [variant acceptance guidance](https://pyvrp.org/dev/new_vrp_variants.html).

**Kill criteria / depth path.** Stop novelty claims if correct rounding/configuration explains the result, the current branch already covers it, or the proposed CI test is redundant/noisy. A reproducible fixture or negative result remains useful preparation. Progress toward deeper competence comes from understanding why a neighborhood/constraint/search change alters the result, defending the benchmark and maintaining a reviewed correction—not from announcing a new routing framework. A new algorithm would need broader prior-art review and held-out results beyond these fixtures; commercial value needs a real workflow and economics separately.

## C2 — A requested QEC test is more attainable than a new decoder

**Catalogue link:** `education-quantum-or-round7.project.qec-decoder`; Stim/PyMatching records and the separate decoder/streaming technical proposals.

**Prior art checked.** PyMatching already implements two-pass correlated matching and explicitly requires correlation support at construction and decode. Sinter already provides parallel sampling, resumable statistics, shot/error/discard counts and CPU-time accounting. Therefore plotting standard versus correlated memory curves or building a CSV/resume wrapper is not itself a new contribution. [PyMatching method/API](https://github.com/oscarhiggott/PyMatching), [Sinter API—development version, stable API must be checked](https://github.com/quantumlib/Stim/blob/main/doc/sinter_api.md).

There is specific visible demand: maintainer-authored **#162**, open and unassigned on the retrieved page, requests Python tests for negative weights with correlations. **#142** requests exact-weight/LER pybind-flow checks but is assigned; do not independently duplicate that scope. A fresh community proposal **#187** already describes saturated-prior robustness, determinism and a paired test, reporting that PyMatching 2.4.0 passes. It is a community proposal/self-report, not a proven invariant or accepted maintainer design. [#162](https://github.com/oscarhiggott/PyMatching/issues/162), [#142](https://github.com/oscarhiggott/PyMatching/issues/142), [#187](https://github.com/oscarhiggott/PyMatching/issues/187).

**Residual question.** Does the current relevant Python binding/test path correctly handle a small independently specified negative-weight/correlation case? The public issue establishes a requested test area; it does not prove a current functional bug. The attempted current test-file retrieval failed, so current coverage is explicitly unresolved.

The underlying negative-weight transformation is already published. *Sparse Blossom*, v2 (14 January 2025), Appendix C derives how to flip the relevant prior/weight representation, adjust the syndrome, decode the nonnegative problem and transform back. Its three-bit example provides a hand-checkable starting oracle. Reproducing that derivation is preparation; integrating a genuinely missing correlation/interface regression could be a contribution. It would not rediscover a method already explained in the paper. [Primary methods, Appendix C](https://arxiv.org/html/2303.15933v2).

**Minimal convincing test, proposed.** First hand-derive a tiny graph's syndrome/parity and minimum-weight alternatives, including negative weights and degeneracies. Exhaustive enumeration on a tiny owned graph can supply an independent ordinary-matching oracle. For a genuinely correlated two-pass case, specify each stage's weights/behavior rather than pretending a heuristic must equal global maximum-likelihood decoding. Accept any equivalent optimum when ties exist; do not demand one arbitrary matching or compare predictions directly with hidden physical truth for an ambiguous syndrome.

Then exercise the documented model/decoder correlation switches, zero/single-fault controls and one deliberately broken test arm. Compare the Python interface with a separately justified expected result; an agreement between two wrappers around the same kernel is not independent proof. Use a small fixed sample only for a clearly defined statistical property; keep all shots/discards and paired disagreements visible. “The true model can never hurt” is not assumed universally for an approximate decoder from one passing test. Streaming/latency is a separate question and needs arrival/queue/feedback semantics.

**Rights/resources.** Earlier verified pins `stim==1.16.0` and `pymatching==2.3.1` are Apache-2.0 reproducibility baselines, not claims of latest versions. Check the current requested target and related PRs before later work. An initial deterministic fixture should fit a proposed cap of one CPU core-hour / 2 GB; allow 24–40 focused hours in a first month to learn the mathematics and prepare a small result. Failure to explain the parity/weight calculation independently redirects to study. No QPU or hardware claim is needed.

**Contribution policy changes the route.** Stim's current CONTRIBUTING requires a CLA/original work and explicitly says AI-generated code does not qualify as original creation. Do not prescribe an agent-written Stim PR. A retrieved PyMatching-specific contribution policy was not established in this pass; its maintainer issue/discussion is the correct future scope/policy channel. Stim's rule must not be silently assigned to another repository. [Stim policy](https://github.com/quantumlib/Stim/blob/main/CONTRIBUTING.md).

**Kill criteria / depth path.** Stop if the current branch already tests it, another contributor owns it, the expected property is false, or only a code-version mismatch explains the case. A manually understood test or precise discrepancy report is a plausible engineering contribution, with acceptance contingent on maintainers. It does not invent error correction, validate leakage on hardware or confer quantum-research seniority. Further research would need a genuinely unresolved decoder/noise question and comparisons against matching and other serious decoders under matched assumptions.

## C3 — Can assessment exports preserve the intended information boundary without breaking valid work?

**Catalogue link:** `education-quantum-or-round7.project.learning-diagnostic`; cross-catalogue learner-exposure repair from the human-domain review. This audits tools/fixtures, not Bio's preparation DAG or learning efficacy.

**Prior art checked.** nbgrader already removes solution/hidden-test regions, computes checksums and has a marking-scheme attachment-leakage check. PrairieLearn already has seeded variants, server-side correct answers, answer-panel controls and correct/incorrect/invalid testing hooks. It also documents AI-assisted question generation and asks authors to review variants/submissions. Randomization plus a hidden answer bank is an existing system feature, not an original research result. [nbgrader configuration](https://nbgrader.readthedocs.io/en/stable/configuration/config_options.html), [PrairieLearn generator/test contract](https://docs.prairielearn.com/question/server/), [AI generation guidance](https://docs.prairielearn.com/question/ai-generation/).

**Residual question.** Is there a real supported export/feedback/scoring path that violates a clearly specified information or answer-validity contract? An example might be a key surviving through a particular attachment/output representation, or a correct alternative solution being rejected. This is a candidate question; no such defect was reproduced here. A platform's hidden keys also cannot erase knowledge already seen by the learner who authored them.

**Minimal convincing test, proposed.** Use a handful of wholly owned question notebooks/forms and a separate expected export manifest. Include a legitimate student-visible image, an instructor-only answer image, visible examples, hidden tests and a correct alternative response. Inspect exported student bytes and feedback as well as the API result. A fixture must catch a deliberately exposed key and also preserve legitimate content; “delete everything” is not a valid privacy/assessment fix. Test scoring with independently written accepted/rejected answers, rather than a generator grading only its own generated correct answer.

For the personal diagnostic, record item/concept exposure and use separately prepared unseen forms where available. If the reader has seen the keys or authored the tested principle, label that diagnostic unblinded. Different random numbers are not proof of equivalent difficulty or new conceptual transfer. Establishing human learning/equivalent forms needs measurement expertise and an independently authorized study, not more synthetic answer checks.

**Rights/resources/channel.** nbgrader's checked licence is BSD-3-Clause. PrairieLearn's current licence has Community/Enterprise/client-side/third-party distinctions; it must not be flattened to MIT. Its public-question source-sharing option is CC-BY-NC, separate from platform code and learner submissions. Use original synthetic questions/media and no student data. The first export/scorer fixture has a proposed four-hour / 1 GB CPU cap inside a 25–40 focused-hour month; full platform setup is conditional and may be inappropriate. [nbgrader licence](https://github.com/jupyter/nbgrader/blob/main/LICENSE), [PrairieLearn licence](https://github.com/PrairieLearn/PrairieLearn/blob/master/LICENSE), [question sharing](https://docs.prairielearn.com/question/overview/).

nbgrader points contributors to its developer guide. PrairieLearn asks for discussion before large changes and an introduction in its public developer channel for people outside education; AI use must be disclosed and a CLA applies. These are future participation conditions, not instructions to contact anyone during this research. A current open bug/PR and exact release must be checked before allocating weeks. [nbgrader contribution route](https://github.com/jupyter/nbgrader/blob/main/CONTRIBUTING.md), [PrairieLearn contribution rules](https://github.com/PrairieLearn/PrairieLearn/blob/master/CONTRIBUTING.md).

**Kill criteria / depth path.** If supported settings already enforce the contract, document/reuse them and stop the novelty claim. If no independently valid answer/exposure oracle exists, keep it as tooling practice. A demonstrated missing fixture, narrow bug or clear configuration example could help an existing project; generic new assessment infrastructure has weak evidence of incremental value. Accepted maintenance plus educator collaboration can develop assessment-engineering judgment. Neither software acceptance nor this audit establishes a new pedagogy or commercial moat.

## C4 — Does an evaluation report compare compatible things, rather than merely record their names?

**Catalogue link:** `ai-ml-round5.project.evaluation`, round-6 capability audit's provenance ledger and metadata repair proposals. This is a small validation extension candidate, not a rewrite of the root's catalogue/merge.

**Prior art checked.** Inspect logs already hold task/version, resolved arguments, model configuration, scorers/metrics, package versions and Git revision/dirty state. Its log workflow addresses stable sample IDs when retrying shuffled tasks. Croissant already describes dataset files, licences and checksums. A JSON ledger collecting those fields is therefore ordinary integration. [Inspect log schema](https://inspect.aisi.org.uk/reference/inspect_ai.log.html), [retry/ID behavior](https://inspect.aisi.org.uk/eval-logs.html), [Croissant](https://github.com/mlcommons/croissant/blob/main/README.md).

Inspect Evals goes further: its current tools generate reproducible reports, references, task/sample/token records and approximate costs with `prices_as_of`; it has task-version/changelog checks and judge-calibration tooling. Do not claim those functions are missing. Its contribution policy distinguishes maintenance-task scores from model benchmark results and requires task-version changes when a change could affect results/interface. [Existing report/lint tools](https://github.com/UKGovernmentBEIS/inspect_evals/blob/main/tools/README.md), [task/version rules](https://github.com/UKGovernmentBEIS/inspect_evals/blob/main/CONTRIBUTING.md).

**Residual question.** Can a real pair of results pass the mature reporting path while a downstream reader receives a misleading comparison because task/scorer/sample/budget/price semantics differ? This audit did not retrieve the current `report_utils.py`, so it does **not establish** that a compatibility check is absent. First reproduce the existing report path or use its supported configuration; if it already prevents the problem, there is no gap to build.

**Minimal convincing test, proposed.** Start with owned no-model log fixtures, not an expensive benchmark rerun. Construct one genuinely comparable pair plus individually changed task version, sample set, binary-versus-partial reward, missing artifact hash, budget and price date. Write expected decisions in advance: comparable, explicitly qualified, or insufficient information. A missing field remains unknown; it does not establish incompatibility, fraud or lack of rights. Preserve raw evidence and distinguish a changed experiment from a changed software HEAD. Metadata equality also cannot prove identical task semantics or that a grader is correct.

Test a small adapter/report annotation against the native report, including false rejections of compatible records. An observed case where the annotation prevents a wrong conclusion is stronger than generating a new catalogue schema. A broad claim that such mistakes are common would require a separate sampled audit; one case does not establish incidence or a market.

**Rights/resources/channel.** Inspect code is MIT at the previously checked boundary; individual eval content/data/sandboxes/model terms differ. Croissant implementation/examples are Apache-2.0, while the specification uses CC-BY-ND 4.0 with stated extension/linking guidance—do not copy it into a modified purported standard. Proposed first-month allowance: 20–35 focused hours; initial 20 fixture pairs, ≤1 core-hour / 1 GB, no model calls or private logs.

Inspect **core** usually requires a maintainer-accepted issue before code; extensions are a first-class route, with human understanding/AI disclosure requirements. **Inspect Evals is different:** current policy restricts PRs to pre-approved contributors and does not accept new evaluation implementation code; it directs existing evals to a register and problem evidence through issue/log routes. No logs were uploaded and no package was published here. [Core contribution policy](https://github.com/UKGovernmentBEIS/inspect_ai/blob/main/CONTRIBUTING.md), [Evals contribution policy](https://github.com/UKGovernmentBEIS/inspect_evals/blob/main/CONTRIBUTING.md).

**Kill criteria / depth path.** Stop if the mature tool/configuration already solves it, the supposed mismatch is actually intentional/clearly labeled, or no independent comparison contract can be stated. A local extension/reproduction report may still teach valuable research engineering. A novel benchmark-validity method would require a new method, representative failure cases and external validation; a commercial moat would require repeated buyer value/distribution beyond a small open adapter.

## A path toward competence that can earn external trust

Choose one candidate after a 4–6-hour prerequisite/fixture probe. A first substantial result is: independently derived expected behavior, a reproducible adverse case, a current-prior-art comparison, and an explanation of the implementation/method boundary. It is acceptable if the conclusion is that the mature tool already works.

The next gate is an independently reviewable local report/test, followed only under later authorization by the project's actual scope/contribution process. An open issue, maintainer comment, accepted PR, release inclusion, independent reuse and sustained ownership are different milestones. Do not label a drafted patch “accepted,” or a merged one-off test “technical leadership.” External review timing and willingness remain outside a 30/90-day promise.

Deeper prominence can come from maintaining a useful part of a system, repeatedly finding consequential errors, explaining the relevant mathematics/domain, and producing work others can reproduce and rely on. This is a plausible development path, not evidence of a guaranteed title, income or lasting moat. The transferable preparation survives a rejected product hypothesis; the commercial claim must earn its own evidence.
