# Formal software verification: bounded methods audit

This is a worker-owned research contribution, not the final career report. It audits an older result missing from the bounded saved-note census; it does not identify the latest model frontier. The question was fixed before retrieval. Different review and root retention remain pending.

[AlphaVerus, exact v1](https://arxiv.org/html/2412.06176v1) is a genuine implementation-plus-proof task given formal statements, rather than only proof completion. The canonical numeric/version table is in the companion JSON’s `observedFacts`; source identity is checked against [arXiv metadata](https://arxiv.org/abs/2412.06176). The [official project](https://alphaverus.github.io/) exposes a code route, but this bounded pass did not follow it.

The important distinction is between an algorithm and proof satisfying a supplied statement, and that statement faithfully expressing the requirement. This distinction does not erase the positive result. A mature verifier supplies useful structured rejection and error feedback; a generator can use it to search for implementation structure as well as proof. Treating all such work as irreducibly human is unsupported. Conversely, acceptance by that tool is not an independent check of the chosen requirement, the compiled application or a maintained service.

The report separates the mutable translation stage from the downstream supplied-statement stage. The former needs a fidelity check; the latter needs evidence that the statement remained fixed during generation and repair. That enforcement was not independently audited here. A source’s claim that critique detects mistakes must not be renamed a formal equivalence certificate. Critique and escape filtering are meaningful safeguards, not evidence that every trusted declaration or assumption was inspected.

The task denominator also constrains interpretation. Splitting functions out of programs changes the unit: function-level success is not joint whole-program success, particularly when dependencies or preceding functions are supplied. A success-anywhere search score does not disclose the first-attempt yield or total useful-work cost. Failed, invalid, rejected and timed-out generations matter. Generation dimensions cannot be silently summed into observed usage; model, verifier, critique, contamination filtering, curation and repair costs require a complete ledger. Comparisons with a proof-annotation system must keep their different input information visible.

The paper’s overlap-control effort is a positive. It does not establish that all underlying model training is uncontaminated or that filtered algorithm tasks represent industrial requirements. A measured model/scaffold comparison does not isolate human productivity, developer learning or hiring demand. No such inference is made.

For trust, the necessary object is an explicit manifest: exact verifier/solver/library/build versions; admitted axioms and trusted external declarations; permitted unsafe or unverified boundaries; specification imports; termination policy; and the connection between checked code and executable behavior. A sample containing a termination measure does not establish total correctness for every task. A missing manifest in this pass means **not established here**, not that Verus is unsound, unusable or unavailable. Displayed HTML code is not an immutable executable artifact, and missing prompt bodies in that conversion are not proof they are absent from every release.

The source budget is closed at three primary surfaces: metadata, exact v1 HTML and the official project page. No repository revision, paper-matched verifier build, code/data/model/dependency licence or complete compute bill was confirmed. No code, corpus, model, native compiler or verifier was acquired or run. Therefore this packet is a methods reading, not reproduction. Public project and historically saved contributor channels are discovery routes; they do not establish current affiliation, vacancy, qualification, permission to contact or permission to submit.

If that project is selected, the proposed change is a reporting contract: record source/version, allowed editing scope and statement hash; every strengthened precondition; transitive trust and termination assumptions; runtime status; all tasks/attempts; independent requirement acceptance alongside proof acceptance; and full human/model/verifier maintenance cost. This is a proposed integration hypothesis, not something the paper tested.

The next-effort decision must be allowed to lose. Withhold original-requirement acceptance if the system silently narrows the admissible inputs or uses an unapproved trust escape. Stop the fidelity claim if an independent oracle cannot be arranged without exposing its keys. Reject extra custom continuation when the ordinary/native baseline meets the same scoped acceptance at lower review and maintenance cost. If tools, rights, prior knowledge or a qualified reviewer do not fit the old approved cap, retain a source/contract report and label proof execution pending. Do not relabel that source-only outcome as a completed verified system.

This result supports the plausibility of automating more proof-producing software work. It does not establish an enduring specification moat, paid scarcity or a 2031 job count. The plausible preparation value is learning to state what was checked, under which assumptions, and whether the checked result was useful—subject to a fresh prerequisite gap and an actual independent oracle. Hardware, protocol, quantum and safety-critical role readiness require their own domain evidence.
