# Health interoperability option: FHIR, OMOP and meaning-preserving data engineering

Research snapshot: 20 October 2026; main evidence cutoff: 19 October 2026. Research and experiment design only. No patient records, installations, validator/server execution, accounts, terminology licence acceptance, downloads of software or bulk data, or outreach. Existing `bio.md`, `bio-round2.md`, `sectors.md` and taxonomy coverage were checked: they cover clinical models and generic EHR integration, without this version/field/state depth. This report proposes an optional child of `darkside2031.bio-science.clinical.workflow.data`; it does not select a new main career bet.

The useful software specialty is preserving meaning across systems and changes: whose identifier, which vocabulary, what unit, which time, which version, and what the receiving workflow can safely infer. Existing servers and validators already handle considerable work. An independently specified reconciliation test can demonstrate engineering skill; a new generic FHIR server or a high schema-validation percentage provides little evidence of an unmet product need.

## 1. Exact versions and support boundaries

**HL7 FHIR:** the official directory still puts **R5, 5.0.0, dated 26 March 2023**, under current published versions. R4 is **4.0.1**, and R4B **4.3.0**. Its July 2026 R6 snapshot and ballot entries sit under work in progress, despite the snapshot's “stable” wording. A contract with an R4 implementation guide remains an R4 contract; automatically switching it to R5/R6 is not interoperability. The continuous build is explicitly volatile. [Official version directory](https://hl7.org/fhir/directory.html)

**OMOP:** **CDM v5.5.0 was released 25 August 2026**, tag commit `ba3dc1b`. Its changes include seven optional fields on existing tables and three vocabulary metadata tables. The new `cdm_release_identifier` makes release provenance explicit. [Release and changes](https://github.com/OHDSI/CommonDataModel/releases/tag/v5.5.0) This supersedes an older assumption that 5.4 is the newest target. The repository explicitly warns that v6.0 is not fully supported by the OHDSI tools/methods and recommends 5.5; its mandatory datetime change alters analytical timing assumptions. The generator package's own **1.0.1** version is not the CDM's 5.5 version. ETL conventions are not generally frozen by CDM version alone, so pin documentation and transformation policy too. [CDM repository](https://github.com/OHDSI/CommonDataModel), [tagged package metadata](https://raw.githubusercontent.com/OHDSI/CommonDataModel/v5.5.0/DESCRIPTION)

**Native validator support is a separate contract.** HAPI's published compatibility table includes R4 4.0.1, R4B 4.3.0 and R5 5.0.0; it records JDK17 for HAPI 8.2.0. It does not establish compatibility for an arbitrary later patch, JDK or R6 package. [Compatibility table](https://hapifhir.io/hapi-fhir/docs/getting_started/versions.html) The release reader exposes **v8.12.1**, commit `c8cc1db`, with a 15 September timestamp; the extracted release page omits the year, so this report does not certify its calendar date or that it is the newest maintained patch. Current documentation shows a snapshot-powered site and a different displayed documentation version. Pin a tag plus validation packages and runtime; do not mistake the documentation header for a release. [Exact release](https://github.com/hapifhir/hapi-fhir/releases/tag/v8.12.1), [documentation site](https://hapifhir.io/hapi-fhir/docs/)

**DQD's 2026 change matters:** DataQualityDashboard NEWS lists **2.9.0, 5 October 2026**, accepting CDM 5.5. Its new vocabulary tables are excluded by default; inherited thresholds remain, and `OBSERVATION.value_as_date` deliberately avoids event-date plausibility checks. May 2026 fixes also changed reporting for filtered checks and not-applicable calculation. [Versioned changes](https://github.com/OHDSI/DataQualityDashboard/blob/main/NEWS.md) The README currently offers 5.5 threshold files while saying package tests cover only 5.3/5.4. That is a documented support/testing distinction, not proof that 5.5 fails. [Requirements and support](https://github.com/OHDSI/DataQualityDashboard)

**India has another version boundary:** canonical NRCeS ABDM pages serve **6.5.0**, based on FHIR 4.0.1 and dated 8 May 2025; `/preview/` serves **7.0.0**, dated 15 July 2026, explicitly a local development build. A 7.0.0 publication path could not be read in this bounded pass. Do not infer that preview is the deployed requirement. The contracting recipient must specify the actual package and profile. [Canonical guide](https://www.nrces.in/ndhm/fhir/r4/), [preview](https://www.nrces.in/preview/ndhm/fhir/r4/index.html)

## 2. What mature tools establish, and the remaining technical branches

HAPI's Instance Validator already checks resource structure, cardinalities, profiles, invariants and terminology using configurable support. The documentation recommends it over the older schema/Schematron route. Raw-string validation can detect defects missed after a forgiving parse; validation resources and terminology support must be present. Its examples distinguish an error for a missing required field from a warning for a code that cannot be validated. [Instance Validator](https://hapifhir.io/hapi-fhir/docs/validation/instance_validator.html) This is strong opposing evidence against selling another generic “FHIR JSON checker.” Native profiles and custom FHIRPath rules should be the first baseline. A semantic check does not automatically require custom AI.

| Branch | Concrete engineering question | Independent check that adds evidence |
|---|---|---|
| Contract and schema | Exact FHIR release, implementation-guide package, canonical URL/version, extensions, `mustSupport`, validator configuration? | Manifest identifies every input; unavailable terminology/checks remain unknown, not pass. |
| Identity | Is a logical resource ID being confused with an identifier assigned by another system? Are two sources using the same local ID? | Explicit synthetic source-to-person crosswalk; no name-based merge; unresolved references quarantined. |
| Codes and units | Is the system/code/version preserved? Does a display string override the code? Does numeric conversion preserve the original quantity? | Owned two-unit arithmetic oracle; retain original fields; unknown or incompatible unit remains unresolved. |
| Time and precision | Are occurrence time, issue time, source update time and ingestion time conflated? Was a month-only date invented into a precise instant? | Expected typed fields and original precision, including offsets and boundary dates. |
| State and provenance | Does replay duplicate records? Does a correction replace the intended version? Does an entered-in-error result remain active downstream? | An event manifest names predecessor/current state independently of payload sorting; retain all source versions. |
| Analytical migration | Is this concept a measurement, observation, condition, or unmapped item? What detail is lost? | Explicit mapping/rejection contract, vocabulary release and field lineage; never map by resource-name resemblance alone. |

The FHIR quantity datatype distinguishes display units from coded units; free-text `unit` cannot simply be assumed to be valid UCUM. Codes depend on their systems, not display labels. [R4 datatypes](https://hl7.org/fhir/R4/datatypes.html) `Observation.effective[x]` concerns the asserted observation time, while resource metadata tracks resource change. [Observation definitions](https://hl7.org/fhir/R4/observation-definitions.html), [resource metadata](https://hl7.org/fhir/R4/resource-definitions.html) Version IDs are **opaque**. Lexicographic or numeric sorting is not a general update policy. Server history support and conflict handling must be negotiated; version-aware operations already exist. [R4 HTTP contract](https://hl7.org/fhir/R4/http.html)

FHIR exchanges resources; OMOP organizes analytical facts with domain and vocabulary conventions. A FHIR `Observation` does not mechanically imply OMOP `OBSERVATION`. The CDM's measurement and observation definitions separate these meanings, and preserve source values alongside standardized concepts. Date choices can depend on the source event being represented. A record can fit SQL types while having the wrong identity, concept, event or unit. [CDM 5.5 field and ETL definitions](https://ohdsi.github.io/CommonDataModel/cdm55.html)

An existing UK baseline also undercuts a generic lineage product claim: **Oxford OMOP Data Mapper** is a documentation-oriented DuckDB ETL tool, and explicitly supports field-level provenance with source, target table/key and column. [Repository, Apache-2.0](https://github.com/tvs-sde/oxford-omop-data-mapper), [provenance design](https://tvs-sde.github.io/oxford-omop-data-mapper/docs/data-provenance.html) The comparison question is whether a small adapter or test fixture improves a supported workflow beyond that existing capability.

## 3. One equipment-light experiment, with a bounded oracle

**Project: R4 synthetic identity and revision reconciliation.** It is a neutral staging/validation exercise with an OMOP rejection/mapping audit, not a complete OMOP ETL. No clinical advice, diagnoses, treatment thresholds, real records or de-identification exercise. One laptop and an already available language runtime suffice for the authored ledger. Running HAPI/DQD would require separately approved existing tooling or a later approved installation; no upstream code was run here.

The public seed is HL7's **R4 4.0.1 `Patient/example`, “General Person Example”**. It is an informative example, not normative truth. [Exact rendered JSON](https://hl7.org/fhir/R4/patient-example.json.html) The FHIR specification is CC0 with trademark restrictions and separate third-party terminology rights; its own terms place clinical/operational fitness on the user. [Rights and scope](https://hl7.org/fhir/R4/license.html) Use a tiny derivative retaining only the structural pattern, replacing identifiers with conspicuously synthetic `example.org` namespaces and removing names, addresses, contacts and narrative. No third-party medical terminology is needed. Publishable owned fixtures could be CC0 after the author explicitly chooses that licence; this report does not license future work on their behalf.

Design exactly **eight snapshots**: two distinct synthetic Patient records in two source namespaces, plus two synthetic Observation streams with three revisions each. The custom observation code means “nonclinical demonstration signal,” and local test units mean only two explicitly defined numerical scales. These are schema vehicles, with no claim to clinically standardized concepts. A local CodeSystem/profile can declare those meanings. Do not pretend a local unit is UCUM. Keep these observations out of a conformant OMOP clinical fact table: the expected report says “no approved standard/domain mapping.” This refusal is a positive correctness outcome.

Define **24 named cases before implementation**: 8 valid transformations/replays; 4 structural/profile defects; 4 identity/reference mismatches; 4 unit/code/precision defects; 4 revision/state defects. Each has an input fingerprint, expected verdict, exact expected output fields or quarantine reason, and no implicit clinical inference. Case denominators stay fixed. A second person can author/review the expected table later; until then this is an authored independent specification, not independently human-validated ground truth. A frozen hidden set of 8 additional permutations is for transfer, separate from the 24 development cases.

**30 days, 25–40 focused hours within the existing project budget:**

1. Spend 5–8h on the version/rights manifest and expected-case table. Specify source IDs, logical IDs, identifier namespace/value, code/system, original and converted number/unit, effective precision, issued/update/ingestion time, state and transformation revision. Declare replay, conflict and loss rules before writing mapping code.
2. Spend 10–15h on a tiny deterministic normalizer and append-only provenance ledger using an already available runtime. Compare with a simple explicit field-map/SQL projection. No network service, patient-facing UI or LLM is necessary.
3. Spend 5–8h on baseline design and manual inspection: (A) native parser/profile validator, (B) native validator plus the same applicable custom profile constraints, (C) explicit mapping plus independently written expected states. If HAPI cannot be run without a new install, mark its results **not run**, retain a runnable specification, and do not claim comparative success.
4. Spend 5–9h measuring case-level outcomes, authoring/debugging minutes and minimal repair effort. Require all 8 valid cases accepted, all declared defects detected or explicitly unresolved, zero wrong-person merges, zero silently invented precision, and idempotent replay. These are fixture acceptance criteria, not population error estimates.

**90 days, an additional 50–80h only if the first stage is useful:** add the 8 withheld permutations and an altered source schema/profile; compare approved native custom constraints with adapter checks; create source-to-target field lineage and a CDM 5.5 migration diff specification. Test duplicate resource IDs across sources, opaque nonnumeric version IDs, out-of-order arrivals, revisions with the same observation time, cancelled/error states, absent versus zero values, unknown units, timezone boundary crossings and partial dates. Preserve both raw and interpreted values. Have an appropriate domain reviewer challenge the *proposed mapping contract* before any future clinical mapping; synthetic arithmetic is insufficient expertise for medical concept mapping.

If approved tools later exist, the full OMOP branch should use real DDL/vocabulary contracts and DQD with disclosed checks, exclusions, thresholds and statuses. The tiny neutral ledger cannot be called OMOP-conformant and cannot meaningfully obtain a full DQD pass percentage. HAPI and related reference-validator wrappers may share machinery: agreement is corroboration of configuration, not two independent truths.

Report the complete 24/8 case matrices, pass/fail/unknown/not-run, active and total time, fixture count, per-field loss, unsupported mappings, repair rounds and existing native-rule coverage. Do not use generation aesthetics, synthetic throughput or a single green percentage as the outcome. Fixed handwritten cases are not random samples; even 0 failures yields no defensible real-hospital reliability estimate.

**Kill criteria:** stop custom-product work if native profile rules plus ordinary SQL solve the declared cases with comparable setup/repair effort; if expected meaning cannot be specified without clinical expertise or inaccessible terminologies; if the proof needs real patient data to appear useful; or if no public workflow can be reproduced. A useful fixture/documentation contribution remains a valid result. The report has established neither a buyer's pain nor willingness to pay. No outreach or patient-system pilot is authorized by this design.

## 5. Implications for 2031 and what remains unproved

Inference: this is a credible **domain integration option** for someone with backend/API, database, testing and operational skills. AI can draft maps, profile constraints, documentation and edge-case candidates. Native servers can absorb much routine protocol work. The transferable depth is diagnosing ambiguous source meaning, choosing explicit loss/state policy, building independently checkable reconciliations, and measuring maintenance burden across versions. None of that proves the work is permanently immune to automation.

An attainable leadership path is adapter/fixture contributor → owner of a reproducible migration or quality contract → reviewer coordinating developers, data stewards and clinical/domain experts. Original contribution might be a well-minimized native-tool defect, a portable regression fixture, a documented version mismatch, or a check with defensible denominators. It must survive existing-tool comparison and maintainer review; a demo repository alone establishes neither originality nor community authority.

Remaining bounded gaps: exact released HAPI runtime/package pin; independent review of the synthetic oracle; NRCeS 7.0.0 publication/deployment status; per-organization mapping and terminology rights; current India/UK vacancies and actual eligibility; authorized clinical data/workflow access; all-in integration/repair effort versus incumbent engines; and a funded customer's measurable requirement. No paid demand, compliance, cryptographic/privacy assurance, clinical correctness, treatment benefit or production readiness has been established.

Evidence status: primary official pages and artifact metadata were inspected, with indexed-only job evidence labeled. No benchmark was executed. Reader failures were retained rather than retried through downloads or login. All additions in the companion JSON are proposals for root deduplication; shared catalogs and prior reports remain unchanged.
