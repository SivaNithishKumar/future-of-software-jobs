# Supply-chain evidence option: bind the claim to the artifact and authority

Prepared 20 October 2026; main evidence cutoff 19 October 2026. Existing security, systems and funded-maintenance notes were read first. They cover identity, generic provenance and funding, without this source-to-artifact binding depth. Proposed child: `darkside2031.security.agent-security.assurance`. No signing keys, accounts, releases, CI runs/publication, packages, software downloads/installations, upstream execution, private repositories/systems or outreach.

The narrow question is: **does a verification result refer to these exact bytes, the expected source revision and builder, the applicable release authority, and the correct supporting evidence?** A valid signature or schema is one part of that chain. Mature tools already enforce many of these checks. The useful depth is specifying, testing and maintaining the remaining policy and evidence boundaries, rather than selling another attestation badge.

## 1. Three standards/native artifact families

### SLSA and in-toto: know which statement is being verified

The official specification entry currently redirects to **SLSA 1.2**, marked approved, with distinct Build and Source tracks. Its specification licence is **Community Specification License 1.0**. This report does not assign an unverified release date. [Current specification](https://slsa.dev/spec/v1.2/)

Do not conflate that specification version with the build predicate URI **`https://slsa.dev/provenance/v1`**, or with **`https://in-toto.io/Statement/v1`**. The in-toto statement identifies subjects by digest and identifies the kind of predicate; filenames are contextual metadata. Its repository licence is Apache-2.0. [Statement contract](https://raw.githubusercontent.com/in-toto/attestation/main/spec/v1/statement.md), [rights](https://raw.githubusercontent.com/in-toto/attestation/main/LICENSE) Those live source files are schema-version references, not immutable commit-pinned runtime code.

SLSA verification explicitly compares artifact digest, recognized builder/signature, expected source/build type and externally supplied parameters. A builder's claimed level is not sufficient without a configured trust relationship. Its guidance recommends rejecting unexpected external parameters; that does not mean rejecting every unknown extension anywhere in the document. [Verification policy](https://slsa.dev/spec/v1.2/verifying-artifacts) The build-provenance schema makes resolved-dependency completeness **best effort through Build L3**. It distinguishes externally controlled parameters from trusted builder internals. Complete inventory and reproducibility cannot be inferred merely from finding this predicate. [Build provenance](https://slsa.dev/spec/v1.2/build-provenance)

### Sigstore/Cosign and GitHub: a serious native verifier baseline

The inspected Cosign catalog marks **v3.1.3**, commit `11926fa`, as latest; listed release-asset timestamps are **6 August 2026**. Code is Apache-2.0. [Release](https://github.com/sigstore/cosign/releases), [tagged rights](https://github.com/sigstore/cosign/blob/v3.1.3/LICENSE) Its official advisory documents a legacy-bundle identity-enforcement bypass, patched in **3.1.3/2.6.5**; the modern protobuf bundle path is described as unaffected. This is a version/format boundary, not a reproduced exploit or a claim that patched code is universally secure. [Maintainer advisory](https://github.com/sigstore/cosign/security/advisories/GHSA-fx35-mq7g-6g98)

Cosign already supports expected certificate identity/issuer and artifact-digest checking. Some modes deliberately disable claim checks; do not silently weaken that baseline. [Verification documentation](https://docs.sigstore.dev/cosign/verifying/verify/) Parts of that live page still discuss a “coming soon” bundle format; use the selected release's actual behavior in a later reproduction, rather than treating every documentation example as an executed compatibility test.

GitHub's native attestation verifier already supports repository/owner scope, reusable signer-workflow and source-ref/digest constraints, predicate type and self-hosted-runner policy. It accepts on-disk bundles for offline verification. Crucially, its manual distinguishes certificate/timestamp evidence from workflow-controlled predicate metadata: the latter can be falsified if that workflow context is compromised. The reusable workflow's signer identity needs the appropriate constraint. [Native verifier contract](https://cli.github.com/manual/gh_attestation_verify) The GitHub CLI binary/version was not inspected or run. Cosign and GitHub's paths can share Sigstore machinery, so agreement is not automatically independent cryptographic validation.

GitHub itself says generation needs verification, and that attestations do not establish artifact security. Public and private repositories use different Sigstore deployment/transparency arrangements. The observed feature is an incumbent baseline, not a reason to presume an account has every permission or to turn on CI. [Platform scope](https://docs.github.com/en/actions/concepts/security/artifact-attestations)

### CycloneDX SBOM/VEX: bind inventory and vulnerability assertions correctly

The official overview names **CycloneDX 1.7**, released **21 October 2025**, with an ECMA publication date **10 December 2025**. The inspected schema repository exposes patch tag **1.7.2**, commit `349314a`; that tag does not change a JSON document's `specVersion` into `1.7.2`. The repository's tagged licence is Apache-2.0. [Overview](https://cyclonedx.org/specification/overview/), [schema tag](https://github.com/CycloneDX/specification/releases/tag/1.7.2), [rights](https://github.com/CycloneDX/specification/blob/1.7.2/LICENSE)

**CycloneDX CLI v0.33.1**, commit `b3cfa4b`, is the inspected native baseline. Its tagged README supports explicit 1.7 validation and a failure exit-code option; it also provides diff/merge/conversion. Code is Apache-2.0, with .NET/runtime/platform requirements. These capabilities already oppose a generic custom SBOM validator. [Tagged tool documentation](https://raw.githubusercontent.com/CycloneDX/cyclonedx-cli/v0.33.1/README.md) The release notes fix lost vulnerability **`affects.ref`** bindings during hierarchical merges. That is a concrete reason to test component identity after transformations. The reader displayed a 23 July timestamp without a year; no calendar year is assigned here. [Tool release](https://github.com/CycloneDX/cyclonedx-cli/releases/tag/v0.33.1)

VEX communicates vulnerability applicability in a particular context. The tagged 1.7 schema includes analysis state and justification; its `not_affected` description recommends justification. That is not a schema-enforced proof of non-exploitability. [VEX purpose](https://cyclonedx.org/capabilities/vex/), [tagged schema](https://raw.githubusercontent.com/CycloneDX/specification/1.7.2/schema/bom-1.7.schema.json) A component reference, product/artifact identity, analysis authority, relevant environment and evidence revision must agree before consuming a suppression. An empty findings array can mean “no known finding in this scan scope/database snapshot”; it cannot establish the absence of vulnerabilities.

## 2. The recursively useful technical branches

| Branch | Specific knowledge and failure question | Defensible acceptance evidence |
|---|---|---|
| Artifact identity | Digest algorithm, exact bytes, archive/container layers, filenames versus immutable identity | Recompute the subject digest; distinguish a rebuilt artifact with the same name/version; record which object was hashed. |
| Source/build binding | Source repository/revision, build type, parameters, reusable workflow and builder mode | Compare expected revision and actual authenticated signer; user-controlled `builder.id` or `releaseApproved` text cannot substitute for authority. |
| Permission and trust | OIDC issuer, signer identity, trust roots, builder admission, role separation, target environment | Independent policy says who may assert which claim; unknown trust material remains unknown. A trusted build can still build unwanted code. |
| Evidence graph | Artifact → provenance → SBOM subject/components → vulnerability report/context | References and digests survive diff/merge/update; each accepted conclusion names its evidence, scope and revision. |
| Time and update | Signing/timestamp context, policy revision, revocation/rotation, new artifact or new vulnerability knowledge | Re-evaluate under the intended policy and information cutoff; do not reject all old signatures solely because a short-lived certificate has since expired. |
| Assurance and operations | Missing, malformed, stale, conflicting and unauthorized evidence; release/exception process | Fail/unknown reasons, explicit exceptions, reproducible diagnostics and repair effort; no silent pass for an unrun check. |

These are engineering requirements for the proposed test, not an invented new standard. A signature verifies an assertion under a trust model; it does not establish code quality, dependency safety, authorization for every environment, inventory completeness or the truth of a workflow's arbitrary text. Conversely, native builders/verifiers may satisfy nearly all the required policy. That result should reduce custom scope.

CRA is not needed to answer this binding question. Existing security notes retain their qualified timeline/scope audit; this pass adds no universal SBOM duty, legal interpretation or compliance certification.

## 3. One tiny synthetic manifest/oracle project

**Project: claim-to-artifact policy reconciliation, with native verification as a separate gate.** Two owned plaintext strings represent artifacts; three conspicuously synthetic component records, one source revision and two build identities use `example.org`. A small SLSA-shaped statement, CycloneDX 1.7-shaped BOM/VEX and policy/evidence manifest describe them. Use a fictional `TEST-VULN-001`, never a claim about an actual package. No executable software, release, key, signature, account, registry upload or real vulnerability scan is needed for this first stage.

The fixtures are authored test data, not captured public bundles and not yet certified as conforming to the standards. Rights for future publication need an explicit author-selected licence; the report does not assign one. Public specifications/tool docs above define the comparison contracts. A future genuine verifier test requires separately approved local tools and permitted existing bundles/trust material; it does not require new signing keys or publishing a release.

Freeze **24 development cases** before implementation: 4 valid policy matches under explicit authenticated-fact assumptions; 4 byte/subject/BOM-binding mismatches; 4 signer/issuer/source/permission mismatches; 4 build/predicate/parameter scope mismatches; 4 vulnerability-reference/context/evidence failures; 4 missing/update/trust-policy cases. Hold out8 changed combinations. Expected outcomes come from a separately authored table of exact fields, allowed authorities, policy version and evidence freshness rules, not from the candidate evaluator or an LLM judge. An independent human review is still a gap.

Keep two outputs separate: **(1) native cryptographic/schema verification status; (2) application policy/evidence match.** All synthetic-only cases have native verification **NOT_RUN**. A matching mock case is labelled `POLICY_MATCH_ASSUMING_AUTHENTICATED_FACTS`, never “verified release.” Mock identity/trust/approval fields belong only to the trusted test harness and must never be accepted from an unsigned supplied manifest. Do not implement new cryptography or accept a producer's self-reported pass as native evidence.

**30 days, 25–40 focused hours within existing project hours:**

1. Spend 5–8h writing the oracle and manifest: artifact byte hashes; source/workflow revisions; expected issuer, signer and builder; predicate/build type; allowed parameters; SBOM/component references; fictional scan scope/database revision; policy authority and version; exact unknown/rejection reasons.
2. Spend 10–15h on an owned field-binding adapter in an already available runtime. Compare naive filename/version matching and predicate self-claims with explicit digest/reference/authority matching. Preserve negative controls and distinguish extra metadata allowed by a schema from unexpected security-relevant build parameters.
3. Spend 5–8h specifying native baselines: pinned Cosign identity/issuer plus subject verification, GitHub's precise source/signer constraints where applicable, and tagged CycloneDX CLI validation/diff/merge. These are **not run** unless approved tooling and permitted bundles are available. A custom comparison cannot claim to outperform them without the matched test.
4. Spend 5–9h on all 24 verdicts, errors and repair effort. Require zero silently accepted wrong-artifact or unauthorized-identity cases under the oracle, preserved reference bindings, explicit unknown for unavailable trust/evidence, and no promotion of mock matches into real verification. Record active/total authoring, diagnosis, repair and review time.

**90 days, another 50–80h only if justified:** use the 8 withheld cases and a changed policy/version. Add multi-subject ambiguity, changed source at the same ref, reusable workflow migration, different authorized builder mode, offline trust-material refresh, SBOM merge/diff, and a fictional new vulnerability assessment invalidating an earlier conclusion. Legitimate old artifacts and approved exceptions are positive controls; universal age rejection is not correctness.

The later approved native gate should use existing permitted artifact/bundle pairs and exact tool/trust/schema versions. It can test wrong bytes, expected identity/source, unavailable trust roots and parser/format rejection without signing anything. Malformed fixture rejection or a simulated timestamp cannot reproduce the real certificate, transparency or advisory behavior. Real platform permissions, issuer claims, release authority and CI isolation require their own authorized environment; they remain untested here.

Metrics: full case-level match/reject/unknown/not-run matrices; false acceptance and false rejection relative to this fixed oracle; unmatched references; unsupported schema/bundle versions; native versus additional-policy coverage; diagnostic/repair rounds; actual active/total time. These fixed adversarial cases do not estimate field prevalence or real incident reduction. Record failed attempts and dependency/coordination costs, not just the number of generated attestations.

**Stop criteria:** native verifier flags plus existing BOM tooling cover the cases with comparable effort; the oracle cannot distinguish a security-relevant mismatch from permitted variation; the proposal requires private access or signing to look useful; or it merely repackages generated documents as assurance. A minimal regression fixture, version-migration note or clearer native error is a valid contribution. A standalone product needs demonstrated buyer workflow, operational acceptance and cost evidence; none is established.

### What actually ran in this pass

Eight owned Python-standard-library hash/field-policy illustrations ran and were saved in `supply-chain-evidence-option-round14-fixtures.json`. They cover one matching mock, changed bytes under the same label, untrusted signer, wrong source commit, wrong-artifact SBOM, predicate approval contradicted by harness authority, wrong-component VEX and missing trust material. All 8 authored expected-result assertions passed. SHA256: `cd8fdd449c9a0d8df372b70bfc265eb33af51bf1a57cc48f5934f3a73b4d5066`.

Every case records cryptographic verification and native schema validation as **NOT_RUN**. No real certificate, signature, SBOM completeness, vulnerability exploitability, release authority, SLSA level or native-tool defect was established. This is an arithmetic/field-binding illustration, not the 24-case proposed benchmark or an independent security audit.

## 5. 2031 interpretation and boundaries

Inference: this is an adjacent platform/security depth path for a developer who can reason about source/build identities, typed evidence, policy, release operations and failure diagnostics. AI can generate manifests, map fields, draft policies and automate triage; native platforms already generate and verify attestations. Evidence ownership may matter more as automated code production expands, but its net effect on headcount is not established.

An original contribution should expose a real remaining mismatch at matched native configuration: a minimized reference-loss case, a clearer verifier failure, a supported format-migration test, or a policy that prevents a concrete wrong-artifact/authority decision without obstructing legitimate updates. Leadership evidence is adoption, review and maintainable release policy across teams; a badge, signed file or long SBOM is not that evidence.

Remaining gaps: immutable source/runtime/trust-root pins; the actual GitHub CLI version and account permissions; matched native verifier/schema runs; independent oracle review; complete inventory ground truth; authentic vulnerability/context evidence; current candidate eligibility and real customer acceptance/cost. Large rendered CycloneDX JSON docs exceeded the reader limit; a bounded tagged raw-schema section was inspected instead, without retrieving/installing the full tooling. No shared catalog or earlier report was edited, and no compliance, production safety, scarcity or standalone moat claim follows.
