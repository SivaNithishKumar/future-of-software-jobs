## Audit judgments and acceptance boundaries

The following are this worker's method judgments and replication gates, rather than new benchmark measurements.

| Question | Judgment or gate |
|---|---|
| What is the unit? | Treat one release-transition repository patch as one task. Do not count its files, tests, PR bodies or agent turns as independently completed maintenance requests. A large change can be valuable without measuring elapsed unattended work. |
| Do changes depend on earlier agent changes? | A claim about sustained maintenance needs later requests to start from the actor's actual earlier output, retaining unresolved debt and state. Resetting to a maintainer's starting snapshot estimates a different problem. The present audit establishes no multi-release survival rate. |
| What information is supplied? | Freeze the release-note-only versus linked-context arm and the exact texts. Separate supplied retrospective context from live clarification, negotiation or discovery of unstated requirements. Do not call enrichment itself leakage without checking its declared treatment role. |
| Are tests hidden? | Actor/grader filesystem, timing and access boundaries must be inspected before calling the tests hidden or independent. The three inspected endpoints did not resolve that boundary. Public dataset field names alone do not answer it. |
| Is new utility required? | Report preservation and requested-change correctness separately. A no-op can preserve everything while delivering no new utility; a patch can satisfy a new example while breaking old consumers. A legitimate specified breaking change also needs an explicit old-contract retirement rule. |
| Which attempts count? | Require a manifest of every selected task, run, missing patch, timeout, budget stop, infrastructure error, retry and later repair. A README's one-run example does not authenticate the paper's complete run/retry policy. Do not silently remove invalid or unfinished attempts. |
| What is matched? | A turn cap is not a common token, compute, elapsed-time or money budget. Native evaluator/reference validation, no-op preservation, actor scaffolds and an external leaderboard are different baselines. A cross-benchmark same-model number does not isolate a causal task-size effect. |
| What was selected? | Generalisation should use repository-held-out or fresh-version cases and report within-repository dependence. An execution-stable curated set does not measure environment recovery or all software work. Do not turn curated difficulty into measured developer hours. |
| What contamination is excluded? | Blocking online retrieval does not by itself rule out pretraining exposure to public release history, known patches or seed benchmarks. Require dated manifest/cutoff and fresh held-out evidence for that stronger claim; exposure was not measured here. |
| Is the full job complete? | Add maintainability, legitimate requirement acceptance, useful integration, security/permission and repair checks only when independently defined. Test score and self-labelled failure causes cannot alone certify those outcomes. |
| Are aggregate rankings ready? | Reconcile the headline/table disagreement and obtain denominator-matched raw result/version manifests first. Do not silently correct the table, infer fraud, or erase the useful task construction because of one unresolved reporting join. |

This preserves the benchmark's positive contribution: a whole release can expose coordination and regression failures that isolated patches miss. It also leaves room for agents or native platforms to improve rapidly. None of these gates establishes permanent human scarcity, a current frontier ceiling, a developer-hour multiplier, headcount or wages.

One additional denominator check is purely arithmetic: no integer solved count out of48 rounds to the printed23.40% DeepSeek-v3p2/SWE-agent result in Table2. Eleven out of47 is one compatible fraction, but this audit has not observed that denominator or any exclusion. Averaging repeats or a reporting/version difference could also explain it. Obtain the exact run-level denominator before treating every table entry as a single48-attempt result; do not silently repair the score or declare a missing attempt.

## One clarification to an existing project

The existing target is `ai-ml-round5.project.evaluation` at `/records/146` of the unchanged `ai-ml-enrichment-round5.json`, with its adversarial scorer pilot, independent expected outcomes, held-out follow-up and existing resource/permission gates. `software.md` ExperimentB supplies an existing local synthetic state-changing workflow context. This proposal substitutes one version/change-regression probe within that chosen artifact; it creates no new project, hours, model campaign or claim of long-horizon mastery.

At the existing first-stage scorer pilot, freeze a tiny versioned requirement ledger and actor-visible versus untouched holdout evidence. Use an unchanged deterministic workflow as a native baseline, a correct implementation/reference as an oracle check, and planted bad outputs: no-op, new feature that breaks an old required consumer, stale-format replay, suppressed failure, and a valid specified change wrongly rejected by obsolete tests. Expected outcomes must precede the candidate implementation. Report uncertain requirements separately; a grader that shares the actor's answer table is not an independent oracle.

At the existing later follow-up, apply an unseen change to the actual chosen first implementation and retained state. Do not quietly reset it to gold. Distinguish this chained-version local mechanism test from SWE-EVO replication and from production maintenance. A no-model fixture arm can test the scorer; a future actor comparison needs separately available, approved resources and matched complete budgets. Native unchanged tooling may already implement the requirement and must remain a positive comparison.

The denominator is all eligible version-change cases, not tests or selected successes. Report first-attempt full acceptance, requested utility delivered, retained required behaviour, accepted-incorrect/rejected-correct counts, failed/unfinished attempts and repair/rollback effects. If later executed, log actual setup, context construction, tool/compute, human review and repairs; never infer them from patch length or benchmark score. Keep version IDs, content hashes, explicit superseded contracts and reasoned indeterminate states. Without real independent utility labels, limit the result to contract consistency.

Stop a superiority claim if native tooling already meets the same contract, the oracle accepts a planted serious fault, obsolete tests reject a legitimate change, gains disappear under equal total budget, or failures are discarded. Stronger fresh-version agents succeeding on this same bounded contract would falsify a local persistent-maintenance weakness; agents synthesising adequate tests/context cheaply would weaken a bespoke verification moat. Successful local fixtures still do not establish employment demand or broad reliability.
