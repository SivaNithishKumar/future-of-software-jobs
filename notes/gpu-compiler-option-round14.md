## Finding and boundary

GPU/compiler work is a defensible specialism to test through numerical contracts, systems diagnosis and workload integration. A generated kernel's accepted samples and device-event speed do not establish a generally correct operator, application savings or hiring readiness. Current frameworks already automate substantial code generation and tuning. The five-year hypothesis is therefore conditional: valuable work may involve unusual operations, numerical/shape regressions, new backends and maintained compiler/runtime integration. The evidence here cannot estimate future headcount or scarcity.

The source audit also weakens blanket criticism of available benchmarks. Current KernelBench has precision-specific tolerances, randomized trials, compiled-PyTorch comparisons and adversarial tests. Triton's tutorial includes native torch.softmax. Reuse those controls before proposing another harness.

## Three primary artifact groups

**1. KernelBench, checked main at 423217d9fda91e0c2d67e4a43bf62f96f6d104f1.** This is an immutable observation of current HEAD, not the paper's environment or a release-qualified reproduction. [README](https://github.com/ScalingIntelligence/KernelBench/blob/423217d9fda91e0c2d67e4a43bf62f96f6d104f1/README.md#L36-L61) defines fast_p over tasks passing correctness and the speed threshold; failed/unsupported/OOM cases cannot silently disappear from a declared task denominator. The local [single-sample runner](https://github.com/ScalingIntelligence/KernelBench/blob/423217d9fda91e0c2d67e4a43bf62f96f6d104f1/scripts/run_and_check.py#L106-L121) defaults to five correctness trials and 100 performance trials; the lower-level [evaluation function](https://github.com/ScalingIntelligence/KernelBench/blob/423217d9fda91e0c2d67e4a43bf62f96f6d104f1/src/kernelbench/eval.py#L394-L413) defaults to one and ten. Report the actual invocation, not an assumed universal setting.

The [correctness path](https://github.com/ScalingIntelligence/KernelBench/blob/423217d9fda91e0c2d67e4a43bf62f96f6d104f1/src/kernelbench/eval.py#L750-L815) repeatedly calls each task's get_inputs, checks shape, then allclose. [Current tolerances](https://github.com/ScalingIntelligence/KernelBench/blob/423217d9fda91e0c2d67e4a43bf62f96f6d104f1/src/kernelbench/eval.py#L83-L102) are 1e-4 for fp32 and 1e-2 for fp16/bf16, used as both absolute and relative tolerances. A nearby comment explicitly distinguishes the older fp32 1e-2 setting. Randomized values do not necessarily vary task-defined shape, stride or distribution.

A narrow static counterexample remains at this pin. [Task23](https://github.com/ScalingIntelligence/KernelBench/blob/423217d9fda91e0c2d67e4a43bf62f96f6d104f1/KernelBench/level1/23_Softmax.py#L21-L28) applies row softmax to torch.rand(4096,393216). For inputs in [0,1), every mathematical probability is below e/393216 = 6.91294817214723e-6. A same-shape all-zero output consequently satisfies the 1e-4 absolute allclose predicate, while losing the entire unit row mass. This is an analytic counterexample to that numerical predicate, not an executed candidate, exploit, complete-harness bypass or an empirical statement about other tasks. The bound has margin relative to ordinary float32 rounding, but no specific device reference was run. Conversely, row-sum alone accepts the wrong uniform vector: logits [0,log(3)] require [.25,.75], whereas [.5,.5] sums to one. The project needs both a reference and appropriate invariants.

The task has 1,610,612,736 elements: float32 input alone is exactly 6 GiB; input plus output is 12 GiB before references, temporary allocations, compiler and cache controls. Reducing its shape creates a different workload and must be labelled accordingly.

The [runner](https://github.com/ScalingIntelligence/KernelBench/blob/423217d9fda91e0c2d67e4a43bf62f96f6d104f1/scripts/run_and_check.py#L314-L338) measures eager and torch.compile references. The [reference timer](https://github.com/ScalingIntelligence/KernelBench/blob/423217d9fda91e0c2d67e4a43bf62f96f6d104f1/src/kernelbench/timing.py#L75-L102) compiles lazily and excludes compilation through warmup. Its [CUDA-event path](https://github.com/ScalingIntelligence/KernelBench/blob/423217d9fda91e0c2d67e4a43bf62f96f6d104f1/src/kernelbench/timing.py#L201-L281) measures current-stream event intervals after cache thrashing; it is not host elapsed time. The thrash allocation is 256 MiB, outside the event interval. Its Triton wrapper ignores trial-count arguments and uses adaptive 25 ms warmup /100 ms repetition budgets. Separate [host timing](https://github.com/ScalingIntelligence/KernelBench/blob/423217d9fda91e0c2d67e4a43bf62f96f6d104f1/src/kernelbench/timing.py#L433-L447) exists. The [speedup heuristic](https://github.com/ScalingIntelligence/KernelBench/blob/423217d9fda91e0c2d67e4a43bf62f96f6d104f1/src/kernelbench/eval.py#L650-L699) flags a result in metadata and warns; it does not prove correctness. [EVAL.md](https://github.com/ScalingIntelligence/KernelBench/blob/423217d9fda91e0c2d67e4a43bf62f96f6d104f1/EVAL.md#L35-L51) documents timing and adversarial checks, including reference reuse, mutation and non-default streams. Their existence prevents a claim that the whole repository lacks such defenses. Source reading did not establish every backend/stream path safe.

**2. The Correctness Illusion in LLM-Generated GPU Kernels**, Dipankar Sarkar, arXiv:2606.20128v2, revised 21 July 2026; preprint, CC-BY4.0. [Methods and limitations](https://arxiv.org/html/2606.20128v2) use author-seeded transcription defects, not a sampled deployed-LLM error rate: the expanded controlled corpus has 16 controls and ten defective variants, including CPU stand-ins. The author reports consistent verdicts across five GPU classes. The fp64 CPU reference is rounded to the target dtype, not guaranteed identical to a library contract. Client decoding makes stride variation nominal; bf16 tests proxy fp16. No independent replication was performed here. Thus this is prior art for boundary testing, not proof of general GPU validation.

The [corpus README at checked HEAD](https://github.com/sarkar-dipankar/gpuemu-corpus/blob/2f15310368118ddd8c76887675f8c6c0f76a0989/README.md) declares MIT OR Apache-2.0, but the inspected root listing has no standalone licence file; actual reuse needs its terms resolved. Its suggested P1 run ID differs from paper section4's primary run ID. This is an unresolved version/data join, not proof either result is false. Stored runs, kernels and daemon were not downloaded. The source snapshot is not paper-matched. Its existing strategy and tolerance tooling also means a general “add fuzzing” proposal is not novel.

**3. Triton tutorial/testing and PyTorch's native compiler controls.** Triton checked main is 2122e24efc1886bfa36337c1f5b07c47d827b1d4; MIT text inspected. The [fused-softmax tutorial](https://github.com/triton-lang/triton/blob/2122e24efc1886bfa36337c1f5b07c47d827b1d4/python/tutorials/02-fused-softmax.py#L85-L109) uses negative-infinity tail masking and approximate exponentiation. Its address expression accepts row stride but assumes contiguous columns; transposed-column input is not covered merely because a Python tensor carries strides. The demonstration checks one irregular shape; the [benchmark](https://github.com/triton-lang/triton/blob/2122e24efc1886bfa36337c1f5b07c47d827b1d4/python/tutorials/02-fused-softmax.py#L185-L234) compares native torch.softmax as well as naive decomposition. Its theoretical memory-traffic ratio is not an independently measured speedup here.

[Triton do_bench](https://github.com/triton-lang/triton/blob/2122e24efc1886bfa36337c1f5b07c47d827b1d4/python/triton/testing.py#L288-L358) runs once, synchronizes, estimates duration, warms and clears cache before timed device-event calls. The actual repetition count adapts to timing. [CUDA-graph timing](https://github.com/triton-lang/triton/blob/2122e24efc1886bfa36337c1f5b07c47d827b1d4/python/triton/testing.py#L140-L207) measures repeated graph replay, a different boundary from a regular host request. Never silently combine those results.

PyTorch checked main e5e5dde90b4f696a31eab48f686084b307a657dc is also a source observation, not a tested compatible runtime. Its [mode mapping](https://github.com/pytorch/pytorch/blob/e5e5dde90b4f696a31eab48f686084b307a657dc/torch/_inductor/__init__.py#L368-L408) exposes default, max-autotune, graph-enabled and no-cudagraph variants. A fair comparison chooses modes explicitly rather than crediting a custom kernel with native compiler optimizations omitted from the baseline. The [Helion announcement](https://pytorch.org/blog/helion/), dated 22 October 2025 with a 23 October update, describes automated indexing/configuration search and generated Triton through Inductor. It reports comparisons against max-autotune and hand-written kernels on named devices. This is platform-authored evidence of bundling; its performance claims were not reproduced or adopted as portable gains. Search time remains a cost. [KernelBench's integration section](https://github.com/ScalingIntelligence/KernelBench/blob/423217d9fda91e0c2d67e4a43bf62f96f6d104f1/README.md#L159-L176) also describes iterative generation with correctness/runtime feedback and a cloud-evaluation RL integration. Those are existing automation mechanisms, not evidence that every kernel problem is solved or that specialist employment grows.

## One project: a bounded softmax contract and measurement ledger

Proposed project gpu-round14.project.softmax-contract. This is a learning/contribution experiment, not a new benchmark suite or originality claim. Start with a single forward row-wise stable softmax, finite float32 inputs, contiguous columns, and explicitly bounded row length. No gradients, attention, arbitrary layouts, nonfinite policy or quantized dtype are implied. Reject unsupported inputs or use the pinned native fallback; never accept them accidentally.

The **first 30–50 focused hours**, a planning assumption, comprise contract/reference (8–12), boundary/counterexample pack (8–12), source trace plus measurement specification (8–14), and an independent fresh-task review/evidence memo (6–12). An existing Python standard-library environment is enough to prepare a tiny stable reference using max subtraction, exp and fsum. Arithmetic here is binary64 host work; float32 rounding, GPU reductions, approximate exp, races and device memory are separate gates. No package is needed for the conceptual fallback.

Use known nonuniform vectors, identical-logit rows, dominant logits and close logits, then positive and negative finite ranges. Predeclare the valid numeric domain and error budget before observing a candidate. A proposed restricted-domain numerical gate is max absolute error <=1e-6 and relative error <=1e-4 where reference probability >=1e-6, together with finite outputs, nonnegativity and row-mass error <=1e-5. These are project choices requiring confirmation against the selected native float32 implementation before launch; if its expected roundoff violates them, revise the declared contract and rerun every arm, rather than relax only a failing candidate. The paper's fp16/bf16 tolerances must not be copied into a float32 project.

The independent reference must include more than the candidate's own tests. A separate reviewer should specify unseen shape/value cases and expected results before learner access. Public illustrations could include column lengths around powers of two and 781; the actual hidden selection must not be those already disclosed here. If no independent setter is available, publish an exposed regression study and withhold an unseen-generalization claim. Deliberate owned faults should demonstrate that zero output, wrong uniform output, a bad tail mask and omitted max subtraction are rejected where their distinguishing conditions apply. A hand-authored fault suite establishes only those detections.

CPU-only acceptance: document and replay a tiny host contract, check independently specified examples, distinguish unsupported inputs, and reproduce the source/arithmetic findings. It does not certify CUDA, Triton semantics, float32 device accuracy, real speed, concurrency or memory safety. Without approved GPU access, finish this useful smaller artifact and retain performance as untested.

The **next 90–150 focused hours** are conditional: approved runtime/pin/baseline reproduction (20–30), operator/boundary and failure testing (25–40), measurement/cost comparisons (25–45), and independent review/reproduction plus contribution memo (20–35). Hardware access and software installs require the user's explicit approval. A compatible CUDA stack and NVIDIA device are not implied by a Mac/MPS laptop. Record exact GPU model/memory, driver, CUDA, PyTorch/Triton versions, target architecture, compiler flags, selected stream, graph/cache policy and contention/power state. Checked HEAD sources are not automatically compatible choices. Keep the tiny workload well below an agreed memory budget; do not run the 6 GiB-input task by default.

Use eager native torch.softmax, Inductor default, a justified max-autotune configuration with graph policy declared, and the pinned hand-written Triton tutorial when its contract fits. Naive decomposition is illustrative only. Confirm native reference agreement and report max/error quantiles plus failing cases, output dtype/shape, input mutation, unexpected allocation, OOM/compile failures and timeouts. Reuse mature adversarial/sanitizer tools only after separately approved setup; a clean finite test pack is not a proof of memory safety.

Report cold preparation/compilation, first useful invocation, warm event intervals, synchronized host requests and graph replay separately. Interleave/reference candidate orders and use identical cache policies. An illustrative performance gate is a paired 95% confidence interval for speed ratio entirely above 1.10 on the preregistered target shape group, with every correctness gate passing and no hidden failure exclusions. The resampling unit must respect grouped/time-correlated trials; raw iterations cannot be treated as independent GPUs or workloads. This is a project decision threshold, not an industry standard. If noise prevents it, call the gain unresolved.

Also report generation/search/failed-compilation/validation/device time, developer review and peak memory per accepted operator. If no AI generator is used, its cost is zero because it was not called, not an assumed free service. A toy 60-second extra preparation cost and 2-microsecond saving break even only after 30 million calls; these invented values are arithmetic, not measured costs. A 2x kernel affecting 20% of total runtime gives only 1.111x whole-workload speed under Amdahl's assumptions. Measure a real authorized caller before claiming operational benefit.

Kill or redirect when native code matches the candidate, a gain disappears under a stronger baseline/host boundary, compilation cannot amortize, required access is unavailable, or the candidate loses numerical/shape coverage. A reproducible negative result remains useful. Original contribution needs a minimized confirmed uncovered defect or justified missing contract at the current upstream version, independent replay and a maintenance plan. Reading a tutorial, reproducing old mutations or winning on a resized task is not novel compiler research.
