## A. vLLM: what the online-serving source actually measures

### R10-V1 — Open arrivals and concurrency limits are present; configured RPS is not achieved throughput

**Observed.** [`get_request`, serve.py:416–530](https://github.com/vllm-project/vllm/blob/aa3564ceefbd605f1d28238fa0fbbb964201c6b8/vllm/benchmarks/serve.py#L416-L530) precomputes gamma-distributed intervals (burstiness 1 is described as Poisson), supports deterministic intervals at infinite burstiness and self-timed traces, then yields against cumulative targets. For a fixed finite rate it rescales the sampled cumulative delays so the final target is `number of requests / request_rate`. Thus this is a finite trace with a normalized horizon; it is not an unconstrained independent Poisson-arrival experiment. The source comment supplies the intended seed-to-seed stability rationale. The scheduling loop uses wall-clock time; request measurement later uses `perf_counter`.

The main loop creates a task for each yielded input without awaiting its completion; the semaphore is inside the task. Therefore calling this simply a closed-loop benchmark would be wrong. Its [CLI explanation:1655–1665](https://github.com/vllm-project/vllm/blob/aa3564ceefbd605f1d28238fa0fbbb964201c6b8/vllm/benchmarks/serve.py#L1655-L1665) explicitly warns actual execution rate can fall below configured request rate under a concurrency cap. [`benchmark_start_time` through gather:1033–1108](https://github.com/vllm-project/vllm/blob/aa3564ceefbd605f1d28238fa0fbbb964201c6b8/vllm/benchmarks/serve.py#L1033-L1108) spans generation plus the final drain; [`calculate_metrics`:758–766](https://github.com/vllm-project/vllm/blob/aa3564ceefbd605f1d28238fa0fbbb964201c6b8/vllm/benchmarks/serve.py#L758-L766) divides successful completions/tokens by that whole benchmark duration.

**Acceptance implication (high consequence for interpretation).** Report configured rate, intended finite schedule/window, actual yielded/admitted counts and timestamps, successful completions, deadline-qualified correct outputs, and drain duration separately. Plot backlog and saturation against offered load. Do not relabel completed requests divided by generation-plus-drain time as offered load, steady-state capacity or accepted customer outcomes. The finite-horizon normalization can be retained, but its workload definition must be named.

### R10-V2 — Queue-inclusive percentiles exist, but not every kind of waiting is included

**Observed.** [`limited_request_func`:986–1002](https://github.com/vllm-project/vllm/blob/aa3564ceefbd605f1d28238fa0fbbb964201c6b8/vllm/benchmarks/serve.py#L986-L1002) preserves send/start time and records `client_queue_time = start_time - request_arrival_time`. However, that arrival timestamp is taken **after the generator yields and payload construction finishes**, at [1095](https://github.com/vllm-project/vllm/blob/aa3564ceefbd605f1d28238fa0fbbb964201c6b8/vllm/benchmarks/serve.py#L1095-L1102). The original desired schedule timestamp is not returned by this generator/serialized in the inspected result path. Queue time can include client task scheduling and pre-send work as well as semaphore waiting; it is not an isolated server-queue metric.

[`serve.py`:1342–1351](https://github.com/vllm-project/vllm/blob/aa3564ceefbd605f1d28238fa0fbbb964201c6b8/vllm/benchmarks/serve.py#L1342-L1351) constructs successful-request queue times when max concurrency is set and constructs `latency + client_queue_time` when configured request rate is finite. [`process_one_metric`:1417–1435](https://github.com/vllm-project/vllm/blob/aa3564ceefbd605f1d28238fa0fbbb964201c6b8/vllm/benchmarks/serve.py#L1417-L1435) supports `e2el_including_client_queue` if explicitly selected. The [CLI:1823–1841](https://github.com/vllm-project/vllm/blob/aa3564ceefbd605f1d28238fa0fbbb964201c6b8/vllm/benchmarks/serve.py#L1823-L1841) lists it; generative defaults are TTFT/TPOT/ITL, not every latency metric.

**Narrow correction.** Do not propose implementing a missing queue-inclusive feature. Select the existing option when applicable. It remains success-conditioned and starts at actual client arrival/yield, not the original intended schedule. Event-loop lateness/payload construction before timestamping and wall-clock adjustments are **unmeasured risks inferred from these paths**, not observed errors in a run. A load-generator fidelity audit needs intended versus actual timestamps on one monotonic basis and a check that the generator can sustain the target. `request_rate=inf` is a saturation/concurrency experiment, not a known external arrival process.

### R10-V3 — Native goodput is a timing SLO; success is not task correctness

**Observed.** In [`calculate_metrics`:619–677](https://github.com/vllm-project/vllm/blob/aa3564ceefbd605f1d28238fa0fbbb964201c6b8/vllm/benchmarks/serve.py#L619-L677), successful outputs supply latency arrays; failed outputs receive zero output length. Goodput checks only selected TTFT, TPOT and ordinary E2EL thresholds. The queue-inclusive option does not change that goodput calculation. TPOT is assigned zero for outputs of length at most one for goodput, while the TPOT percentile list contains only lengths greater than one. ITL flattens chunk intervals across requests, giving it a different sampling unit from request-level E2EL. If no successful latency exists, the percentile code uses a zero fallback at [758–790](https://github.com/vllm-project/vllm/blob/aa3564ceefbd605f1d28238fa0fbbb964201c6b8/vllm/benchmarks/serve.py#L758-L790); the separate warning/failure count must prevent that zero from becoming a performance result.

For the specifically inspected OpenAI **completions** backend, [`endpoint_request_func.py`:224–293](https://github.com/vllm-project/vllm/blob/aa3564ceefbd605f1d28238fa0fbbb964201c6b8/vllm/benchmarks/lib/endpoint_request_func.py#L224-L293) sets start time immediately before POST, marks success on status 200 plus at least one valid choice chunk, and sets latency to the most recent such chunk. It does not evaluate the answer against task ground truth. These observations should not be extrapolated to every endpoint implementation. SSE chunks may contain multiple tokens; ITL should not automatically be called a hardware per-token latency distribution.

**Acceptance implication (high).** Keep native timing goodput as a clearly named diagnostic. Add a separate numerator: **independently accepted, permitted output within the intended-arrival deadline**, divided by all offered requests and separately by elapsed time. Unknown, cancelled, timed-out, malformed and semantically incorrect cases need explicit states. Retain completion-conditioned latency percentiles alongside failure/deadline rates; do not invent a finite completion latency for non-completers. Audit the oracle for accepted-wrong and rejected-correct cases. No scalar produced here establishes semantic quality, policy compliance or value.

### R10-V4 — Warm state, deadlines and output-length policy can change the comparison

**Observed.** The reusable HTTP session has a [six-hour total client request timeout:841–858](https://github.com/vllm-project/vllm/blob/aa3564ceefbd605f1d28238fa0fbbb964201c6b8/vllm/benchmarks/serve.py#L841-L858), distinct from the readiness-check timeout. Readiness and optional warmups run before the timed main loop; warmups repeat the first request and gathered outputs are discarded, at [860–934](https://github.com/vllm-project/vllm/blob/aa3564ceefbd605f1d28238fa0fbbb964201c6b8/vllm/benchmarks/serve.py#L860-L934). `num_warmups` defaults to zero at [1756–1760](https://github.com/vllm-project/vllm/blob/aa3564ceefbd605f1d28238fa0fbbb964201c6b8/vllm/benchmarks/serve.py#L1756-L1760); that does not imply a cold server because a readiness request or previous traffic can warm it.

Model ID and tokenizer ID are chosen separately; omitted model selects the server's first model, at [2103–2124](https://github.com/vllm-project/vllm/blob/aa3564ceefbd605f1d28238fa0fbbb964201c6b8/vllm/benchmarks/serve.py#L2103-L2124). Token totals prefer response usage and otherwise retokenize generated text (or use one when no tokenizer exists), at [621–636](https://github.com/vllm-project/vllm/blob/aa3564ceefbd605f1d28238fa0fbbb964201c6b8/vllm/benchmarks/serve.py#L621-L636). Random and timed-trace modes force ignore-EOS to match requested lengths, at [2157–2186](https://github.com/vllm-project/vllm/blob/aa3564ceefbd605f1d28238fa0fbbb964201c6b8/vllm/benchmarks/serve.py#L2157-L2186). Temperature is no longer forced greedy by default, at [2223–2228](https://github.com/vllm-project/vllm/blob/aa3564ceefbd605f1d28238fa0fbbb964201c6b8/vllm/benchmarks/serve.py#L2223-L2228).

**Gate.** Fix model/tokenizer immutable revision, input/output distributions, sampling/EOS/stop policy, endpoint and server configuration, client/server hardware, placement/network, concurrency, prefix/cache state, warmup/compile/cold-start scope, and task quality before comparing throughput. Record separate cold and warm claims when relevant. The six-hour transport timeout is not a portfolio/business deadline. A client deadline/drop policy and server cancellation/resource-after-cancel measurement need their own approved design. Preserve detailed results: [`--save-detailed` and pruning:2404–2418](https://github.com/vllm-project/vllm/blob/aa3564ceefbd605f1d28238fa0fbbb964201c6b8/vllm/benchmarks/serve.py#L2404-L2418) control per-request material; saved model names/optional metadata are not a complete immutable hardware/runtime manifest.

## B. Inspect AI: accepted outputs, grader coverage and cost

### R10-I1 — Accuracy is conditional on available scored values

**Observed.** [`results.py`:166–177](https://github.com/UKGovernmentBEIS/inspect_ai/blob/6b3c96fa58f6c172f2feb2c9ed68718ec72c27c8/src/inspect_ai/_eval/task/results.py#L166-L177) first selects samples that have a score for that scorer. [`scorer_for_metrics`:396–430](https://github.com/UKGovernmentBEIS/inspect_ai/blob/6b3c96fa58f6c172f2feb2c9ed68718ec72c27c8/src/inspect_ai/_eval/task/results.py#L396-L430) removes NaN/unscored values; [480–482](https://github.com/UKGovernmentBEIS/inspect_ai/blob/6b3c96fa58f6c172f2feb2c9ed68718ec72c27c8/src/inspect_ai/_eval/task/results.py#L480-L482) records scored and unscored counts. [`accuracy.py`:29–37](https://github.com/UKGovernmentBEIS/inspect_ai/blob/6b3c96fa58f6c172f2feb2c9ed68718ec72c27c8/src/inspect_ai/scorer/_metrics/accuracy.py#L29-L37) averages the supplied values. Thus missing scorer records, unscored sentinels and planned tasks are distinct denominators. This is not concealed by the framework: [`EvalResults`:881–903](https://github.com/UKGovernmentBEIS/inspect_ai/blob/6b3c96fa58f6c172f2feb2c9ed68718ec72c27c8/src/inspect_ai/log/_log.py#L881-L903) exposes total planned samples, completed samples and, for graceful drain/cancel, resolved logged samples.

The native model grader calls a model and parses its verdict; an absent/invalid verdict returns `Score.unscored(reason="grader_failed")`, at [`scorer/_model.py`:283–359](https://github.com/UKGovernmentBEIS/inspect_ai/blob/6b3c96fa58f6c172f2feb2c9ed68718ec72c27c8/src/inspect_ai/scorer/_model.py#L283-L359). [`Score.unscored`:158–179](https://github.com/UKGovernmentBEIS/inspect_ai/blob/6b3c96fa58f6c172f2feb2c9ed68718ec72c27c8/src/inspect_ai/scorer/_metric.py#L158-L179) expressly preserves context while excluding it from metrics/reducers. The default grader role can fall back to the evaluated model when no optional role binding exists; see [model-grader parameters:84–95](https://github.com/UKGovernmentBEIS/inspect_ai/blob/6b3c96fa58f6c172f2feb2c9ed68718ec72c27c8/src/inspect_ai/scorer/_model.py#L84-L95). A separate role name is not proof of an independent oracle.

**Acceptance implication (high).** A report must show planned `(task ID, epoch)` trials, actually attempted/resolved trials, scorer coverage, missing/error/unscored counts, native conditional score, and independently accepted outputs per planned task. Keep grader failure distinct from task failure while counting both as unresolved acceptance. Validate grader confusion against independent expected states/labels, including permitted-but-unusual and fluent-but-wrong outputs. A task log status of `success` means run/error policy completion, not that every task answer was correct. Preserve multiple scorer and epoch/reducer definitions rather than mixing pass@k, average score and repeated success.

### R10-I2 — Dollar costs and grader usage are built in; unknown is not zero

**Observed.** [`ModelUsage`:17–69](https://github.com/UKGovernmentBEIS/inspect_ai/blob/6b3c96fa58f6c172f2feb2c9ed68718ec72c27c8/src/inspect_ai/model/_model_output.py#L17-L69) contains full-price input, output, cached read/write, reasoning and optional total-dollar-cost fields. Full-price input explicitly excludes cached input; blindly multiplying `total_tokens` by one rate is wrong. [`record_and_check_model_usage`:3088–3136](https://github.com/UKGovernmentBEIS/inspect_ai/blob/6b3c96fa58f6c172f2feb2c9ed68718ec72c27c8/src/inspect_ai/model/_model.py#L3088-L3136) calculates cost and records per-model/per-role sample and task contexts. The grader's ordinary `generate` call uses the same recording path; do **not** presume native grader usage is omitted. Task [usage collection:1254–1261](https://github.com/UKGovernmentBEIS/inspect_ai/blob/6b3c96fa58f6c172f2feb2c9ed68718ec72c27c8/src/inspect_ai/_eval/task/log.py#L1254-L1261) preserves aggregate model and role usage.

[`model_usage_cost`:3139–3202](https://github.com/UKGovernmentBEIS/inspect_ai/blob/6b3c96fa58f6c172f2feb2c9ed68718ec72c27c8/src/inspect_ai/model/_model.py#L3139-L3202) handles serving-model attribution and falls back to called-model prices with a warning when an unpriced serving model is reported. It returns `None` without cost data. [`compute_model_cost` / `sample_total_cost`:3309–3344](https://github.com/UKGovernmentBEIS/inspect_ai/blob/6b3c96fa58f6c172f2feb2c9ed68718ec72c27c8/src/inspect_ai/model/_model.py#L3309-L3344) applies separate cache rates, then sums only non-None usage costs. Therefore a numeric known-cost sum or cost-limit counter need not certify complete price coverage. `ModelUsage.__add__` also preserves a known side when the other cost is None; an aggregate number alone does not reveal missing-price components.

**Gate.** Save the exact model/provider/served-model identifiers, role bindings, price-data/config revision and billing assumptions. Report known priced spend **plus unknown-cost calls/usage**, not just a sum. Reconcile to provider bill/usage export where authorized; include local compute/allocation separately if applicable. Do not double-count reasoning tokens if already included in output billing. These are accounting requirements, not a current-price claim or an assertion that every provider normalization is correct.

### R10-I3 — Response replay, provider prompt caching and first-execution cost differ

**Observed.** A framework response-cache hit returns the saved output early at [`model/_model.py`:1494–1530](https://github.com/UKGovernmentBEIS/inspect_ai/blob/6b3c96fa58f6c172f2feb2c9ed68718ec72c27c8/src/inspect_ai/model/_model.py#L1494-L1530). It emits a cache-usage hook but bypasses ordinary provider-usage recording. The code [3113–3116](https://github.com/UKGovernmentBEIS/inspect_ai/blob/6b3c96fa58f6c172f2feb2c9ed68718ec72c27c8/src/inspect_ai/model/_model.py#L3113-L3116) explicitly states that cached reads consume no provider capacity and are excluded from reported provider rate. Provider prompt-cache tokens are different: their charges are calculated in the ordinary usage cost path.

**Preserved claim.** That is a reasonable marginal provider-cost convention. It is not evidence that generating those outputs originally cost nothing, nor that a cached repeated evaluation replicates live provider latency or independent model samples. Record replay-hit counts, cache policy/key, original generation provenance and whether the comparison is replay, incremental run spend or first/full acquisition cost. Offline teacher labels, synthetic-data generation and calibration collection outside this eval context require explicit ledger entries. No statement about their empirical amount is made here.

### R10-I4 — Retried attempts and scoring budgets require explicit reconciliation

**Observed.** The [sample retry loop:2268–2368](https://github.com/UKGovernmentBEIS/inspect_ai/blob/6b3c96fa58f6c172f2feb2c9ed68718ec72c27c8/src/inspect_ai/_eval/task/run.py#L2268-L2368) reruns an errored sample; each attempt initializes per-sample model accumulators at [2487–2489](https://github.com/UKGovernmentBEIS/inspect_ai/blob/6b3c96fa58f6c172f2feb2c9ed68718ec72c27c8/src/inspect_ai/_eval/task/run.py#L2487-L2489), with the reset defined in [`model/_model.py`:3051–3059](https://github.com/UKGovernmentBEIS/inspect_ai/blob/6b3c96fa58f6c172f2feb2c9ed68718ec72c27c8/src/inspect_ai/model/_model.py#L3051-L3059). This does not reset task-wide usage there. The final [sample serializer:3494–3512](https://github.com/UKGovernmentBEIS/inspect_ai/blob/6b3c96fa58f6c172f2feb2c9ed68718ec72c27c8/src/inspect_ai/_eval/task/run.py#L3494-L3512) stores current sample usage plus retry errors; the retry-error schema contains errors and recent events, not a complete aggregate cost counter. [3921–3949](https://github.com/UKGovernmentBEIS/inspect_ai/blob/6b3c96fa58f6c172f2feb2c9ed68718ec72c27c8/src/inspect_ai/_eval/task/run.py#L3921-L3949) retains events from the most recent ModelEvent onward. Simply summing final per-sample counters can therefore miss earlier sample-attempt usage. Conversely, summing every resumed/task-attempt aggregate may double-count inherited usage: task retry/reuse is a separate level. Use attempt IDs/provenance and reconcile, rather than assuming either sum is a universal total.

The visible solver [limit scope:2761–2776](https://github.com/UKGovernmentBEIS/inspect_ai/blob/6b3c96fa58f6c172f2feb2c9ed68718ec72c27c8/src/inspect_ai/_eval/task/run.py#L2761-L2776) includes sample token/cost/message/turn/time limits. Scoring occurs afterward with its own time allowance, half the original time limit when set, at [3041–3078](https://github.com/UKGovernmentBEIS/inspect_ai/blob/6b3c96fa58f6c172f2feb2c9ed68718ec72c27c8/src/inspect_ai/_eval/task/run.py#L3041-L3078). **Source-inspection inference:** the sample actor cost limit should not be advertised as a cap on combined actor-plus-grader cost merely because both appear in the final usage totals. A specific scorer can implement additional limits; this pass did not audit custom scorers or every nested limit context.

Provider exceptions/cancellations complete an error event and raise before the ordinary output-usage recording block, at [`model/_model.py`:1619–1715](https://github.com/UKGovernmentBEIS/inspect_ai/blob/6b3c96fa58f6c172f2feb2c9ed68718ec72c27c8/src/inspect_ai/model/_model.py#L1619-L1715). **Bounded inference:** without returned/reported usage, this path alone cannot certify the billed cost of an interrupted or failed request. A particular provider may normalize or expose it elsewhere; provider SDKs and billing exports were not audited. Do not claim all such attempts are unbilled or always omitted from actual invoices.

**Gate (high).** Predeclare separate actor, evaluator, preparation and full-run budgets; retain sample/task/provider retry counts and original IDs, failed/cancelled attempts, grader fan-out, replay provenance, runtime/tool/sandbox spend and human review/repair. Report cost per independently accepted task with all planned tasks retained. Dollar limits whose unpriced components are unknown are partial limits, not guaranteed spend ceilings.

## Arithmetic illustration — executed, but not a framework test

A tiny self-authored Python standard-library fixture used four fabricated requests. Desired arrival times were `[0,1,2,3]`; actual yields `[0,1.4,2.8,4.2]`; sends `[0,2,4,6]`; terminal times `[1,3,5,8]`. The first three were fabricated transport successes, only the first/third independently correct, and the last a timeout. With an eight-second whole run:

| Different question | Arithmetic result |
|---|---:|
| Successful completions / run second | 3/8 = 0.375 |
| Independently accepted outputs / run second | 2/8 = 0.25 |
| Median send-to-last-token latency, successes | 1.0 s |
| Median actual-arrival-to-last-token latency, successes | 1.6 s |
| Median intended-schedule-to-last-token latency, successes | 2.0 s |
| Correct within two seconds of intended schedule / all offered | 1/4 = 25% |

No finite all-request completion p99 was invented for the timeout. This illustrates why selecting vLLM's existing queue-inclusive metric still differs from preserving the intended schedule and acceptance contract. It is not a vLLM output/performance measurement.

A second fabricated ledger had ten planned agent trials, six scored (five judge-correct), two explicitly unscored and two errors with no scorer record. Conditional scored accuracy is 5/6 = **83.3%**; if four outputs pass independent acceptance, accepted/planned is **40%**. Assumed costs were actor $0.10, grader $0.04, reconciled failed provider attempts $0.03, offline teacher $0.20, tools $0.03 and human review $0.40: known recorded-model spend $0.14 differs from assumed full cost $0.80, or **$0.20 per accepted task**. The additional costs are invented illustration inputs, not discovered charges or observed software omissions. The executed fixture printed these values; it imported no audited framework.

## Residual unknowns and limits

1. No selected actual model, client/server hardware, task dataset, service version/configuration or provider price file was run or validated. The audited clients cannot establish physical throughput, energy, quality or business value by source reading.
2. vLLM client-generator overhead, wall-clock movement, cancellations, six-hour timeout behavior, prefix-cache effects and streaming chunk semantics remain to be measured on the selected endpoint. The audit covers the identified generation/completions paths, not every backend/audio/embedding mode. A desired timestamp manifest is a proposed extension to measurement, not a proven runtime omission under every dataset adapter.
